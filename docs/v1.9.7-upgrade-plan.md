# v1.9.7 依赖升级规划

> 目标:在 v1.9.6 基线上,完成核心依赖的安全与版本升级,重点是 **lance/lancedb 9.0 湖仓升级** 与 **ray 安全补丁**,并顺带收尾一批小版本。全程以「分批、可回滚、测试门控」推进。

---

## 1. 背景与目标

- v1.9.6 发布时(`pyproject.toml` 锁定)与 `uv.lock` / `.venv` 实际版本**严重不同步**(lock 仍停留在 pylance 4.0.1 / lancedb 0.30.2)。升级前必须先对齐基线。
- `lance 9.0.0` / `pylance 9.0.0` 已于 2026-07-24 发布,带来 **FTS v2 默认格式**;`lancedb` 已至 ~0.36。
- `ray < 2.56.0` 存在高危漏洞 **CVE-2026-57516**(代码注入),有强安全升级动机。
- 其余核心(fastapi / pydantic / openai / uvicorn / httpx / structlog 等)经核查**已是最新或接近最新**,本版不动。

**范围**:依赖版本升级 + 必要的 API 兼容适配。**不含**新功能开发。

## 3. 升级原则

1. **精确 pin 不松绑**:`daft / ray / lancedb / duckdb / pyarrow / metaflow` 维持 `==` 精确锁定(版本绑定矩阵要求,记忆约束:pyarrow 必须匹配 daft + lance bundle)。
2. **分批推进,每批可独立合并与回滚**:P0 安全优先 → P1 湖仓核心 → P2 小版本。每批单独 commit + 全量测试门控。
3. **lock 与 pyproject 同步**:每批结束后 `uv lock` + `uv sync`,确保三者一致。
4. **镜像 rebuild**:依赖变更需重建 `arrow-lake` 镜像(记忆:rebuild ~3–5min,走代理 `host.docker.internal:17887`)。
5. **数据兼容先行**:lance/lancedb 升级前,先在小数据集验证旧数据可读 + 索引可重建。

---

## 4. 分批升级方案

### 批 0:uv sync 基线对齐(前置,0.5 天)

**问题**:`uv.lock`(pylance 4.0.1 / lancedb 0.30.2)与 `pyproject.toml`(≥7.0 / ==0.33.0)不一致,`.venv` 实际跑旧版。

**动作**:
```bash
uv lock --upgrade-package pylance --upgrade-package lancedb
uv sync
```
**验证**:`.venv` 实际版本 = pyproject 声明;`arrow-lake version` 输出正确组件版本。

> 这一步把基线拉到 pyproject 声明的 0.33.0 / pylance 7.x,后续批次在此基础上再升。

---

### 批 1:P0 — ray 安全升级(2–3 天)

**动机**:CVE-2026-57516(代码注入,ray < 2.56.0)。

**动作**:
1. `pyproject.toml`:`ray[default]==2.54.1` → `==2.56.0`
2. **先验证 metaflow-ray 0.1.4 对 ray 2.56 的兼容性**(头号风险):metaflow-ray pin 较老,可能不支持 ray 2.56。若不兼容 → 评估 metaflow-ray 新版本 或 临时 pin ray 到 CVE 修复版(如 2.56 内的 patch)。
3. **评估 ray serve breaking**:Ray Serve 2.55+ 不再支持 ingress model multiplexing / 自定义路由。**项目 REST 用 FastAPI + uvicorn(非 ray serve),理论不受影响**——但需 grep 确认项目无 `ray.serve` 用法。
4. `uv sync` + rebuild 镜像。
5. ray data / 分布式路径回归:`daft.set_runner_ray()`、metaflow-ray flow。

**风险**:
- 🔴 **metaflow-ray 0.1.4 不兼容 ray 2.56** → 可能需升 metaflow-ray 或 pin ray。这是批 1 的 go/no-go 关口。
- 🟡 ray data 2.56 的 `to_pandas` 回归(有 opt-out flag `RAY_DATA_ENABLE_ARROW_BACKED_PANDAS_CONVERSION`)。

**go/no-go**:若 metaflow-ray 不兼容且无新版,批 1 降级为「pin ray 到 2.56.x + metaflow-ray 维持 + 监控」,或暂缓(风险接受评估)。

---

### 批 2:P1 — 湖仓核心升级 lancedb + pylance 9 + duckdb(3–5 天)

**本版主线**,与正在进行的 **LanceDB async FTS 迁移**(记忆 `project_lancedb_async_fts`:AsyncTable 0.33.0 原生 FTS/hybrid,3 处 `to_thread` 待迁)**合并推进**,省一次回归。

#### 2a. duckdb 1.5.2 → 1.5.5(0.5 天,先做,独立低风险)
- 纯 bugfix,API 兼容。
- OLAP 11 文件路径回归(`query sql / olap_query / materialize / daft`)。

#### 2b. lancedb 0.33.0 → 0.34(或 0.36)+ pylance → 9.0.0(2–4 天)
- **先确认 lancedb 0.34/0.36 的 pylance 依赖范围**:0.34 发布(2026-07-02)早于 pylance 9.0.0(2026-07-24),0.36 可能支持 pylance 9。选定目标版本后改 pin。
- **lance 9.0.0 breaking 全在 FTS**:
  - FTS v2 成为默认索引格式 → **新建 FTS 索引默认 v2**,旧 v1 索引可读。
  - 核心 lance 数据格式向后兼容(旧数据集可读)。
  - Rust API 改名(FMIndex)不影响 Python。
- **项目影响面**:
  - 直接 `import lance` 仅 1 文件(`lance.dataset` ×20, `LanceDataset` ×2)→ 直接改动小。
  - lancedb 深度用 async API(`AsyncTable` ×11, `Connection` ×53)→ **主要工作量**。
- **必须做**:
  - 完成 async FTS 迁移(3 处 `to_thread` → AsyncTable 原生:`fts.py:411` / `hybrid.py:235` / `faceted.py:234`)。
  - **重建现有 FTS 索引为 v2** + 对比检索质量(项目 FTS 是核心,中文 jieba)。
  - async search / hybrid / faceted / vector 全路径回归。
- **数据兼容验证**:芜湖/业务数据集(jd_ddd / wuhu_report)旧 lance 数据可在新版读取。

**风险**:
- 🔴 lancedb 0.33→0.36 跨 3 个小版本,async/search API 变更是最大未知。
- 🟠 FTS v2 检索质量与 v1 一致性(需用真实数据集对比)。
- 🟡 版本绑定:lancedb 新版是否强制升 pyarrow(若强制,连带 daft 评估)。

---

### 批 3:P2 — 小版本收尾(1 天)

- metaflow `==2.19.22` → `==2.19.35`(2.19 系列内,`spin` 命令等,低风险)
- sentence-transformers `5.4.0` → `5.6.1`(v5 系列内,小升)
- tantivy 评估小升(FTS v2 相关,与批 2 协同)
- 其余确认持平(fastapi/pydantic/openai/uvicorn/httpx/structlog/tenacity/rich/click 均已新)

每项改 pin + `uv sync` + 针对性回归(metaflow flow / embed / FTS)。

## 6. 风险与回滚

| 风险 | 等级 | 缓解 |
|------|------|------|
| metaflow-ray 0.1.4 不兼容 ray 2.56 | 🔴 | 批 1 go/no-go 关口;不兼容则 pin ray 或暂缓 |
| lancedb async API 变更 | 🔴 | 与 async FTS 迁移合并做;逐文件迁移 + 单测 |
| FTS v2 检索质量漂移 | 🟠 | 真实数据集对比 v1/v2;保留 `LANCE_FTS_FORMAT_V1` 回退环境变量 |
| 全量回归不稳定(测试隔离污染) | 🟠 | 记忆已知问题;分模块跑 + `-x` 早停 |
| 版本绑定断裂(lance↔lancedb↔pyarrow↔daft) | 🟡 | 每批 `uv lock` 解析验证;不松绑 `==` |
| 镜像 rebuild 网络/代理坑 | 🟡 | 走 `host.docker.internal:17887` + uv cache 复用 |

**回滚策略**:每批独立 commit;若某批测试红,`git revert` 该 commit + `uv sync` 回退 + 旧镜像 tag 回滚。镜像保留前序 tag(`arrow-lake:1.9.6`)作为回退点。

## 7. 验证策略

1. **单元/集成**:`pytest -q --tb=line --no-header`,分模块 + 全量(39min,记忆值)。
2. **E2E**(host facade 或容器 REST):
   - 芜湖 wuhu_report(大 KG,18045 顶点)—— 压测 lance/lancedb 写入 + 读取 + FTS。
   - jd_ddd(业务 DDD)—— RAG hybrid + FTS v2 质量对比。
   - noaa_china(结构化)—— OLAP/duckdb 路径。
3. **FTS v2 对比**:同一数据集,分别用 v1/v2 索引跑 `text_search`/`hybrid_search`,对比 top-k 结果与延迟。
4. **镜像验证**:rebuild 后 `arrow-lake version` + 冒烟(serve + ingest + query)。

## 8. 待确认项核实结果(2026-07-30 核实)

- ✅ **daft 0.8.0**:**未发布**(最新 0.7.21, 2026-07-17)。daft 持平 0.7.x,批 3 小升 0.7.8→0.7.21(低风险);0.8 待发再评估。
- ✅ **lancedb-pylance 兼容**:lancedb **0.36.0**(最新)的 pylance 是**可选 extra**(`pylance>=5.0.0b5`),tests extra pin `pylance==9.0.0`。**兼容 pylance 9.0.0**。→ 批 2 目标锁定 **lancedb 0.36.0 + pylance 9.0.0**。
- ✅ **metaflow-ray 兼容**:metaflow-ray `setup.py` 的 `install_requires=[]`,**不声明 ray pin**(ray 由环境提供)→ ray 升 2.56 无 pin 阻塞。运行时仍需验证 metaflow-ray 0.1.4 代码不依赖 ray 2.56 废弃 API。
- ✅ **项目 ray.serve**:确认用了 `embed/ray_serve_encoder.py`,但用法为 `get_deployment + handle.remote`(**客户端 consumer**),**不在** Ray Serve 2.55+ breaking 范围(ingress multiplexing/自定义路由),且有 local fallback 兜底。批 1 风险低-中(留意 `get_deployment` 可能的 deprecation 警告)。
- ✅ **tantivy 与 FTS v2**:FTS v2 是 lance 文件格式层(lance 内嵌 tantivy),与项目 `fts` extra 的外部 tantivy 包(0.25)不同层面,互不影响。关闭。

**go/no-go 结论**:
- 批 1(ray 2.56.0)**GO** — metaflow-ray 无 pin 阻塞;ray.serve 用法不在 breaking 范围。
- 批 2(lancedb 0.36.0 + pylance 9.0.0)**GO** — 兼容性确认。
- 两个批次均可推进,主要剩余工作量在 async FTS 迁移 + 全量回归(代码层),非依赖解析层。
