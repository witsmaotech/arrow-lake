01产品定位与核心命题

Arrow Lake 是面向 AI/ML 团队的生产级多模态数据湖仓库。传统智能检索架构往往是「向量库 + 关系库 + 图谱 + 检索系统」拼装四个组件，数据跨组件搬运、一致性难保证、运维复杂。Arrow Lake 的命题是收敛——一份列式湖仓底座同时承载五类能力，三种入口归一到同一个 Lake facade。

核心命题

让数据从摄入到可被 RAG / KG / 分析消费的全链路，在一个 facade 内可治理、可审计、可离线运行。v1.9.6 把这条链路从「能用」推进到「可信赖」：RAG 可溯源防幻觉 · 治理兑现（masking + 血缘）· 安全 fail-closed · 部署自包含。

五能力一体

能力引擎入口
向量检索 ANNLance 索引（IVF_PQ / HNSW / SQ / RQ）经 DuckDB vector_searchLake.search()
全文检索 BM25Lance FTS 倒排（Tantivy + jieba）Lake.text_search()
OLAP 分析DuckDB lance_scan + DuckLake 物化视图Lake.olap_query()

多模态：文本（bge-m3 / Qwen3-Emb，1024 维）、图像（CLIP text+image 双塔）、音频 / 视频（Whisper / decode）统一进 Lance 多模态向量列 + MinIO blob 原文，支持文搜图 / 图搜图 / 图搜文。

设计哲学

Facade + Mixin 组合
一个 Lake 拥有全部能力，内部按子系统懒加载、按能力桥接（Bridge + Protocol）。
优雅降级是一等公民
Ray 不可用→本地、MinHash→CPU、KG→Vector RAG、Gremlin→REST。基础设施不全也持续服务。
配置驱动 · 四层覆盖
代码默认 < .env < 环境变量 < YAML，34 个子配置覆盖每个子系统。
压测驱动 · 不投机优化
gate 框架对 async / 分布式索引 / ColBERT 逐项裁决，数据证明该做才做。

02五层贯穿，治理横切

请求自上而下穿越 ① 接入 → ② 能力 → ③ 计算 → ④ 存储引擎 → ⑤ 持久化，治理 / 可观测 / 安全作为横切面贯穿全部层级。每层只依赖其直接下一层；知识图谱是能力层直达持久化的唯一旁路。

① 接入层Entry
四入口归一到 Lake facade：SDK（Python）· REST（FastAPI，20 routers / 159 routes）· CLI（16 组）· Console（原生 JS，同源 mount /console，复用 REST + RBAC，bind-mount 改即生效）。
② 能力层Capabilities
摄入：ingest_documents_and_index 收口 parse→store→embed→FTS→vector 一条龙，SDK=HTTP 对齐。检索：vector / fts / hybrid(RRF) / faceted / ensemble + cross-encoder reranker。RAG：多策略 + 会话 + 引用 + 流式 + faithfulness verify + GraphRAG。KG：hyper-extract 抽取 + per-dataset 图 + Gremlin 注入防御。
③ 计算层Compute
DuckDB OLAP：主力查询路径（olap_query / vector_search / fts 全经 DuckDB）。嵌入器矩阵：Local / Daft / CLIP / RayServe。clean 写回：语义 steps→SQL→restore_dataset 原地清洗 + 派生血缘。
④ 存储引擎Engines
LanceDB（Table / Namespace / 索引 / 版本 / tags / branches）+ HugeGraph（动态图 kg_{ds}）+ Gravitino（catalog 联邦 + tag-driven ACL）。
⑤ 持久化Persistence
数据面：MinIO/S3（Lance 列式 + 对象）+ HugeGraph rocksdb + DuckDB 文件。控制面：libSQL system_db（9 store：rbac / identity / catalog / task_history / lineage_index / rag_session / governance / user_state / ingest_dlq），opt-in + fail_close / fail_soft 双模。
⟂ 横切面

治理（Gravitino catalog / masking / lineage / audit）· 可观测（structlog JSON + Prometheus + OpenTelemetry）· 安全（RBAC 3 级 + JWT/API Key + 注入防御 + 限流）——经 hook / 中间件作用于各层，不进入主调用链；控制面状态由 system_db 持久化。

03技术栈 · DARMU

记忆口诀 DARMU（Daft + Arrow/Lance + Ray + Metaflow + dUckdb），外加 HugeGraph 图谱层、Gravitino 治理层、libSQL 控制面与 Console 前端。

层技术角色

应用层LanceDB 0.33.0向量库 SDK：Table / Namespace / 索引 / 版本 + search_async
分布式Ray 2.54.1head + worker + GPU；KG 构建 / 批嵌入

图谱HugeGraph 1.7知识图谱存储 + Gremlin 遍历；per-dataset 动态图
治理Apache Gravitino 1.3.0统一 catalog + tag-driven ACL + masking policy + retention
对象存储MinIO / S3blob 原文 + 备份
缓存 / 任务Redis ≥5分布式会话 + JWT 黑名单 + 任务跨 worker + rate_limit / lockout

LLM / 嵌入OpenAI / Anthropic / Ollama / vLLM / DeepSeek / 百炼RAG + KG 抽取；cross-encoder reranker (bge-reranker-v2-m3)
关键澄清

DuckDB 是主力查询路径而非 fallback。olap_query / vector_search / fts 全部由 DuckDB 执行（40+ 处调用），LanceDB 提供 Table / 索引 / 版本管理 API，DuckLake 在其上提供物化视图。三者分工见 ADR-06。

05核心业务流程

5.1文档摄入 → 索引

1
POST /datasets/{name}/ingest/documents
支持多格式（PDF / Office / 图像 / 混合）+ append 到已存数据集。
2
parse → chunk → embed → store (Lance)
parse 走 kreuzberg / docling；7 种分块；多模型嵌入；写入 Lance 列式表。
3
auto create_vector_index
≥256 行建 IVF_PQ；<256 行 WARN skip（brute-force）。
4
auto FTS 索引
v1.9.5 起 hybrid 默认生效；v1.9.6 ingest_documents_and_index 收口，SDK = HTTP 对齐。

5.2RAG 问答 · 防幻觉闭环

七步闭环，每条论断可追溯到源 chunk 与检索分数；流式响应首帧 citations、末帧 latency + verification。

1
query transform
HyDE / multi_query 改写（extract_llm=qwen-turbo，快）。
2
retrieval · hybrid
vector + fts，RRF 融合。
3
rerank · cross-encoder
bge-reranker-v2-m3（本地 /opt/models/），连续分排序。
4
GraphRAG 三路并行
asyncio.gather(vector + search_ka + neighbor)，use_kg=true 时启用。
5
context assembly
token budget 组装上下文。
6
LLM generate · streaming
qa_llm=qwen-plus@16384（最优 QA）。
7
faithfulness verify
逐句 vs context → support_ratio / unsupported；embedding cosine（默认）+ LLM judge（opt-in）。

5.3KG 构建 + GraphRAG

1
kg_build(dataset) → feed_text chunks
hyper-extract 经 snap / strict / enum 质量门。
2
MERGE_FIELD 合并
非 LLM，稳定 15% 内存，治 BALANCED grouped OOM。
3
HugeGraph upsert
per-dataset kg_{ds}，PRIMARY_KEY 幂等。
4
build_index + GraphRAG
KA LRU mtime 失效；三路并行 retrieve（109s → 50s）。

5.4治理闭环 · masking + lineage + audit

1
mask-preview
POST /datasets/{name}/quality/mask-preview（ADMIN，列名白名单）。
2
create policy
POST /gravitino/policies/masking（function 4 选 1，审计入 Lance）。
3
enforce
RBAC _apply_masking 对 VIEWER 透明（fail-closed 返空表）。
4
lineage
GET /lineage/graph/{name}?max_nodes=500 + /history（列级血缘）。
5
audit
GET /audit/query?event_type=masking_policy_created（HMAC 签名，零新表）。

5.5OLAP + 清洗写回

1
POST /datasets/{name}/query/olap
DuckDB SQL，RBAC 行 / 列 ACL。
2
POST /datasets/{name}/clean
语义 steps → SQL → restore_dataset 写回；lineage 自动记 clean 派生边（列级）。

06横切关注点

6.1安全 · fail-closed 主线

原则：信任边界出错向安全一侧失败，绝不向数据泄露失败。

路径失败场景fail-closed 行为
masking _apply_masking引擎抛错 / 未知函数 / hash 缺 key返空表 slice(0,0)
row-filter _apply_row_filter表达式不可解析 / 列缺失 / 类型不匹配返空表
masking _fetch_rulesGravitino 拉规则失败raise RuntimeError（不返空规则集）
启动MASKING__HMAC_KEY 缺失启动阻断（ALLOW_MISSING_KEY=1 opt-in）
mask-preview列名非法标识符白名单拒（防 SQL 注入），端点 ADMIN
lineage 图谱节点 / 边标签HTML 转义（vis title + DOT / Mermaid，防 XSS）

其他：RBAC 3 级（VIEWER / EDITOR / ADMIN）+ API Key / JWT（Redis 黑名单）+ 注入防御（Gremlin 参数化 / SQL prepared / 路径标准化）+ 限流。

6.2治理

  • Gravitino：统一 catalog，tag-driven ACL，masking policy，retention。
  • masking：4 函数（redact / hash 128 位 / partial / nullify）+ HMAC fail-fast + mask-preview + audit（复用 Lance audit_record，零新表）。
  • lineage：lineage.html 可视化（vis-network ≤2000 / G6 v4 更大）+ 列级血缘 + max_nodes 截断 + stats.truncated 透明告知。
  • audit：HMAC-SHA256 防篡改，每个状态转换记录（摄入 / 验证 / 分块 / 嵌入 / 查询 / 清洗 / masking 策略）。

6.3可观测

structlog JSON 日志 + Prometheus 指标 + OpenTelemetry（Jaeger，opt-in --profile tracing）+ audit 全覆盖（structlog + libSQL 双写）。

07部署架构

7.1镜像 · 模型 bake，离线就绪

v1.9.6 核心改进：模型权重 bake 进镜像，服务启动零网络下载（HF_HUB_OFFLINE=1）。

镜像基础模型大小
arrow-lake:1.9.6（CPU）python:3.12-slimreranker 2.2G (modelscope) + docling 506M (HF)16.8GB
arrow-lake:1.9.6-gpunvidia/cuda:12.4.1-runtime同上 + cu124 torch~18GB

reranker 走 modelscope 缓存（HF hub 国内受限）→ 本地路径加载 CrossEncoder("/opt/models/...")；docling 走 HF cache（HF_HOME）。build 时 BuildKit named context --build-context 指向 host 缓存，零下载。

7.2容器栈 · prod_minimal

11 服务：api / minio(+init) / nginx / lance-rest / hg-server(+hubble) / redis / system-db / gravitino(+init) / ollama-relay / proxy-forwarder。

  • api 容器 read_only: true——改 Python 需 rebuild 或 dev.override 热重载。
  • WSL2 mirrored 网络：容器外网经 socat 中继（ollama 11534 / proxy 17887）。
  • NO_PROXY 必含 host.docker.internal + 内部服务名。

7.3控制面 · system_db

libSQL 接管控制面（v1.9.0），opt-in（SYSTEM_DB_ENABLED=true）。数据面零触碰——9 个 store 覆盖 RBAC / identity / token / catalog / 任务 / lineage / RAG 会话 / governance，按重要性分 fail_close（RBAC / identity）与 fail_soft（catalog / tasks / rag）双模。

09关键决策 · ADR

ADR-1

模型 bake 进镜像 vs 运行时拉

决策：bake（reranker + docling）。
理由：生产 / 离线自包含、首启快、版本固定、多副本一致。代价：镜像 +4.6GB。
ADR-2

fail-closed 默认

决策：masking / rbac 异常返空表或 raise，不泄露未脱敏。
理由：隐私 / 授权路径上宁可空结果也不泄露。与 RBAC「默认拒绝」一致。
ADR-3

cross-encoder reranker 默认

决策：bge-reranker-v2-m3（连续分，替 Ollama 二值判断）。
理由：检索质量是 RAG 头号因子；cross-encoder 排序优于二值。CPU 可跑，GPU 更快。
ADR-4

masking HMAC fail-fast

决策：缺 key 启动阻断（ALLOW_MISSING_KEY=1 opt-in）。
理由：hash 脱敏需密钥签名；静默 fallback nullify 是合规隐患。
ADR-5

GraphRAG 模板方法 + 三路并行

决策：super().query() 单一模板 + _extra_context_task 钩子；asyncio.gather 三路。
理由：消除子类复制（parity bug）；并行砍延迟 40–50%。
ADR-6

reranker 经 modelscope + 本地路径

决策：bake modelscope snapshots → /opt/models/，RERANKER_MODEL=本地路径。
理由：HF hub 国内受限（hf-mirror 不稳）；modelscope 缓存可用，离线加载。
