# v1.8.9 — KG 双阶段 LLM 拆分（抽取 vs 问答）

## Context

KG 流程里 LLM 用于两个关注点截然不同的阶段，当前**共用一个 `llm` 配置**：

1. **知识解析构建**（`kg_build` → hyper-extract `feed_text` 结构化抽取）：要 **json_schema 约束解码 + 高吞吐 + 低成本** → 轻量模型够用（ministral-3:3b / 百炼 qwen-turbo）。
2. **RAG 问答召回**（`load_ka_for_query` → `ka.chat()` 生成回答）：要 **强推理 + 中文生成质量** → 旗舰模型更合适（deepseek-v3 / qwen-max / qwen3.5:27b）。

现状：`HEExtractor` 持有单个 `_chat_client`（`_get_chat_client()`，由全局 `llm` + `he_model` 名覆盖构建），BUILD 的 `_create_ka` 和 QUERY 的 `load_ka_for_query → _create_ka` 都用它。

**目标**：拆成两个可独立配置的 LLM，向后兼容（不设则回退全局 `llm`）。部署默认：抽取=ministral-3:3b（保持），问答=百炼 deepseek-v3（新），其余候选在 compose env 注释为示例。

## 当前架构

- `arrow_lake/config/rag.py`：`LLMConfig`(L12) 全局；`HugeGraphConfig.he_model`(L177) 仅模型名覆盖。
- `arrow_lake/knowledge_graph/he_extractor.py`：`__init__`(L109) 存 `_llm_config/_model/_hugegraph_config`；`_get_chat_client`(L162) 单例缓存（百炼走 `create_client(bailian:...)`，否则 `ChatOpenAI`）；`_create_ka`(L234) 内部调它；`build_dataset_ka`(L612,L641) BUILD；`load_ka_for_query`(L268) QUERY。
- `arrow_lake/_lake_kg.py:_create_kg_extractor`(L185) 传 `self._config.llm + model=hg.he_model + hugegraph_config=hg`，实例缓存共用。

## 实施（向后兼容）

### 1. 配置 `rag.py` HugeGraphConfig
```python
he_extract_llm: LLMConfig | None = None   # KG 抽取; None → 全局 llm (+ he_model)
he_qa_llm: LLMConfig | None = None        # RAG 问答; None → 全局 llm
```

### 2. 抽取器 `he_extractor.py`
- `__init__` 解析双配置：`_extract_llm_cfg = hg.he_extract_llm or llm_config`（model 用 `he_model or cfg.model`）；`_qa_llm_cfg = hg.he_qa_llm or llm_config`。
- `_get_chat_client()` 体抽成 `_build_client(cfg, model)`；保留 `_get_chat_client()` 作 extract 别名；新增 `_get_extract_client()` / `_get_qa_client()`。
- `_create_ka(template, *, llm_client=None)`：传入 client 或默认 extract。
- `load_ka_for_query` → `_create_ka(template, llm_client=self._get_qa_client())`；`build_dataset_ka` 不变（默认 extract）。

### 3. 部署 `docker-compose.prod_minimal.yml` api env
QA=百炼 deepseek-v3，extraction 留空（回退全局 ministral），候选注释：
```yaml
ARROW_LAKE__HUGEGRAPH__HE_QA_LLM__PROVIDER: openai
ARROW_LAKE__HUGEGRAPH__HE_QA_LLM__API_BASE: https://dashscope.aliyuncs.com/compatible-mode/v1
ARROW_LAKE__HUGEGRAPH__HE_QA_LLM__API_KEY: "${DASHSCOPE_API_KEY}"
ARROW_LAKE__HUGEGRAPH__HE_QA_LLM__MODEL: deepseek-v3
# 候选: qwen-max / 本地 qwen3.5:27b (api_base=http://host.docker.internal:11534/v1)
# 抽取换百炼轻量: ARROW_LAKE__HUGEGRAPH__HE_EXTRACT_LLM__MODEL: qwen-turbo (同 api_base/key)
```
百炼容器内须走代理（proxy-forwarder 17887→7887），dashscope 不能进 NO_PROXY。DASHSCOPE_API_KEY 放 `deploy/.env`。

### 4. 测试 `tests/unit/kg/test_he_extractor.py`
mock `_build_client`，断言 load_ka_for_query 用 qa 配置、build_dataset_ka 用 extract 配置；均 None 时回退全局 llm（向后兼容）。

## 验证
1. host `pytest tests/unit/kg/ -q --tb=line`。
2. `make -C deploy prod-minimal-build` → recreate → healthy。
3. 进容器确认 `_create_kg_extractor` 解析到 extract=ministral-3:3b / qa=deepseek-v3。
4. REST `POST /kg/ask`（复用 jd_ddd）：`retrieval_count>0` + 回答质量（deepseek 优于 ministral）+ 日志确认 chat 打到 dashscope。
5. 回归 `POST /kg/build` 仍走 extract（ministral）。

## 风险 / 取舍
- 百炼 QA 走代理：链路/key 缺失则 chat 失败；回退注释 he_qa_llm → 全局 ministral。
- **已排除**：`create_client`(client.py:400) 只 `create_llm` 返普通 `BaseChatModel`，不绑 json_schema（结构化绑定在抽取 feed_text `.parse()` 时做；chat 是纯生成）→ deepseek-v3 经 create_client 做 chat 安全。
- **不拆**：embedder 两阶段共用（FAISS 索引 build/query 维度须一致）。
- `search_ka` 也走 `load_ka_for_query`（qa client 建 KA）但 search 不调 LLM，无害。
- 3 级 env 嵌套（`HUGEGRAPH__HE_QA_LLM__MODEL`）pydantic-settings v2 支持，impl 验证。
- 优先级：`he_extract_llm`(全配置) > `he_model`(名) > 全局 `llm`。
