Gravitino 元数据治理

可选元数据治理层：目录浏览、标签分类、合规策略、ML 模型注册、统计信息与优雅降级。理解 Gravitino 与 Turso/libSQL RBAC 的职责边界。

难度 · 进阶 耗时 · 20 分钟 依赖 · Gravitino 1.3.0 + Lance REST
状态：可选治理层

Gravitino 是 Arrow Lake 的可选元数据治理组件（RBAC/tag/血缘/fileset 治理），不在数据/查询热路径上：数据集 CRUD、查询、KG、search、RAG 均不依赖 Gravitino。卡死或不需要时，设置 gravitino.enabled: false 临时关闭即可，核心功能完全不受影响。本章对应 Arrow Lake v1.9.6，Gravitino server 已升级至 1.3.0。

RBAC 说明（v1.9.0+）

访问控制的一等持久化后端是 Turso/libSQL（RbacStore，fail-close），不是 Gravitino。GravitinoRBACBridge 仅是可选旁路——Gravitino 关闭时 RBAC 照常生效，不要高估 Gravitino 角色的作用。

2配置

Gravitino 默认关闭（enabled: false）。启用时所有调用均包装在 try/except 中——Gravitino 不可用时 Arrow Lake 使用本地 DuckDB/Lance 目录继续正常运行。

新入职数据工程师探索数据湖中有哪些数据集：浏览 catalogs → 列出 tables → 查看单个表结构。

5场景 C — 合规策略：保留与脱敏

合规官执行数据保留规则和列级脱敏。策略将治理意图与执行分离：声明式定义规则，再应用到表。

必填 function 字段

脱敏策略的 function 必须是 redact/hash/partial/nullify 之一，否则返回 400。省略时默认 redact。策略存储在 Gravitino，但执行由 MaskingEngine（读取路径）与 RetentionEnforcer（后台线程）落地——见第 17 章脱敏。

6场景 D — ML 模型生命周期

模型目录将版本管理与服务解耦：用别名（latest、production）控制哪个版本用于何处——更新别名，而非代码。

7场景 E — 统计信息与场景 F — 优雅降级

统计信息采集后以 stats.* 前缀存为 Gravitino 表属性；查询引擎可据此做 join 排序与过滤下推决策。大量摄取后定期采集。

优雅降级

Arrow Lake 设计为优雅降级：Gravitino 是增强层，不是硬依赖。核心操作（ingest / search / query）始终可用；元数据治理功能在不可用时降级为 503。客户端应把 /api/v1/metadata/* 返回的 503 视为"功能不可用"，而非需要重试的错误。

8后台同步与熔断

GravitinoSyncScheduler 作为后台守护线程运行在 API 进程中：每隔 sync_interval_seconds 执行 sync_outbound（DuckDB → Gravitino）与 sync_inbound（Gravitino → DuckDB），通过 GravitinoBridge.lock 保证线程安全。

熔断器（v1.9.6）

连续 5 次同步周期失败后调度器主动停止同步线程（而非无限重试），避免慢速远程调用期间持有锁阻塞请求处理。触发后日志输出 gravitino_sync_circuit_open，提示设 gravitino.enabled=false 或修复 server/版本后重启——治理层永远不会拖垮数据面。

10最佳实践与反模式

实践指南
标签命名小写 + 下划线 + 域前缀：pii、fin_revenue、gdpr_subject
粒度标记列而非仅标记表——实现精细脱敏
策略命名{域}_{类型}_{范围}：gdpr_retention_90d、fin_mask_email
模型别名始终维护 production 和 latest；URI 用不可变路径（s3://models/name/v3）
同步30 秒默认足够；不低于 5 秒；批量操作前检查健康
常见反模式

跳过健康检查就批量治理；期望实时同步（后台是最终一致，5-300s 延迟）；过度打标签使治理更难；忽略 503 当错误重试。

11v1.9.6 — 1.3.0 升级与可靠性

v1.9.6 把 server 与 SDK 均升到 1.3.0，并修复四处 SDK 兼容性问题：

  • docker 布局变更：GRAVITINO_HOME=/opt/gravitino（旧版 /root/gravitino），数据卷须挂 /opt/gravitino/data。升级走全新启动（重建空卷后重跑 gravitino-init，实际数据在 MinIO 不受影响）。
  • Catalog S3 属性用 s3.*：s3.endpoint/s3.access-key-id/s3.secret-access-key，location 用 s3://。旧的 fs.s3a.* 在 1.3.0 fileset catalog 上不生效。
  • as_schemas()（非 as_schema_catalog()）：SDK 1.x 删了旧方法，改 as_schemas() 返 SupportsSchemas。
  • 1-level namespace：list_filesets(ns) 的 ns 要 1 级（只 schema），3 级会报 must have 1 level。
  • 代理中和：Docker daemon 自动注入的 HTTP_PROXY 致 s3a SigV4 被改 → minio 403。compose 显式置 HTTP_PROXY/HTTPS_PROXY: "" + NO_PROXY: "*" 覆盖。
排查口诀

改 SDK 调用前先核实方法名：docker exec api python -c "from gravitino import Catalog;print([m for m in dir(Catalog) if 'schema' in m or m.startswith('as_')])"。sync 连续失败看 gravitino_sync_circuit_open（5 次后停）。403 多半是 s3a 误配（改 s3.*）或代理注入。Gravitino 卡死时最简：gravitino.enabled=false 临时关。
