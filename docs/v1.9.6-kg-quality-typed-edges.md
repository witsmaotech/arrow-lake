# v1.9.6 KG 质量治理：prompt 收紧 + 动词驱动 typed 边 + 抽取模型升级

> 起因：实测 `wuhu_report` 的 KG（kg_wuhu_report）语义质量差，定位根因后做治本改动。本文记录分析 + 设计。

## 1. 问题实测（2026-07-29）

`wuhu_report`（芜湖市城市生命线安全工程一期建设方案，552 页政企文档，1252 chunk）的 KG：
- 模板 `project_concept_graph`（优质模板：22 实体类型 + 16 关系，definition 100% 填充）
- 抽取 LLM `qwen-turbo`（百炼），QA `qwen-plus`
- 规模：**9829 顶点 / 24936 边**

### 1.1 退化抽取（最严重）

顶点分布：entity 8568（87%）/ chunk 1252 / organization 8 / document 1，**person/location/concept/event 全 0**。

entity.type 头部被**裸数字实体**占据：

| type | 数量 | 典型 name | 典型 definition（编造）|
|---|---|---|---|
| 主体 | 2529 | `12` / `15` / `16` | "12是监测值守服务的单价（万元/年）" |
| 指标 | 1457 | `17` / `18` / `20` | "项目工作量，表示完成该项目所需的人月数量" |
| 数据 | 617 | `30` / `35` | "显示屏播放器的数量" |
| 技术 | 775 | `2G` / `3G` / `4G` | "支持2G通信协议的移动网络技术" |

正文 chunk[351] 明明有真实体（裂缝计 / 主梁 / 临江桥 / 裕溪河大桥 / 桥梁防船撞主动预警系统 / AIS），KG 里却是 `12`/`15`/`16`。~4000 个实体是数字/编号，definition 全是编造（模板强制填 def + 弱信号 → hallucinate）。

### 1.2 typed 结构全塌缩

边分布：references 13097（结构）/ related_to 9336（语义）/ contains_chunk 1252 / next_chunk 1251。**typed 边 part_of/belongs_to/located_in/participates_in/depicts 全 0**，9336 条语义关系全塞泛化 `related_to`。语义密度仅 1.1 条/实体，relation 描述同义重复（"指标关系"×N）。

## 2. 根因（两轮代码探索确认）

**关键鉴别**：模板本身没问题（project_concept_graph 是优质模板，在项目方案书等定性文档上 100% def 质量碾压 entity_graph）。问题在三个独立的可治理点：

1. **prompt 不够硬** — `project_concept_graph.yaml` 的 `rules_for_entities` 只有一条弱规则"不抽取规格碎片如 5*8/4U"，挡不住把数量/编号/型号当实体。定量工程文档（满篇设备个数/尺寸/规格/报价）尤其易触发。

2. **路由不认域类型** —
   - `_ENTITY_TYPE_LABELS`（entity_router.py:46-52）只认 13 个 key → 4 个 typed 标签（person/org/location/event，concept 故意不映射）。project_concept_graph 的 22 个域类型里**只有 `组织` → organization**，`主体/角色/区域` 都 → None → 落 generic `entity`。
   - `DEFAULT_RELATION_ROUTES`（entity_router.py:55-93）只 4 条，3 条要 source=person、1 条要 event，project_concept_graph 都不产生 → **所有关系全塌 related_to**。schema 里的 `part_of`(entity→entity)**无任何路由可达**。
   - project_concept_graph 的 16 个 relation 动词（包含/属于/采用/部署/处理…）全不在任何 route 的 synonym 集里。

3. **抽取模型偏弱** — qwen-turbo 在 552 页政企文档上数字幻觉严重（小模型 + 复杂结构化抽取）。

## 3. 设计（治本三改）

### 改动 1 — 抽取 prompt 收紧（`templates/project_concept_graph.yaml`）

`rules_for_entities.zh` 末条弱规则替换为硬规则：**严禁把纯数字/数量值/尺寸/规格值/编号/型号/页码/章节号作为实体 name**；name 必须是命名术语。指标类只抽"命名的指标"（如"系统响应时间"），绝不抽具体数值。`.en` 镜像同步。entity `type` 字段的 `指标(...)` 描述收紧为"命名的技术指标，不抽具体数值"。

### 改动 2 — 激活 typed 顶点 + 动词驱动 typed 边

**核心思路**：project_concept_graph 的 16 个 relation 动词是干净的域语义，**按动词路由**比按 NE 端点有效（现 route_relation 要 person/event 源，域类型永不匹配）。新域边标签设为 **entity→entity**，而 double-write（builder.py:465-493）保证每个实体都有一个 generic `entity` 顶点 → 域边端点用 generic entity id 恒可解析，不撞 typed 端点约束。

- **2a typed 顶点（NE 保守）** — 扩 `_ENTITY_TYPE_LABELS`：`主体→organization`、`角色→person`、`区域→location`（组织已有）。其余 17 个域类型保留 generic entity + 富 type 字段；concept 故意不映射（避免"418 孤立 concept 顶点"老问题）。
- **2b 新增 5 个域边标签（entity→entity）** — schema.py 加 `deployed_on/uses/processes/provides/requires`，属性同 part_of（relation_type, description）。
- **2c 动词路由表 + route_relation 通配** — route_relation 加 source 通配（`"*"`），DEFAULT_RELATION_ROUTES 末尾追加 5 条 verb 驱动域路由（source="*", target="*"），按动词分流：

  | 动词 | edge_label |
  |---|---|
  | 包含/contains, 属于/is_a, 依赖/depends_on, 集成/integrates | `part_of` |
  | 采用/uses, 训练/trained_on | `uses` |
  | 部署/deployed_on, 部署于/located_in | `deployed_on` |
  | 处理/processes | `processes` |
  | 提供/provides | `provides` |
  | 要求/requires | `requires` |
  | 承担/报价/交付于/达成/遵循 | `related_to`（兜底） |

  末尾追加 → NE 具体路由（person→org belongs_to 等）优先命中；`角色 -[belongs_to]-> 组织` 仍走 person→org。

### 改动 3 — 抽取模型升 qwen-plus（`deploy/docker-compose.prod_minimal.yml:283`）

`HE_EXTRACT_LLM__MODEL: qwen-turbo → qwen-plus`（qwen-plus 支持 json_schema 约束解码 ✓；QA 已用 qwen-plus@16384）。容器栈需 `--force-recreate api`；host E2E 重建 `export ARROW_LAKE__HUGEGRAPH__HE_EXTRACT_LLM__MODEL=qwen-plus`。

## 4. 验证（重建后）

清图重 build wuhu_report（`make kg-clear-graph DS=wuhu_report` → 同步 heredoc `execute_build` 避 fire-forget GC），抽取用 qwen-plus，重评：
- entity.name 抽样不再有裸数字（数字实体占比 ~47% → 个位数%）。
- typed 顶点 person/org/location > 0。
- typed 边 deployed_on/uses/processes/provides/requires/part_of 全 > 0，related_to 占比大降。
- definition 仍 100% 填充且不再编造。

## 5. 取舍

- 不重引入 concept 映射（避免孤立 concept 顶点老问题）。
- 不做后处理数字过滤脚本（治本优于外科手术）。
- 17 个非 NE 域类型不强行塞 typed 标签（保留 generic entity + 富 type，符合 project_concept_graph 设计哲学：域类型用 `type` 属性承载，比 5 个 NE 标签更丰富更正确）。

## 6. 教训

- **评估 KG 质量别只看 definition 填充率**——会骗人（裸数字也能 100% 编造 def）。要抽样看 entity.name 是否真命名实体。
- **定量工程文档是 KG 抽取的高危类**——满篇数字/规格/报价，必须配硬 prompt 约束 + 较强模型。
- **类型化结构靠动词路由，不靠端点 NE 标签**——域文档的关系动词是干净语义，按动词分流到 typed 边比强塞 NE 顶点标签更有效。
