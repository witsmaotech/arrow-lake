## 1. 背景与目标

### 1.1 问题:控制面没有关系型存储

经全仓 grep + 4 路并行 agent 调研确认,平台当前**没有任何关系型数据库承担系统结构化数据**。DuckDB 是嵌入式 OLAP 查询引擎(非持久元数据库);SQLAlchemy 仅用于"从外部 SQL 库读数据进来"(`ingest/connectors_sql.py:3-89`),平台自己不持有 RDBMS。

8 类"系统级结构化数据"当前落点与痛点:

| # | 数据类别 | 当前落点 | 致命痛点 |
|---|---|---|---|
| 1 | **RBAC ACL(行/列/schema)** | 进程内字典 `PermissionChecker`(`api/rbac.py:83-98`) | 重启即丢;多 worker/多副本不一致;无锁竞态。**源码注释自述"designed for trivial upgrade to database-backed store"**(`rbac.py:84-88`) |
| 2 | **用户/身份** | **不存在**(单一共享 API key env / 硬编码 `user_id="api-user"`,`routers/auth.py:92-119`) | 无用户表、无凭据、无多租户、审计到不了人;`admin.py:23 list_users` 直接返回"未实现" |
| 3 | **任务历史/态** | Redis hash(2h TTL)+ 内存 `TaskManager._tasks`(`api/tasks.py:121-123`) | 2h 后自动消失,无历史可查 |
| 4 | **Catalog 注册元数据** | `tempfile.mkdtemp` 临时 DuckDB 文件(`catalog/actor.py:65-90`) | **重启即焚**;且 prod_minimal 已砍 Ray,此路径基本不跑 |
| 5 | **死信队列(ingest)** | 本地 JSONL 文件 `data/ingest_dlq.jsonl`(`ingest/dead_letter.py:70`) | 单机、多 worker 不共享、无并发安全 |
| 6 | **血缘查询** | Lance `_lineage_events`(append-only)+ 内存 BFS + `LIKE '%\"name\"%'` 匹配(`catalog/lineage.py:482-484,508-623`) | 持久但非关系型;查询无索引;**自动埋点钩子 `lineage_hooks.py` 写了却全仓零调用** |
| 7 | **审计** | Lance `_audit_trail`(append-only 湖格式,`workflow/audit.py:88`) | 持久但不便做管理型关系查询 |
| 8 | **JWT 黑名单** | Redis + 内存 OrderedDict(`auth_service.py:52,109`) | TTL/LRU 可能淘汰 |

补扫又发现 6 类散落+易失的结构化数据:

| # | 数据类别 | 当前落点 | 痛点 |
|---|---|---|---|
| 9 | **RAG 会话/feedback** | `rag/session.py:21-35` 纯内存 list,`history_dataset` 参数名存实亡 | 重启即丢对话与评分 |
| 10 | **维护任务 run history** | `maintenance_scheduler.py:54,166` 内存 `_last_report` | 无可查历史 |
| 11 | **调度定义** | `schedule.py` 仅构建 Metaflow 装饰器,无持久存储 | 调度重启后丢失 |
| 12 | **schema 变更历史** | `schema.py:113,134` 只做 LIVE 校验,无落库 | 治理盲点 |
| 13 | **配置变更历史** | `cli/config_cmd.py` 仅 show/export,无 changelog | 无配置审计 |
| 14 | **个人 API token** | **不存在**(只有 1 个全局共享 `api_key`,`auth.py:30`) | 无法做"用户自管多 token + 撤销" |

### 1.2 目标

引入 **turso(libSQL / SQLite fork)** 作为**统一基础数据库**,只接管**控制面**的结构化数据(需要事务、需要关系查询、需要持久一致的部分),数据面(Lance/DuckDB/HugeGraph/MinIO)完全不动:

1. **P0 RBAC + 身份持久化**:把 `PermissionChecker` 的 4 个 dict + 硬编码 `api-user` 换成真实 `users/roles/role_permissions/dataset_acls/schema_acls/denies` 表 + `personal_tokens`。解决重启丢失、多副本不一致、审计到人。
2. **P1 收敛易失/单机文件凑合存储**:Catalog 注册表、任务历史(完成态)、ingest 死信、RAG 会话/feedback 统一进 turso,获得持久化 + 可查询 + 事务。
3. **P2 治理面**:血缘可查询索引(事件仍存 Lance)、schema 变更历史、维护/调度 history、配置 changelog;启用血缘自动埋点钩子。
4. **P3 用户态补齐**:saved_query / dashboard / favorite / preference / notification 建表即用,顺带补齐 `list_users` 用户管理。

### 1.3 非目标(明确边界)

- **不替换 Gravitino**:Gravitino 仍是独立部署的元数据 federation 服务(`deploy/docker-compose.prod_minimal.yml:589-740`,自带 `gravitino-data` 卷),平台继续当 client。turso 只建本地镜像对账表(留作未来工作,见 §10),不接管 Gravitino 角色。
- **不接管数据面**:Lance(数据 + `_audit_trail` + `_lineage_events` 事件流)、DuckDB(OLAP)、HugeGraph(KG)存储模型不变。血缘/审计**事件流仍在 Lance**,turso 只建查询索引。
- **不删 Redis**:任务实时态、JWT 黑名单、限流计数、DuckDB 信号量仍留 Redis。turso 只接管"历史/持久/关系"部分。
- **不接管可观测栈**:Prometheus 指标(`core/metrics.py`)、OTLP 追踪(`api/telemetry.py`)、stdout 结构化日志(`core/logging.py:58`)高频时序/流,归 Prometheus/Jaeger/Loki,不进 turso。
- **不做 SSO/OAuth**(P3 范围外):personal_token 是本地签发的 bearer token,不接外部 IdP。
- **run_tracker 不动**:它只读 Metaflow Client(`workflow/run_tracker.py`),无自有数据。

## 2. 选型:为什么是 turso(libSQL)

### 2.1 候选对比

| 维度 | PostgreSQL | SQLite(裸) | **turso(libSQL)** ✓ |
|---|---|---|---|
| 部署形态 | 独立 server 容器(重) | 嵌入式文件(无 server) | **嵌入式 + 自托管 sqld server 二选一** |
| 与现有架构契合 | 多一个重容器,偏离"嵌入式"风格 | 与 DuckDB 同嵌入式模式 | **与 DuckDB 嵌入式模式一致**,可文件可 server |
| 多 worker 一致性 | 原生 C/S,天然共享 | 多进程写不安全(WAL 有限) | **sqld server 模式原生共享**;MVCC 并发写 |
| 运维成本 | 高(vacuum/连接池/调优) | 低 | **低**(SQLite 生态,零 vacuum) |
| 副本/分支/PITR | 需另搭(流复制) | 无 | **libSQL 原生副本 + 分支 + PITR + BYOK** |
| 向量/FTS | pgvector(扩展) | FTS5 | **原生 `vector32` + `vector_distance_cos` + FTS5** |
| 事务/关系查询 | 完整 SQL | 完整 SQL | **完整 SQL(SQLite 兼容)** |

### 2.2 turso 契合点

1. **嵌入式血统**:平台已有 DuckDB(嵌入式 OLAP)、Lance(嵌入式列式),turso(libSQL)同属嵌入式家族,**部署心智一致**,不必引入"重数据库"运维负担。
2. **server 模式解决多 worker**:prod_minimal 跑 4 个 uvicorn worker——自托管 sqld 让 4 worker 共享一个库,强一致。
3. **未来多副本零阻力**:libSQL 原生副本(主从),未来平台扩多节点时 RBAC/元数据天然复制。
4. **SQLite 兼容**:生态成熟,Python `libsql` 包是 sqlite3 DB-API 风格,学习成本为零。
5. **原生向量/FTS**:P3 用户态(saved_query 全文搜)或未来轻量向量场景可直接用,不必再加依赖。

### 2.3 边界:什么不进 turso(回答"埋点/日志要不要加")

| 类别 | 归属 | 理由 |
|---|---|---|
| Prometheus 指标 | Prometheus/Grafana | 高频时序计数器/直方图,进程内 registry+/metrics 拉取 |
| OTLP 分布式追踪 | Jaeger/Tempo | 流式 span export |
| stdout 结构化日志 | Loki/ELK | 高频日志流,`core/logging.py:58` 仅 StreamHandler |
| JWT 黑名单 / 限流计数 | Redis | 高频读写 + 短 TTL |
| run_tracker | Metaflow | 只读 Metaflow Client |
| 数据快照 backup | 对象存储 | 大体积 Lance data + manifest |

**结论:埋点(指标/追踪)和日志不进 turso**——它们是高频时序/流,归可观测栈。turso 只承接"需要事务、需要关系查询、需要持久一致"的系统控制面数据。

## 4. 数据模型(按批次)

### 4.1 P0 — RBAC + 身份 + personal_token(详细)

替换 `rbac.py` 的 4 个 dict + 硬编码 `api-user`。

```sql
-- V001__init_rbac.sql
-- 身份
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT UNIQUE NOT NULL,
  email TEXT UNIQUE,
  password_hash TEXT,              -- argon2 哈希;bootstrap/token-only 用户可空(本方案不做 SSO,见 §1.3)
  role TEXT NOT NULL DEFAULT 'viewer',  -- admin/editor/viewer
  is_active INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,        -- ISO8601
  updated_at TEXT NOT NULL
);

-- 个人 API token(用户自管多 token,替换全局共享 api_key)
CREATE TABLE personal_tokens (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,              -- 用户给的标签("ci-pipeline")
  token_hash TEXT UNIQUE NOT NULL, -- 存 sha256(token),不存明文
  token_prefix TEXT NOT NULL,      -- 前 8 位,展示识别("al_xxxxxx…")
  scopes TEXT,                     -- JSON:权限范围
  expires_at TEXT,
  last_used_at TEXT,
  created_at TEXT NOT NULL,
  revoked_at TEXT
);
CREATE INDEX idx_personal_tokens_user ON personal_tokens(user_id);
CREATE INDEX idx_personal_tokens_hash ON personal_tokens(token_hash);

-- 角色→权限(表化,启动时从 _ROLE_PERMISSIONS 常量 seed 默认值)
CREATE TABLE role_permissions (
  role TEXT NOT NULL,
  permission TEXT NOT NULL,
  PRIMARY KEY (role, permission)
);

-- 数据集级 ACL(替换 PermissionChecker._dataset_acls dict)
CREATE TABLE dataset_acls (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  dataset_name TEXT NOT NULL,
  principal TEXT NOT NULL,         -- user_id 或 role 或 '*'
  principal_type TEXT NOT NULL,    -- 'user' | 'role'
  access TEXT NOT NULL,            -- 'allow' | 'deny'
  conditions TEXT,                 -- JSON:行/列过滤条件
  created_at TEXT NOT NULL,
  UNIQUE (dataset_name, principal, principal_type)
);
CREATE INDEX idx_dataset_acls_ds ON dataset_acls(dataset_name);

-- schema/列级 ACL(替换 _schema_acls dict)
CREATE TABLE schema_acls (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  dataset_name TEXT NOT NULL,
  column_name TEXT NOT NULL,
  principal TEXT NOT NULL,
  principal_type TEXT NOT NULL,
  mask_type TEXT,                  -- 'hash' | 'redact' | 'partial' | NULL
  access TEXT NOT NULL,
  created_at TEXT NOT NULL
);

-- deny-list(替换 _denied dict)
CREATE TABLE acl_denies (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  dataset_name TEXT NOT NULL,
  principal TEXT NOT NULL,
  reason TEXT,
  created_at TEXT NOT NULL
);
```

## 5. 关键设计决策

### 5.1 schema 治理:轻量 SQL runner(已定)

- 项目当前无 alembic、无任何 migration 框架。**不引入 alembic**(加 ORM/SQLAlchemy 上下文,与项目无 ORM 现状冲突)。
- 自建轻量 runner:`migrations/V001__init_rbac.sql` 顺序文件 + `schema_version` 表记录已应用版本,`SystemDB` 启动时自动跑未应用迁移。
- 文件命名:`V<NNN>__<batch>_<desc>.sql`,按编号顺序应用;每文件幂等(可重复跑不报错)。

### 5.2 角色权限:表化 + 默认 seed(已定)

- 建 `role_permissions` 表,启动时从现有硬编码 `_ROLE_PERMISSIONS`(`rbac.py:32`)常量 `INSERT OR IGNORE` seed 默认值。
- 保留现有行为(admin/editor/viewer 三档),同时支持运行时自定义角色/权限调整(无需改代码重发)。

### 5.3 数据流与缓存

**数据流(以 RBAC 细粒度请求为例)**:
1. 请求 → `api_key_middleware`/`jwt_auth_middleware` 解析凭证 → `get_current_user` 查 `personal_tokens`(join `users`)→ 构造 `User`
2. `require_role(Role.X)` 角色门槛(不变)
3. `PermissionChecker.apply_table_filter` 细粒度 ACL:内存 dict → `rbac_store.get_dataset_acls(dataset, role)`
4. ACL 变更(`/admin/acl/*`):`checker.set_acl()` → `rbac_store.upsert_acl()`

**缓存(避免每请求打库)**:
- store 内置短 TTL 内存缓存(ACL ~5s),热路径不每请求查 sqld。
- ACL 变更时主动失效本 worker 缓存。
- 多 worker 各持缓存 + 短 TTL(最终一致,5s 可接受);未来可用 libSQL CDC(`PRAGMA capture_data_changes_conn=1`)+ Redis pub/sub 做主动失效。

### 5.4 降级策略(安全语义)

| 领域 | sqld 不可用时 | 理由 |
|---|---|---|
| **RBAC/身份** | **fail-close**(拒绝所有非公开请求) | 安全优先,宁可拒绝不可放行;`/health`/`/metrics`/docs 公开路径仍放行 |
| 任务历史/Catalog/DLQ/RAG | **fail-soft**(记日志、返回错误或回退旧路径) | 非安全关键,不影响数据面 |
| 血缘索引 | **fail-backfill**(查询降级回 LIKE+BFS,新事件不索引,恢复后从 Lance 补) | 索引可从 Lance 重建 |

**健康门**:api 容器 `depends_on: system-db: condition: service_healthy`;lifespan 启动探活,连不上则 **fail-fast**(lifespan 启动失败,不静默跑)。

> ⚠️ **fail-close 的运维含义**:P0 上线后 RBAC 完全依赖 sqld,sqld 长时间宕机 = 平台不可用。对策:sqld 健康检查 + restart:unless-stopped + 数据卷持久 + 可选只读副本;启动期保留"全局 api_key bootstrap"作逃生通道(见 §5.6)。

### 5.5 并发写(review 修正)

- libSQL 默认**单写连接**;sqld 作为 server 会串行化多客户端写请求。
- 控制面写(RBAC/元数据)低频,默认单写够用。
- 高频写(`task_history`/`lineage_edges`)若成瓶颈:开 `PRAGMA journal_mode='mvcc'` + `BEGIN CONCURRENT`,同行冲突按消息含 `"conflict"`/`"busy"` 应用层重试。

### 5.6 personal_token 安全

- **生成**:`secrets.token_urlsafe(32)`,前缀 `al_`(arrow-lake),明文只在创建时返回一次。
- **存储**:存 `sha256(token)` 的 `token_hash`,不存明文;`token_prefix`(前 8 位)用于 UI 展示识别。
- **校验**:`hmac.compare_digest` 防时序攻击;查 `personal_tokens` join `users`,命中且未过期/未撤销 → 构造 `User`。
- **与现有认证共存**:`auth_mode` 扩展为 `api_key | jwt | token | both | all`;`X-API-Key` header 复用(优先查 personal_tokens,miss 再回落全局 api_key)。全局 `api_key` 保留作 bootstrap/admin 逃生通道。

## 8. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| sqld 宕机 → RBAC fail-close → 平台不可用 | **高** | 健康检查 + restart + 数据卷持久 + bootstrap api_key 逃生通道;未来加只读副本 |
| 个人 token 泄露 | 中 | 存 hash 不存明文;支持 revoke;过期时间;UI 展示 prefix 不展示全量 |
| 多 worker 缓存不一致(ACL 变更延迟) | 中 | 短 TTL(5s)可接受;未来 CDC+pub/sub 主动失效 |
| 现有 RBAC 单测改造回归 | 中 | store Protocol 先行,行为不变;回归测试逐改造 |
| libsql Python SDK 稳定性 | 低 | `libsql` 是生产就绪包(libSQL fork,经受过考验);非 beta 新引擎 |
| 血缘索引与 Lance 事件漂移 | 低 | `lineage_edges` 可从 Lance `_lineage_events` 重建;fail-backfill 补偿 |
