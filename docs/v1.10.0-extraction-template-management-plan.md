## 0. TL;DR

「知识抽取模板」(下文统称**模板**)是 hyper-extract 的 YAML 预设,定义「从文档 chunk 抽取哪些实体/关系、用什么 guideline prompt、输出什么强类型结构」。当前平台把 7 个领域模板**打包在镜像里**(`arrow_lake/knowledge_graph/templates/*.yaml`),要新增/修改必须改代码 + rebuild。

v1.10.0 的核心价值:**不 rebuild、不重启,在前端 CRUD 一个新模板,后端 KA/KG 立即能按它抽取建图**。可行性已由代码核实(见 §2):`Template.create()` 本就支持**绝对 YAML 文件路径**加载,项目模板就是这么进的 gallery —— 我们只需把扫描目录从「包内」扩到「可写卷上」,再补 CRUD API、UI、缓存失效与 per-dataset 绑定。

三句话设计:
1. 用户模板 YAML 落在可写卷 `/data/lake/templates/`(`lake-data` 卷,与 KA dump 同卷)。
2. CRUD 把 YAML 写盘后调用 `reset_gallery_cache()`(`doc_type_router.py`)刷新内存 gallery —— 下一次 `/kg/build` 即按新模板抽取。
3. 数据集可显式**绑定模板**(per-dataset override),优先级高于 doc_type 路由。
4. **build 时把所用 YAML 快照进 KA dump** —— dump 自包含,查询侧(`load_ka_for_query`)读快照不依赖 gallery;根治「模板删/改后旧图查询失败」与查询路径解析(见 §4.7,review C1/H2)。

## 1. 背景与目标

### 1.1 用户诉求(原话)

> 「数据集 chunk 后通过 hyper-extract 模板在前端应该有个配置管理界面,能够动态添加编辑等,这样平台的扩展性才会更强大」
> 「不仅仅是界面管理,打通后端的 ka kg 能够根据新模板进行抽取建立图谱能力」

即:**前端 CRUD + 后端动态抽取建图,二者缺一不可**。纯界面不算交付;纯后端不可用也不算。

### 1.2 为什么要做(价值)

- **质量瓶颈在模板不在模型**(见 CLAUDE.md「KG / hyper-extract」:`concept_graph` 自由类型 + optional description → 即使 qwen-turbo 也 0% 描述)。要让平台对不同领域(金融/法律/医疗/工业/项目…)都能产出高质量 KG,**必须能快速迭代模板并按数据集套用**。打包进镜像的迭代成本(改代码→rebuild 3-5min→recreate)扼杀了这种迭代。
- **平台扩展性**:平台定位是基础设施,新行业接入不应排期进发版。模板是「接入新行业知识结构」的主要扩展点,理应运行时可管理。

### 1.3 目标(可验证)

| # | 目标 | 验证方式 |
|---|------|---------|
| G1 | 前端能 CRUD 模板(列表/新建/编辑/预览/试跑/删除/设默认) | `console/extraction-templates.html` 跑通,无 rebuild |
| G2 | 新建模板后**不 rebuild/不 restart**,下一次 KG build 即生效 | 建 `foo` 模板 → `/kg/build` 用 `foo` → 抽出实体 |
| G3 | 数据集可显式绑定模板,优先级高于 doc_type 路由 | 数据集 A 绑 `foo`,doc_type=report → 用 `foo` |
| G4 | 模板 YAML 严格校验,试跑有沙箱(限行数/限 LLM 调用) | 坏 YAML → 422 带定位;试跑返回实体样本 |
| G5 | 现有打包模板登记为**系统模板只读**,向后兼容 | 列表区分 system/project/user,系统模板不可删/改 |

### 1.4 非目标(YAGNI,显式砍掉)

- ❌ 模板版本树 / 多版本并存(已有 KA dump 版本管理 `ka_versioning`,模板侧不重复造)
- ❌ AB 测试 / 在线市场 / 多人协作编辑 / 可视化 schema 拖拽编辑器(先 YAML 文本编辑,见 §10 路线图 M4 可回炉)
- ❌ 运行时修改 hyper-extract 预设库(`site-packages/hyperextract/templates/presets/`)—— 那是依赖,只读

### 1.5 术语

- **知识抽取模板 (extraction template)**:一份 hyper-extract YAML,含 `output.entities/relations.fields` + `guideline`。本设计贯穿使用此术语以区别其他「模板」(SQL 模板/邮件模板等)。
- **系统模板 (system)**:随镜像打包的领域模板(`arrow_lake/knowledge_graph/templates/*.yaml` + hyper-extract presets),只读。
- **用户模板 (user)**:经前端创建、落 `/data/lake/templates/` 的模板,可改可删。

## 2. 现状分析(代码核实)

> 本节每条结论都有代码引用,非凭记忆。

### 2.1 模板怎么加载 —— **核心发现:`Template.create()` 已支持绝对路径**

`doc_type_router.py` 的 `_merge_project_templates()`(L358-400)把项目模板注册进 gallery,关键一句(L387):

```python
gallery.templates.append(TemplateInfo(
    path=str(yml.resolve()),   # ← 绝对文件路径作 path
    category="project",
    ...
))
```

其 docstring 明确写道(L362-363):

> *Project templates use their ABSOLUTE FILE PATH as TemplateInfo.path so **Template.create() loads them directly** (vs preset 'category/name' paths).*

而 `he_extractor.py:310` 实际加载:

```python
return Template.create(
    template_path,              # ← 既可是 "general/concept_graph",也可是 "/.../foo.yaml"
    self._language,
    llm_client=...,
    embedder=self._embedder,
    chunk_size=cfg.he_chunk_size,
    ...
    node_strategy_or_merger=MergeStrategy.MERGE_FIELD,
    edge_strategy_or_merger=MergeStrategy.MERGE_FIELD,
)
```

**结论:把一个新 YAML 放进扫描目录、让它进 gallery,`Template.create()` 就能加载它 —— 这条链路现在就能跑,无需改造 hyper-extract。** 这是 v1.10.0 可行性的基石。

### 2.2 模板的两个来源

gallery 由 `_shared_gallery()`(`doc_type_router.py:403`,`@lru_cache(maxsize=1)`)构建:

1. **hyper-extract presets**:`TemplateGallery.build()`(L180-255)扫 `site-packages/hyperextract/templates/presets/{category}/{name}.yaml`,path = `category/name`。跳过 `base_*`(AutoType 基类,不可直接抽取)。
2. **项目模板**:`_merge_project_templates()` 扫 `arrow_lake/knowledge_graph/templates/*.yaml`,path = **绝对路径**,category = `project`。当前 7 个:`concept_graph / project_concept_graph / legal/finance/medical/ddd_concept_graph / entity_graph`。

`reset_gallery_cache()`(L412)清 lru_cache —— **这是热重载的现成钩子**(注释明言 "dev/test helper for preset hot-reload")。

### 2.3 doc_type → 模板的三层路由(`DocTypeRouter.resolve_with_source`,L486)

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | `override` | 配置 `he_doc_type_templates` 显式映射,最高优先;项目模板可用裸名引用(`_project_name_to_path`,L456) |
| 2 | `gallery` | 模板元数据匹配(tags→category→name token→description),**新模板自动被匹配** |
| 3 | `default` | 兜底 `he_default_template` |

另有 `degraded`:gallery 命中高风险(hypergraph)模板时自动降级到 default(避免已知 IndexError 崩溃,L505-517)。

### 2.4 build 一刻如何选模板 —— **发现 gap:无 per-dataset 显式绑定**

`builder.py:370` 的模板选择点:

```python
template_path = self._extractor._resolve_template(
    dataset_doc_type, _sample, None,    # ← 只靠 doc_type + 内容启发式
)
```

`_resolve_template`(`he_extractor.py:268`)优先级:`template_type` 参数 > config 默认 `template_type` > `TemplateTypeSelector` 时序启发式 > `DocTypeRouter.resolve(doc_type)`。**全程没有「这个数据集就该用模板 X」的显式入口** —— 只能靠 doc_type 间接路由。

`build()` 签名(`builder.py:149`)也无模板参数:

```python
async def build(self, dataset_name, chunks_table, *, incremental=False) -> str:
```

**这正是 v1.10.0 要补的 per-dataset 绑定**(见 §4.4):给 `build` 加 `template_override`,优先级压过 doc_type 路由。

### 2.5 抽取/合并/落盘链(已就绪,不动)

- 粒度:`he_kg_granularity`(v1.9.12 起默认 `map_reduce`),`builder.py:352-358` 决定 dataset/map_reduce/chunk。
- 合并:`MERGE_FIELD`(非 LLM 字段级合并),`he_extractor.py:318`。
- KA dump:`/data/lake/ka/{artifact_key}/ka/{data.json, metadata.json, index/}`,`metadata.json` 记录所用模板(可查 `builder.py:534` `d.get("template") == Path(template_path).stem`)。
- 实体消歧:`entity_resolver.py`(opt-in,默认 off),与本设计正交。

### 2.6 部署约束(已核实)

- api 容器 `read_only: true`(`docker-compose.prod_minimal.yml:73`)。
- 可写卷:`/data/lake`(lake-data,compose:361)、`/data/metaflow`、`/app/.duckdb`、`/app/.docling-cache`。
- KA dump 已在 `/data/lake/ka`(compose:241,注释明言「read_only 容器只能写挂载卷」)。
- **→ 用户模板 YAML 必须落 `/data/lake/templates/`(同一 lake-data 卷),绝不能落 `/app/`(只读)。**

### 2.7 前端现状(已核实)

- console 原生 JS + ES module。共享:`src/api.js`(`request(method, path, {body, headers, signal})`)、`src/auth.js`(`getAccessToken/getApiKey/API_BASE`)、`src/ui/{toast,modal,table}.js`。
- `console/ingest.html:172-183` 的 doc_type 下拉**硬编码 9 项**,且值(`research_paper`/`legal_contract`/`financial_report`)与 `DOC_TYPE_ALIASES` 规范键(`paper`/`legal`/`finance`)不一致,也无 `project` —— **这正是要被动态模板列表替换的死代码**。
- `console/admin.html` 是 CRUD 参考实现(用户管理),复用其布局 `assets/console-layout.js`。
- 鉴权:双层(Bearer JWT + `X-API-Key`),`request()` 内 401 auto-refresh。

## 3. 架构设计

### 3.1 总览

```

┌────────▼─────────────────────────────────────────────────────────────┐

│   _resolve_template(): override > selector > doc_type router          │
│   → he_extractor._create_ka(path) → Template.create(YAML 绝对路径)    │
│   → feed_text 全部 chunk → MERGE_FIELD 合并 → 落 /data/lake/ka         │
│   → _insert_kg 写 HugeGraph (kg_{artifact_key})                       │
└───────────────────────────────────────────────────────────────────────┘
```

### 3.2 三条核心数据流

1. **CRUD 写模板**:UI → API → `template_registry.save()`(YAML schema 校验 → 写 `/data/lake/templates/{name}.yaml` → 写 system_db 元数据 → `reset_gallery_cache()`)。下一次 gallery 重建即含新模板。
2. **build 用模板**:`/kg/build` 带 `template_override=<name|path>` → `builder.build(..., template_override=)` → `_resolve_template` override 优先 → `Template.create(abs_path)`。
3. **试跑(dry-run)**:`POST .../dry-run` 带 `{template_yaml, sample_text, max_lines}` → 临时写 `/data/lake/templates/.dryrun/{token}.yaml` → 喂前 N 行 → 返回抽取的实体/关系样本 → 删临时文件。不写 gallery、不建图。

### 3.3 设计原则

- **复用而非重造**:`_merge_project_templates` 的机制(扫目录→绝对 path 入 gallery)直接复制成 `_merge_user_templates`,扫 `/data/lake/templates/`。不碰 hyper-extract。
- **系统模板只读,用户模板可写**:两类物理分离(包内 vs 卷上),权限自然分流。
- **YAML 是单一事实源**:system_db 元数据是 YAML 的索引/缓存(便于列表/搜索/绑定),YAML 本身才是抽取时真正读取的。元数据可从 YAML 重建(自愈)。
- **缓存失效最小化**:仅 CRUD 时 `reset_gallery_cache()`;不做定时轮询、不做 per-template 细粒度失效(过早优化)。

## 4. 后端动态抽取(✨ 核心)

> 本章回答:「为什么不 rebuild / 不 restart 就能加载新模板」。

### 4.1 用户模板目录与扫描

新增 `arrow_lake/knowledge_graph/doc_type_router.py::_merge_user_templates(gallery)`,镜像 `_merge_project_templates` 的实现,差异:

| 维度 | 项目模板(`_merge_project_templates`) | 用户模板(`_merge_user_templates`,新) |
|------|---------------------------------------|----------------------------------------|
| 目录 | `Path(__file__).parent/"templates"`(包内,git 跟踪,只读) | `HugeGraphConfig.he_user_templates_dir`(默认 `/data/lake/templates`,卷上,可写) |
| category | 现状 project 模板统一标 `project`、靠 tags 路由 | **保持领域语义或靠 tags**(见表下纠偏)—— 勿塞来源 |
| source(新派生字段) | `system`(presets + project) | `user`(从加载位置派生;UI 来源 chip 用它) |
| 可变性 | 只读(系统模板) | 可改可删 |
| path | 绝对路径 | 绝对路径 |

> **⚠️ category vs source(设计纠偏 / review H1)**:`gallery.match()`(doc_type_router.py:275)layer-2 用 `t.category == doc_type` 路由,`validate_taxonomy()`(L565)对未知 category 报 drift warning(仅豁免 `project`,L569)。**切勿把「来源」塞进 category** —— 早期稿曾写 `category="user"`,那样 user 模板会失去 doc_type 自动路由能力并触发 taxonomy warning。正确做法:`category` 保持领域语义(finance/legal…,与 `DOC_TYPE_ALIASES` 规范键对齐;无明确领域时复用现状「靠 tags 路由」);`source` 由加载位置派生(preset/project→`system`,user_dir→`user`),仅供 UI 来源 chip。user 模板须填正确 `tags` 才能被 doc_type 自动路由,否则只能靠显式绑定(§4.4)。

`_shared_gallery()` 末尾追加一行调用:

```python
@lru_cache(maxsize=1)
def _shared_gallery() -> TemplateGallery:
    gallery = TemplateGallery.build()
    _merge_project_templates(gallery)
    _merge_user_templates(gallery)          # ← 新增
    return gallery
```

目录通过 config 注入(便于测试与多环境),config 加字段:

```python
# arrow_lake/config/...  HugeGraphConfig
he_user_templates_dir: str = "/data/lake/templates"
```

compose `api` 服务 `environment:` 增(与 `HE_KA_BASE_DIR` 同位置):

```yaml
ARROW_LAKE__HUGEGRAPH__HE_USER_TEMPLATES_DIR: "/data/lake/templates"
```

(`/data/lake` 已是可写卷,**无需新增卷挂载**。)

### 4.2 缓存失效(热重载)

gallery 是 `lru_cache(maxsize=1)`,新建/修改/删除模板后调 `reset_gallery_cache()` 即让下一次访问重建。**无需 restart、无需 rebuild**:

- API 的 POST/PUT/DELETE 成功落盘后立即 `reset_gallery_cache()`。
- **进程内缓存**:注意 lru_cache 是进程级的。多 worker(uvicorn `--workers N`)部署时,一个 worker 刷了自己的 cache,其他 worker 仍持旧 gallery。**对策**:默认 `--workers 1`(prod_minimal 现状);若未来多 worker,CRUD 后给所有 worker 发 invalidate(经 Redis pub/sub 或简单设 TTL 短 lru)。**M1 范围内 prod_minimal 单 worker,不引入复杂度**(YAGNI)。

### 4.3 YAML schema 校验(写盘前)

新增 `arrow_lake/knowledge_graph/template_registry.py`,核心 `validate_template_yaml(raw: str) -> TemplateDef`。校验规则(与 `project_concept_graph.yaml` 结构对齐):

**必需顶层字段**:`language`(非空 list)、`name`(合法标识符 `^[a-z][a-z0-9_]*$`,与文件名一致)、`type`(`graph`|`model`|`hypergraph`,默认 `graph`)、`output`、`guideline`。

**output.entities.fields / output.relations.fields**(二者至少一个):
- 每个字段:`name`(必)、`type`(`str`/`int`/`float`/`bool`,必)、`description`(`{zh,en}` 或 str,必)、`required`(bool,默认 false)。
- entities **必须有 `name` 字段**(抽取锚点);relations **必须有 `source`/`target`/`type` 字段**。
- **denylist**:字段名禁止 `__`、禁止 Python 保留字;`name` 禁止与系统模板重名(防 shadow)。

**guideline**:`target.{zh,en}`(必,角色描述)、`rules_for_entities.{zh,en}`(list,可为空)。**prompt 注入面 → 见 §9**。

**大小上限**:YAML ≤ 64 KiB(guideline 通常 < 10 KiB;防 DoS)。**另加结构上限**(review 安全):嵌套深度 ≤ 6、拒绝 YAML `<<` merge key 与 alias 放大、字段总数 ≤ 50、guideline 每侧 ≤ 8 KiB(防 PyYAML alias 放大 + 超长 prompt 注入面)。

校验失败 → `TemplateValidationError`(带字段路径),API 转 422 + 定位信息(如 `output.entities.fields[2].type: required`)。

> 校验只做**结构/schema**合规,不评判抽取质量(质量靠试跑,§4.5)。

### 4.4 per-dataset 模板绑定(补 §2.4 的 gap)

#### 4.4.1 build 签名扩展

`builder.py:build` 增可选参数:

```python
async def build(self, dataset_name, chunks_table, *,
                incremental=False, template_override: str | None = None) -> str:
```

`template_override` 透传到 `execute_build` → `_execute_build`,在 §2.4 的选择点短路:

```python
# builder.py 内 _execute_build,模板选择点(原 L370 附近)
if template_override:
    template_path = self._extractor._resolve_template_path(template_override)
else:
    template_path = self._extractor._resolve_template(dataset_doc_type, _sample, None)
```

`he_extractor` 增 `_resolve_template_path(ref)`:接受裸名(`foo`)或绝对路径;裸名先查 user/project 模板,再查 preset;解析不到 → `TemplateNotFound`(转 404/422)。

#### 4.4.2 优先级(从高到低)

1. **per-dataset 显式绑定**(本设计新增,`template_override`)
2. `template_type` 显式参数 / config
3. `TemplateTypeSelector` 时序启发式
4. `DocTypeRouter` doc_type 路由
5. `he_default_template` 兜底

#### 4.4.3 绑定存哪

per-dataset 绑定存 **libSQL system_db**(见 §7),key = dataset_name。`/kg/build` 请求体支持 `{template: "foo"}`,后端先查绑定再回退。Console 在数据集详情/ingest 页提供「抽取模板」选择器(动态拉 `/extraction-templates` 列表)。

> 绑定存在 system_db 而非数据集 metadata:数据集 metadata(lance schema)是数据面,模板是治理面,分层清晰;且 system_db 已管 RBAC/任务历史/血缘,天然是治理元数据归宿(v1.9.0 libSQL 接管)。

### 4.5 试跑(dry-run)沙箱

`POST /api/v1/admin/extraction-templates/dry-run`,body `{template_yaml, sample_text, max_lines=200}`:

1. `validate_template_yaml` 校验(失败即返 422,不消耗 LLM)。
2. 临时落盘 `/data/lake/templates/.dryrun/{token}.yaml`(token 不可猜;目录前缀 `.` 被 `_merge_user_templates` 跳过,不进 gallery)。
3. 截取 `sample_text` 前 `max_lines` 行(默认 200,上限 500)。
4. `_create_ka(temp_path)` + 单 chunk `feed_text` → 返 `{entities: [...], relations: [...], entity_count, relation_count, elapsed_ms}`(只取前 30 条预览)。
5. **finally 删临时文件**(无论成败)。
6. LLM 调用复用 extract client(百炼 qwen-turbo),单次调用,无并发,不计入 KG build 统计。

**安全**:试跑用 ADMIN 权限;`sample_text` ≤ 64 KiB;并发试跑 ≤ 3(信号量);超时 60s。

### 4.6 不需要 rebuild 的证明(对照表)

| 改动 | 旧方式 | v1.10.0 |
|------|--------|---------|
| 加模板 | 改 `arrow_lake/.../templates/*.yaml` → rebuild 镜像 3-5min → recreate | UI 新建 → 写 `/data/lake/templates/` → 刷 cache → **0 rebuild,0 restart** |
| 改 guideline | 改 YAML → rebuild | UI 编辑 → 落盘 → 刷 cache → 下次 build 生效 |
| 删模板 | 改代码 → rebuild | UI 删 → 删文件 + 元数据 → 刷 cache |
| 数据集换模板 | 改 doc_type 或 `he_doc_type_templates` → recreate api | 数据集详情换绑定 → 下次 build 生效 |

**唯一仍需 recreate 的场景**:改 `_merge_user_templates` / 校验逻辑 / API 代码本身(即 v1.10.0 的实现代码)。dev override(`-f dev.override.yml up -d --force-recreate api`)秒级热重载,无需 rebuild(见 CLAUDE.md「容器构建」)。

### 4.7 查询路径模板解析 + dump 快照(✅ review C1/H2 修复)

> **这是 review 发现的 CRITICAL 修复**:build 路径之外,**查询路径有独立的模板解析**,原稿漏覆盖 —— 不补这节,user 模板建的图「build 成功、查询全挂」。

**问题**:`he_extractor._build_ka_for_query`(L362-386)在 GraphRAG / `/kg/graph` / `kg.html` 问答时,从 `metadata.json` 读模板 **stem**,再解析回路径:

```python
if template and "/" not in template and not template.endswith(".yaml"):
    candidate = _PROJECT_TEMPLATES_DIR / f"{template}.yaml"   # ← 只查项目模板目录!
    if candidate.is_file():
        template = str(candidate)
ka = self._create_ka(template, ...)   # user 模板 stem 在此解析不到 → TemplateNotFound
```

user 模板 stem 不在 `_PROJECT_TEMPLATES_DIR` → `Template.create` 抛 "Template not found" → 用 user 模板建的 KG,`/kg/graph`、`/rag/query?use_kg=true`、`kg.html` 问答**全部失败**。

**根治:build 时快照 YAML 进 dump + metadata 存可加载路径**(一并治 H2 编辑破坏旧 dump):

1. **build 落盘时**(`builder.py` 写 KA dump 处)把所用模板 YAML 复制成 `ka_dir/template.yaml`(自包含快照),并在 `metadata.json` 写 `template` = **该快照绝对路径**(含 `/` 或 `.yaml`,触发 L379 guard 透传,绕过 `_PROJECT_TEMPLATES_DIR` 解析)。
2. **查询时** `_build_ka_for_query` 拿到路径直接 `Template.create(path)` —— 读快照,**与 gallery / 原模板文件的后续删改彻底解耦**。
3. **副作用收益**:① user 模板被删/改后旧图查询不受影响(治 H2);② DELETE 的 `TEMPLATE_IN_USE` 校验仍是好习惯但不再致命(C1)。

**边界**:preset 模板(`general/concept_graph` 等包内标识)不快照(包内稳定),metadata 仍存 stem 走原解析,完全兼容;仅 user/project **文件路径型**模板快照。

**回归验收**(进 §10 M1):用 user 模板 build 后,`/kg/graph` + `/rag/query?use_kg=true` + `kg.html` 问答必须成功加载。

## 7. 数据模型

### 7.1 YAML 文件(单一事实源)

`/data/lake/templates/{name}.yaml`,schema = §4.3 + `project_concept_graph.yaml` 结构。这是抽取时 `Template.create()` 真正读的文件。

### 7.2 libSQL system_db 元数据表(索引/缓存)

```sql
CREATE TABLE IF NOT EXISTS extraction_templates (
    name          TEXT PRIMARY KEY,           -- 与 YAML name 一致
    source        TEXT NOT NULL,              -- 'user'(本表只存 user;system/project 不入表,运行时扫描)
    doc_type      TEXT,                       -- 适配的 doc_type(可空=通用)
    file_path     TEXT NOT NULL,              -- /data/lake/templates/{name}.yaml
    description   TEXT,
    owner         TEXT,                       -- 创建者 username
    is_default_for TEXT,                      -- 是否为某 doc_type 默认(可空)
    content_hash  TEXT NOT NULL,              -- YAML sha256,自愈校验
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS dataset_template_bindings (
    dataset_name  TEXT PRIMARY KEY,
    template_name TEXT NOT NULL REFERENCES extraction_templates(name),
    bound_by      TEXT,
    bound_at      TEXT NOT NULL
);
```

**自愈(降级,review M1)**:**不在每次 list 热路径扫盘**(模板多会拖慢列表)。list 只读 system_db(快);自愈降级为 ① 进程启动时全量对账一次 + ② 按需 `GET .../?reconcile=true`(ADMIN 触发)+ ③ CRUD 写盘时同步表。表/YAML 最终一致,不阻塞读。

### 7.3 内存:gallery(`TemplateInfo` 复用)

`doc_type_router.TemplateInfo` 已有 `path/category/name/type/tags/description/entity_fields/...`。user 模板复用同结构,`category="user"`,加一个 `source` 概念用于 UI 区分(可由 category 推导:project→system, user→user, preset→system)。

## 9. 安全与校验

> 模板含 `guideline`(prompt),是**用户可控的 LLM 输入** → prompt injection 面。这是本设计最大的安全考量。

### 9.1 威胁与对策

| 威胁 | 对策 |
|------|------|
| 恶意 guideline 注入(python 网络请求)。 |
| YAML 反序列化攻击 | **只用 `yaml.safe_load`**(现状已是,`_merge_project_templates` L370);拒绝 `!!python/object` 等 tag。 |
| 模板名路径穿越(`../../etc/passwd`) | name 严格正则 `^[a-z][a-z0-9_]*$`;`file_path` 恒在 `/data/lake/templates/` 下(`Path.resolve()` 校验 prefix)。 |
| 试跑被当免费 LLM 代理 | ADMIN-only;`sample_text` ≤ 64 KiB;并发 ≤ 3;超时 60s;**可加 per-admin 试跑配额**(M2,经 system_db 计数)。 |
| 超大 YAML DoS | YAML ≤ 64 KiB;字段数 ≤ 50;guideline 每侧 ≤ 8 KiB。 |
| 删模板导致旧 dump 查询失败 | DELETE 前 `GET .../usage` 校验,有绑定 → 422。 |
| system 模板被改写破坏基线 | system/project 物理在只读区,API 403。 |

### 9.2 权限

- 所有端点 **Role.ADMIN**(prefix `/api/v1/admin`)。
- 查询类(列表/详情)可放宽到 VIEWER?**否** —— 模板 guideline 可能含敏感业务逻辑描述,默认 ADMIN-only;M2 视需求再放只读给 VIEWER。
- console 联调用 ADMIN api key(`dev-api-key-for-local-testing-only`)+ JWT。

### 9.3 校验分层

1. **结构校验**(§4.3,写盘前,同步,快)
2. **试跑**(§4.5,LLM 调用,慢,可选)
3. **生产观测**:build 后看 `/kg/quality`(orphan_rate/avg_degree/relation_type_coverage,CLAUDE.md),模板回归可量化。

### 9.4 审计(review H3)

模板直接决定「知识如何被抽取」,是治理面变更,必须审计。项目已有 `arrow_lake/workflow/audit.py` + `_lake_audit.py`(v1.9.x 审计/血缘)。CRUD 端点(POST/PUT/DELETE/PUT default)接入现有 audit hook,记录 `action=template_create|update|delete|set_default` + `name` + `actor` + `content_hash`(变更前后哈希),便于回溯「某图为何用了某套枚举」。审计写入复用现有 libSQL 审计表,不新增基础设施。

### 9.5 LLM 解码模式与注入面(review)

`guideline` 作 system-role prompt,注入面**取决于解码模式**:json_schema 约束解码(百炼 `qwen-turbo/plus`)把输出锁死在固定结构,注入面小;**json_object-only 模型(`qwen-max`/`deepseek-v3`,见 CLAUDE.md「百炼模型分档」)可被恶意 guideline 塑形 JSON 内容**,注入面更大。建议:模板试跑/抽取**优先 json_schema 模型**;UI/文档标注 object-only 模型的额外风险。

## 11. 风险与未决

| 风险 | 等级 | 说明 / 缓解 |
|------|------|-------------|
| 多 worker 下 gallery 缓存不一致 | 🟡 | prod_minimal 单 worker 无此问题;多 worker 需 invalidate 机制(M4)。短期文档注明「模板管理需单 worker 或 restart 后全 worker 生效」。 |
| user 模板质量参差拖垮 KG | 🟡 | 试跑(M3)+ `/kg/quality` 观测兜底;system 模板保证基线。不预审内容(无法自动判质量)。 |
| prompt injection 经 guideline | 🟠 | §9.1 全套对策;ADMIN-only;guideline 不拼接系统指令,作 user role 注入。**需 security-reviewer 过审(实现时)**。 |
| 模板文件被外部直改(绕过 API) | 🟢 | 自愈对账(§7.2)在下次列表时纠正;`content_hash` 检测。不阻塞,因 ADMIN 才有卷访问权。 |
| hyper-extract 升级改了 Template.create 签名 | 🟢 | 当前用绝对路径是稳定特性(project 模板依赖它);升级时回归测试覆盖。SDK 1.2.1↔server 等兼容性问题与本设计正交。 |
| 删除模板致旧 KA dump 查询失败 | 🟡 | DELETE 前 usage 校验(422);文档提示「删模板前先重建依赖它的数据集」。 |
| 中文实体名 normalize / 消歧与新模板交互 | 🟢 | 正交:`normalize_name`/`entity_resolver` 在模板下游,不感知模板来源。新模板一样受益。 |
| `gallery.match` O(模板数)线性 × 4 层,chunk 粒度 per-chunk 调用 | 🟢 | 现状 ~90 模板 + 1200 chunk <1s;user 模板 >500 时按 tag/category 建倒排索引(perf)。短期不阻塞。 |
| `reset_gallery_cache()` 每次重扫 ~80 个 preset YAML(不变量) | 🟢 | 单次 CRUD 几十 ms 可接受;模板量大时把 presets 部分单独缓存(M4/perf)。 |
| 多 worker 下 gallery lru_cache 各自独立 | 🟡 | **prod_minimal 单 worker 无此问题;多 worker 部署必须配 Redis pub/sub invalidate 或 restart 全 worker,否则部分 worker 持旧 gallery → 模板时有时无**(§4.2)。短期:文档 + 默认单 worker。 |
