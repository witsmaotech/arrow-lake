# v1.9.4 数据血缘 & 全生命周期埋点评审 (Lineage / Provenance Audit)

> 状态:评审完成 (2026-07-24)。范围:仅 `arrow_lake/` 生产代码 (排除 `tests/`/`examples/`/`docs/`)。所有结论附 `file:line` 证据,关键结论已交叉核实。
>
> 触发:用户反馈"整个数据血缘没有做起来,整个数据集各个环节周期埋点太少,体现不出追踪可溯源"。本评审核实该判断并定位根因。

## 0. 结论 (Verdict)

**不是"没做",是"做了一半、接通面窄、埋点薄、两套子系统是死代码"。** 血缘基建其实相当完整 (5 套溯源基底 + Lance 原生版本),问题在**接线**:

1. **只有 ingest (create/append) 真正喂血缘**——`_lake_ingest.py` 13 处调用 `_lineage_after_ingest`,异步三写 (Lance `_lineage_events` + libSQL 邻接索引 + Gravitino REST)。其余 7 个环节几乎不喂。
2. **即使 ingest,事件也是瘦的**:`source_datasets=[]` (硬编码空)、`actor="system"` (默认)、`lance_version=None` (没传)、无行数、无 schema 快照。
3. **`lineage_hooks.py` (5 个 `auto_record_*`) 和广义 `AuditTrail` 整块是死代码**——零生产调用方,给人"没做"的错觉。
4. **"谁 (actor)"几乎全程缺失**——router 层有认证用户却不向下传,这是"可溯源"最致命的洞。
5. **OTel span 埋点写在代码里但生产是黑的**——`_OTEL_AVAILABLE=False` (可选依赖默认 NoOp)。

用户"体现不出追踪可溯源"的体感**准确**,但根因不是架构缺失,是**接通窄 + 字段薄 + actor 全丢 + 两套自动捕获层没接线**。

## 3. 三个系统性根因

1. **接线断层**:`_lineage_after_ingest` 接通了,但同一套 `auto_record_*` 模式没复制到 query/rag/export/schema/kg/clean/delete——hook 写好了却没人 import。一次性接线工作没做完,不是架构缺失。
2. **actor 全程缺失**:router 层有认证用户 (`datasets.py:321` `_user`) 但**从不向下传**到 ingestor/storage/lineage。溯源最核心的"谁干的"在数据面彻底丢失。
3. **埋点薄 + 双轨死代码**:即使接通的 ingest,事件字段也空 (`source_datasets=[]`/`lance_version=None`);同时 `lineage_hooks.py` 和广义 `AuditTrail` 两套本该自动捕获的层是死的。

## 5. 已有的真东西 (不要重造)

评审时务必区分"已建可用"与"待接线",避免重复造轮子:
- **Lance 原生版本/tags/branches**:每次写自动版本化,`list_versions`/`read_at_tag`/`read_at_branch` 可用。
- **LineageStore 三写**:Lance + libSQL 邻接索引 + Gravitino REST 已活 (ingest 路径)。
- **GovernanceStore schema_changelog**:add/alter/drop column 已记录 (补 actor 即可)。
- **TaskManager task_history**:8 类异步任务终态已持久化 (补 detail 即可)。
- **RAG 会话库**:`rag_sessions`/`rag_turns`/`rag_feedback` 已记 question/answer/citations。
- **Backup manifest**:含 sha256 etag,verify 可用。
- **KA 版本归档**:archive/list/rollback 已实现。
- **OTel span 埋点**:代码里已写 (`_lake_ingest.py:491`/`_lake_search.py` 6 处/`_lake_query.py:80`),装依赖即亮。
