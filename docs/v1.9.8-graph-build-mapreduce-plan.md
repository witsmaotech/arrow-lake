# v1.9.8 重大改进规划:大文件高效高质量图谱构建

> 2026-08-01。源于 wuhu(552 页 PDF/1250 chunks)图谱构建实战血泪 + hyper-extract/hugegraph skill 反思。核心:解耦抽取与合并、厘清 docling 必要性、消歧治本、工具链加固。

## 一、背景:本会话踩出的根本矛盾

wuhu 图谱构建反复卡壳,根因是**架构层耦合**,不是单点 bug:

| 粒度路径 | 抽取 | 合并 | 速度 | 质量 | 坑 |
|---------|------|------|------|------|----|
| **per-chunk**(当前大文件默认,auto>500) | 并发 extract | ❌ 无 | 快(并发) | **差**(同实体 N 顶点、跨 chunk 关系全断 → 碎片/孤立) | 图谱质量低 |
| **per-dataset** | 串行 feed_text | ✅ MERGE_FIELD | **慢**(1250 chunks ~2.5h) | 中(只精确名合并,不消歧) | tiktoken 外网卡 + 某边界挂起 + 工具链重 |

**两难**:要质量就忍 dataset path 串行+卡;要速度就牺牲合并。本会话的消歧代码虽样本验证 OK,却因 dataset path 卡无法全量实证。**症结 = 抽取粒度和合并粒度被绑死在一条 path 上**。

## 二、改进 1:map-reduce 抽取架构(核心,解耦)

把"抽取"和"合并"拆成独立阶段,各取其快:

```
MAP     per-chunk 并发抽取(复用 chunk path 的 build_concurrency + hyper-extract extract)
        → 每块独立 ExtractionResult(不 insert)
SHUFFLE 全局实体池:normalize_name(已有)+ embedding 余弦聚类(阈值 0.60)
REDUCE  簇内批量 LLM 消歧 → canonical(entity_resolver,已实现+样本验证)
        + 跨 chunk 关系此时自然连通(端点都映射到 canonical)
INSERT  一次 _insert_kg 写 HugeGraph(canonical + 跨 chunk 关系 + 已重映射 entity_chunks)
```

**收益**:
- **快**:并发抽取(map),不串行 feed_text
- **质量**:全局合并消歧(reduce),跨 chunk 关系连通 → 治孤立/碎片
- **避坑**:绕开 dataset path 的 `build_dataset_ka` 串行 + HybridChunker/tiktoken 重初始化边界
- **复用**:chunk path 的 `_process_chunk`(只抽取部分)+ entity_resolver(已实现)

**落地**:`builder.py` 新增 `he_kg_granularity: "map_reduce"`(大文件默认)。`_execute_build` 加分支:并发 extract 收集全局 `result`(不 insert)→ `resolve_entities(result)` → 一次 `_insert_kg(entity_chunks=合并)`。

## 三、改进 2:ingest 链路反思——docling 必需性 + hyper-extract 边界

### 核心结论:**docling/kreuzberg 必需,hyper-extract 不能替代它**

职责不同:
- **docling/kreuzberg** = **解析**(PDF/DOC/PPT 二进制 → 结构化文本/markdown + 表格)。LLM 不参与版面/OCR。
- **hyper-extract** = **抽取**(文本 chunks → 实体/关系三元组)。输入必须是文本,吃不了 PDF 二进制。

所以链路是 `PDF → docling(文本)→ chunk → hyper-extract(三元组)`,hyper-extract 在 docling 之后,**不能跳过 docling 直接吃 PDF**。

### 但有三处可优化

1. **按输入格式分流,不一刀切 docling**:
   - PDF/DOC/PPT/扫描件 → docling(布局+表格+OCR,重型)
   - TXT/MD/CSV/JSON/HTML → **跳过 docling**,直接 chunk(快 10×)
   - 当前 `ingest` 已部分分流,但默认重型;应显式按 mime 路由
2. **docling 走 GPU**(552 页 CPU ~40s/页 = 6h+,GPU 5.4min):生产固定 GPU override(memory 已记 SOP)
3. **KG 抽取复用 ingest chunks,不重新 chunk**:dataset path 的 `build_dataset_ka` 用 hyper-extract HybridChunker 重新 chunk(需 tiktoken),与 ingest 产出的 chunks 重复且引入外网依赖。**map-reduce path 直接用 ingest chunks 喂 extract**,不再走 HybridChunker → 同时消灭 tiktoken 外网卡点。

### docling vs kreuzberg 决策

| 维度 | docling | kreuzberg |
|------|---------|-----------|
| 表格结构 | ✅ TATR 强 | ❌ 拍平 |
| 版面/阅读序 | ✅ layout-heron | ❌ 纯文本 |
| 速度 | 慢(CPU 200s/页,GPU 1s/页) | 快 |
| 依赖 | 重(torch+模型) | 轻 |

**建议**:工程/财报/方案类(表格密集,如 wuhu)用 **docling(GPU)**;纯文本/新闻用 kreuzberg。按 `doc_type` 路由。

## 六、改进 5:hyper-extract 引擎/Auto-Type/模板选型(skill + reference 深读)

### 5.1 Auto-Type(产物结构,8 种)
- **Record 系**(无关系):AutoModel(单对象)/ AutoList(有序)/ AutoSet(去重)——非图谱。
- **Graph 系**(建图谱,5 种):
  - **AutoGraph**:二元关系(经典 KG,含概念层次 is-a/part-of)——wuhu 默认。
  - **AutoHypergraph**:多元超边(3+ 实体,如多方协作)——可选增强。
  - **AutoTemporalGraph**:二元+时间(建设时间线)。
  - **AutoSpatialGraph**:二元+地点(区域部署)。
  - **AutoSpatioTemporalGraph**:二元+时间+地点。
- **wuhu 选型**:方案文档主体是系统/组织/概念二元关系 → **AutoGraph**;若需"多方联合演练"语义再评估 Hypergraph;有建设里程碑/区域分布再上 Temporal/Spatial。不一上来上最复杂的超图/时空图。

### 5.2 Method(抽取算法,9 引擎,两类)

**Typical 系(直接抽取,小中文档,per-chunk 友好)**:

| 引擎 | 特点 | 适合 |
|------|------|------|
| itext2kg | 高质量三元组,迭代精炼,node 带 label+name | 知识图谱、质量优先 |
| **itext2kg_star** | + SemHash 语义去重 + observation_date 边元数据 | **生产级**(map-reduce 的 map 引擎首选) |
| kg_gen | 轻量纯三元组,node 只 name,灵活 schema | 快速原型、自定义 schema |
| atom | 时序原子事实 + 证据归因 + 置信度(ka.facts) | 时序分析、事实验证、时间线 |

**RAG 系(检索增强,大文档,慢但覆盖彻底)**:

| 引擎 | 特点 | 适合 |
|------|------|------|
| light_rag | 最快 RAG,二元边(source/target/description/keywords/strength) | 中-大文档,通用首选 |
| **graph_rag** | 社区检测(graspologic hierarchical Leiden)+ **层次化摘要** | **超长文档(>50K 词),覆盖最彻底** |
| hyper_rag | N 元超边(participants 列表,2+ 实体) | 多方关系(协作/交易/联合机制) |
| hypergraph_rag | 超边=完整语义单元(知识片段,completeness_score),node 带 key_score | 高级超图、保留原文上下文 |
| cog_rag | 双超图(宏观 Theme 超边 + 微观 Entity 边) | 多跳推理问答 |

> **"层次"建图 = 两层含义**:① AutoGraph 的 is-a/part-of 边语义(概念层次);② graph_rag 的 Leiden 社区层次摘要(主题层次)。hyper-extract 无独立"层次图"Auto-Type。

### 5.3 wuhu 大文件三方案对比

| 方案 | 机制 | 优 | 劣 |
|------|------|----|----|
| **map-reduce + itext2kg_star/模板**(v1.9.8 P0) | per-chunk 并发抽取 → 全局 entity_resolver 消歧 → 一次 insert | 并发快 + SemHash 去重 + 消歧治本 + 复用现有 chunk path/entity_resolver | 需新 `map_reduce` path |
| **graph_rag**(hyper-extract 原生) | 内置 Leiden 社区检测 + 层次摘要 | 超长文档质量最高,自动发现主题结构 | 串行慢 + 依赖 networkx/graspologic + method 路径待修 |
| **light_rag**(hyper-extract 原生) | 二元边 + 检索,快 | 平衡 | 串行 feed + 检索开销,无社区结构 |

### 5.4 落地路线
- **短期 v1.9.8 P0**:**map-reduce + project_concept_graph 模板**(走 AutoGraph 等价)+ entity_resolver 消歧。已验证可行(消歧样本 + chunk path 并发)。
- **中期评估**:map-reduce 质量不够 → 试 **graph_rag**(原生社区+层次)或 **hyper_rag**(多方联合语义,如应急协同)。前置:修 `method/` 路径(memory:当前 broken,只有模板路径稳定)+ 装 networkx/graspolic。

## 改进 7:模板强化(project_concept_graph,质量基线)

模板已高质量(22 类型 + 16 关系严格枚举、definition 必填、防数值/量纲当实体、易混类区分)。结合 wuhu 实战(孤立/碎片/无语义边),补强:

### P0(随 map-reduce 一起,v1.9.8)
1. **关系 type-pair 约束**:16 关系只约束 type 枚举,**不约束 source/target 的 entity type** → LLM 乱连无意义边(如"金额—训练→硬件""主体—部署于→条款")。加**合法 type-pair 白名单**(`部署: 软件/模型→硬件/平台`、`承担: 主体→条款/服务`、`训练: 模型→数据`、`报价: *→金额` 等)+ post-validate 过滤违规边。治无语义边噪声(孤立/碎片的另一来源)。
2. **关系 description 必填**:当前 `relations.description required: false` → 改 `true`。`_build_neighbor_context` 注入 LLM 时拿 `relation_type + description`(第一批修复已取 relation_type,再加 description),问答质量再提一档。

### P1(v1.9.9,信息完整性)
3. **provenance 字段**:entity/relation 加 `source_chunk`(抽取时记录所在 chunk)。问答可引用原文片段 + 审计哪些关系是无源常识臆造。借鉴 atom 引擎的证据归因。
4. **指标/金额/条款 value 属性**:当前为防"数值当实体"只抽命名(指标类只抽"系统响应时间"不抽"7天")——**数值彻底丢了**。加 `value` 字段存数值(name 仍是命名术语,value 带"7天/9.89%/500万")。不污染图结构,不丢关键事实(问答能答"响应时间是多少")。

### P2(v1.9.9,抽取准确率)
5. **22 类型 few-shot**:易混类(硬件vs软件/模型vs技术/指标vs要求/资质vs安全)加 1-2 示例,降误分(wuhu 实战见过 type 塌缩)。或在 entity_router 扩 CJK 别名。
6. **entity_id 规范化 + aliases**:`identifiers.entity_id: name` 是精确名合并根因(孤立)。**entity_resolver 已治本**(map-reduce 的 reduce 阶段);模板加 `aliases` 字段(LLM 抽时列别名/简称)辅助消歧 + 前端"又名"展示。

### P3(v1.10+,按需)
7. 关系 `confidence`(LLM 自评,atom 风格)/ `condition`(项目文档的"若...则..."条件条款);`包含/is_a` 关系天然成树,加树校验 + 层次展示。

> **最值得马上做**:P0 的 type-pair + description 必填——wuhu 质量(无语义边 + 关系语义单薄)的直接解,模板小改,配合 map-reduce 立竿见影。

## 改进 8:能力边界 review —— 能否达到层次化检索 + 超图

### map-reduce 的能力边界
map-reduce(AutoGraph 二元 + entity_resolver)解决**高效率 + 高质量**(并发 + 消歧),但**不内建**:
- **层次化检索**(社区/主题层次):plain graph 无社区结构 → 需叠 Leiden
- **超图**(多元 N 元关系):AutoGraph 二元边 → 需 AutoHypergraph

### 路线对比

| 路线 | 高效率 | 高质量 | 层次化 | 超图 | 复杂度 |
|------|--------|--------|--------|------|--------|
| map-reduce(AutoGraph) | ✅ | ✅ | ❌ | ❌ | 低 |
| graph_rag(原生) | ❌串行 | ✅ | ✅Leiden | ❌ | 中 |
| hyper_rag(原生) | ❌串行 | ✅ | ❌ | ✅N元 | 中-高 |
| **map-reduce + Leiden**(渐进) | ✅ | ✅ | ✅叠加 | ❌ | 中 |
| **map-reduce on AutoHypergraph**(渐进) | ✅ | ✅ | (再叠) | ✅ | 高 |

### 结论:渐进叠加(推荐)
没有"全维度 + 快 + 简单"的银弹。graph_rag 的层次化和 hyper_rag 的超图都以**串行+重计算**换能力,与"大文件高效率"冲突。**map-reduce 把"高效率+高质量"基础打牢,再按需叠加高级能力**(社区/超图)。
