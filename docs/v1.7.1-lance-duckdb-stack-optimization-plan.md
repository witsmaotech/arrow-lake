# v1.7.1 Lance / LanceDB / DuckDB 技术栈优化升级方案

**日期**: 2026-06-25
**范围**: lancedb 应用层 · pylance 格式层 · DuckDB + lance 扩展引擎层
**目标**: 在已完成 v4→v6 升级的基础上，系统性评估三层技术栈的版本升级与代码/配置优化空间，分批落地低风险高收益项。
**状态**: 🟡 设计中（第一批实施中）

---

## 1. 背景与三层视图

项目以 **Lance 列式格式** 为湖仓底座，访问层分三部分，需协同评估：

| 层 | 角色 | 关键依赖 | 项目入口 |
|---|---|---|---|
| **应用层** | SDK 建表/搜索/嵌入/FTS | `lancedb` | `arrow_lake/ingest/`、`arrow_lake/query/` |
| **格式层** | 直接操作 Lance 文件/索引/事务 | `pylance` | `arrow_lake/ingest/_storage_*.py` |
| **引擎层** | 进程内 SQL + 向量/全文表函数 | `duckdb` + duckdb `lance` 扩展 | `arrow_lake/query/_db.py`、`session_manager.py` |

> DuckDB 是**主力查询路径**（`lance_scan` / `lance_fts` / `lance_vector_search` 分布在 9 个文件、40+ 处调用），并非单纯 fallback。引擎层配置优化权重高。

## 5. 版本升级风险评估（头号风险）

### 核心风险：duckdb `lance` 扩展与 pylance 格式版本断裂

容器内 `INSTALL lance` 拉取的是 **DuckDB 官方 `core` 扩展仓库**版本（commit `1b4ef68`，绑定 DuckDB 1.5.2 ABI），**不是** `lance-format/lance-duckb` 独立构建。

- ✅ 与 DuckDB 1.5.2 ABI 绑定，**不会**出现 DuckDB 版本断裂。
- ⚠️ core 扩展的 Lance 格式支持**滞后于上游 pylance**。若 pylance 7.0 默认写 v2.2/v3，而 core 扩展只认 v2.1 → **DuckDB 读不了 lancedb 新写的文件**，40+ 处查询全部受影响。

### 建议升级路径（降低风险）

```
1. 测试容器升 lancedb 0.33.0 + pylance 7.0.0
2. 【关键验证】新版写一个 Lance 文件 → docker exec 跑：
     INSTALL lance; SELECT * FROM lance_scan('s3://...');
   确认 DuckDB core 扩展能读取
3. 若读取失败 → 写入侧锁定 Lance format version 对齐：
     lance.write_dataset(..., enable_v2_format=...)  # 或 data_storage_version
4. lancedb 0.33 兼容性：create_fts_index 仍可用（标 legacy），
   tantivy 后端是否移除需确认（0.31 beta 曾计划移除）
5. 跑全套 pytest（含 KG/doc_type 集成测试）+ Phase 4 端到端验证
```

**升级评估表**：

| 升级 | 风险 | 主因 |
|---|---|---|
| lancedb 0.30.2 → 0.33.0 | 中 | API 变更，FTS 后端可能调整 |
| pylance 6.x → 7.0.0 | **高** | 文件格式版本，影响 DuckDB 读取 |
| duckdb 1.5.2 → 不动 | 无 | 已是最新线 |

## 6. 第一批实施详情（P0 配置层）

> 目标：零/低代码风险，立即见效。仅改 `deploy/docker-compose.prod.yml`。

### 6.1 LANCE IO/CPU 线程（P0-1）

**问题**：数据存 MinIO（S3 协议），lance SDK 对象存储读取吞吐依赖 `LANCE_IO_THREADS` / `LANCE_CPU_THREADS`，当前 compose 完全未设 → 用 lance 默认值（偏保守）。

**改动**：在 `x-storage-env: &storage-env` anchor（line 65）追加，被 api / ray-head / ray-worker / ray-gpu-worker 4 个服务继承：

```yaml
x-storage-env: &storage-env
  # ... existing ...
  LANCE_IO_THREADS: "${LANCE_IO_THREADS:-64}"    # IO 密集，高并发对象存储读取
  LANCE_CPU_THREADS: "${LANCE_CPU_THREADS:-4}"   # 匹配 ray 4 CPU；api(2 CPU) 可在 .env 覆盖为 2
```

**收益**：MinIO 读取并行度提升，向量检索 / lance_scan 吞吐上升。
**风险**：极低（线程数软上限，OS 调度）。CPU 线程略高于实际核数无害。

### 6.2 DuckDB 内存上调 + 容器内存配套（P0-2）

**问题**：`max_query_memory_mb=512`（`olap.py:39`）对向量检索 + 聚合偏小，易触发 spill 到 `temp_directory` 拖慢查询。

**权衡分析（关键）**：

| 维度 | 现状 | 约束 |
|---|---|---|
| api 容器内存 | 4G | 4 个 uvicorn worker 共享 |
| 每 worker DuckDB 预算 | `4 并发 × 512MB = 2GB` | 4 workers 理论 8GB > 4G（已超配） |
| `max_concurrent_queries` | 4 | `OlapConfig` |
| 宿主机可用 | 65GB | 充裕，可放宽容器限制 |

**改动**（`docker-compose.prod.yml` api 服务）：

```yaml
environment:
  # ... existing ARROW_LAKE__OLAP__* ...
  ARROW_LAKE__OLAP__MAX_QUERY_MEMORY_MB: "${OLAP_MAX_QUERY_MEMORY_MB:-1024}"   # 512 → 1024
deploy:
  resources:
    limits:
      memory: ${API_MEMORY_LIMIT:-8G}    # 4G → 8G（配套，宿主机内存充裕）
      cpus: "${API_CPU_LIMIT:-2.0}"
```

**注入链已验证**：`config/main.py:102` `env_nested_delimiter="__"` → `ARROW_LAKE__OLAP__MAX_QUERY_MEMORY_MB` 直接覆盖 `OlapConfig.max_query_memory_mb`，经 `session_manager.py:396` 注入 `DuckDBSession(max_memory_mb=...)`。**零 Python 代码改动。**

**收益**：单查询可用内存翻倍，减少 spill，大聚合/join 提速。
**风险**：低。`OlapConfig.validate_memory_budget()`（`olap.py:89`）提供 70% RAM 告警；8G 容器下 4 workers 实际靠并发利用率运转，DuckDB `memory_limit` 为软上限。
