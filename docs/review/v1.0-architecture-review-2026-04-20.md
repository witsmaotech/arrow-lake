# Arrow Lake v1.0 架构评审纪要

**日期**: 2026-04-20
**基于**: `docs/architecture-v1.0-draft.md` v1.0-draft
**参与方**: Winston (Architect), Amelia (Developer), John (PM), Mary (Analyst)
**状态**: 待用户决策

---

## 评审背景

v1.0 架构设计文档经多轮迭代后进行五方评审。本次评审覆盖以下关键更新：

1. Lance 从组件提升为统一数据格式层，DuckDB/DuckLake 消费 Lance，MinIO 降级为 Lance 的 S3 存储后端
2. DuckDB 1.5.2 Lance 原生扩展发现（`__lance_scan`, `lance_vector_search`, `lance_fts`, `lance_hybrid_search`）
3. DuckLake 从"不集成"修订为"可写衍生层"（ADR-06 修订）
4. 新增第三章：Ray / Daft / Metaflow 计算框架
5. M0 范围扩展：新增 DuckDB 扩展加载 + 查询层重构

---

## 一、Winston (Architect) 评审意见

### 1.1 肯定

- **Lance 格式层决策**是本次修订中最有价值的架构决策。依赖方向单向（Lance → DuckDB/DuckLake → MinIO），可独立替换每一层。
- DuckLake 作为可写衍生层的模式清晰，类似 Delta Lake 的 read-only checkpoint + writable commit log。
- 计算框架独立章节（Ch.3）是正确做法。

### 1.2 风险与建议

| # | 问题 | 严重度 | 建议 |
|---|------|--------|------|
| W1 | DuckDB Lance 扩展版本耦合（1.5.2 是首个内置版本，属前沿） | HIGH | 文档需包含 DuckDB 版本锁定策略和已知可用矩阵 |
| W2 | `lance_vector_search`/`lance_fts`/`lance_hybrid_search` 功能完整性未验证 | HIGH | 对比 Lance Python API，文档化已知缺口和 workaround |
| W3 | Lance 扩展与 DuckDB 之间的错误边界未定义（文件损坏/索引过期时的行为） | MEDIUM | 需明确错误传播策略 |
| W4 | 跨存储 JOIN 复杂度无上限（DuckDB 内存中同时拉取 Lance + DuckLake） | MEDIUM | 定义查询复杂度预算 + DuckLake 数据生命周期/TTL + 降级路径 |
| W5 | Ch.3 缺失数据流契约（框架间数据一致性保证） | MEDIUM | Ray 写 Lance → Daft 读 Lance 的最终一致性需声明 |
| W6 | Ch.3 缺失资源隔离策略（Ray/Daft/Metaflow 共享还是独立集群） | MEDIUM | 需明确资源分配方案 |
| W7 | Ch.3 缺失失败域分析（Ray 崩溃对 Metaflow workflow 的影响） | MEDIUM | 需定义检查点/重启机制 |
| W8 | Ch.3 缺失技术选型论证（为何 Ray+Daft+Metaflow 而非 Ray Datasets / Prefect / Airflow） | LOW | 需具体选型标准 |
| W9 | M0 查询层重构需有回滚路径 | HIGH | 使用 adapter pattern / feature flag，确保可回退到 PyArrow bridge |

### 1.3 缺失项

- 分布式追踪（可观测性）
- Schema 演化传播（Lance 新列 → DuckDB catalog 是否自动刷新）
- 多租户隔离
- 备份恢复
- 成本模型

## 二、Amelia (Developer) 评审意见

### 2.1 M0 阻断项

| # | 问题 | 严重度 | AC 需求 |
|---|------|--------|--------|
| A1 | `__lance_scan()` 是内部 API（双下划线），DuckDB 次版本可能移除 | **CRITICAL** | 必须通过 `_base.py` 抽象层，任何模块不得直接调用；需定义 fallback path AC |
| A2 | `ATTACH TYPE lance` 表发现问题（1.5.2） | **CRITICAL** | `metadata.py`/`faceted.py` 依赖 `information_schema` 发现列，需集成测试验证 |
| A3 | 扩展加载可能在 GPU 容器无网络时失败 | HIGH | 必须在启动时 fast-fail + pre-bundle 扩展到 Docker 镜像 |
| A4 | `storage_options` 无定义 schema | HIGH | 全局 vs 每数据集？环境变量派生？需明确 schema |
| A5 | `__init__.py` 950+ 行 God Class 分解无具体 AC | MEDIUM | M0 必须包含分解 AC，否则 M0 成移动靶 |
| A6 | Lance 不支持删列，`dedup.py`/`nemo_curator_filter.py` 的 schema 变更可能导致静默回归 | MEDIUM | 去重/质量路径需测试覆盖 |

### 2.2 跨格式风险

| # | 问题 | 说明 |
|---|------|------|
| A7 | DuckLake 使用 Parquet 内部格式，与 Lance 形成"双格式"管道 | 导出路径增加格式转换；测试需覆盖 DuckLake 中间状态 |
| A8 | Lance 和 Parquet NULL 表示不同 | 跨格式 JOIN 的 NULL 语义未定义，无测试覆盖 |
| A9 | CatalogActor 迁移 Ray 后每次调用变为网络往返 | μs → ms 延迟；`test_lineage_store.py` mock 全部失效，需 100% 重写 |
| A10 | Daft 惰性求值 + ingest 管线副作用（写磁盘/审计事件） | 错误时机不可预测；无 AC 定义审计事件触发时机 |
| A11 | Argo bridge 需要 K8s 新 Helm templates + service accounts + RBAC | 当前 deployment.yaml 仅处理 query service |

### 2.3 核心建议

> **不要在 DuckDB Lance extension 抽象层 AC 确定并 review 之前开始 M0 实现。** 所有后续工作都依赖它。直接对 `__lance_scan()` 构建查询模块再回头加抽象 = 重写，不是重构。

## 三、John (Product Manager) 评审意见

### 3.1 核心观点

1. **v1.0 标签有误导性** — 原始架构文档描述 Daft SQL 作为主 OLAP，但实际代码中 `daft_sql()` 是 `NotImplementedError`。REST API 建立在部分 SDK 方法还是 `NotImplementedError` 的基础上。**优先让 SDK 真正工作，再加端点。**

2. **M2/M3 时间线质疑** — RAG 4 周？KG 4 周？各自需要 1 周 spike + NO-GO trigger。HugeGraph 是全新分布式系统，4 周集成+生产就绪乐观。

3. **DuckLake 推迟建议** — Lance 已支持版本管理/压缩/schema 演化。DuckLake 的需求未验证。**闻起来像过早优化。**

### 3.2 建议砍掉/推迟的项目

| 项目 | 建议 | 理由 |
|------|------|------|
| DuckLake writable derivative | **推迟到 v1.0 之后** | 未验证需求，增加存储复杂度 |
| Knowledge Graph (M3) | **缩减为 2 周 spike + MVP** | 4 周乐观 |
| Multi-model ensemble search | **推迟** | 非 user pain point |
| Faceted search (DuckDB CUBE) | **推迟** | 低需求信号 |
| NeMo Curator GPU pipeline | **推迟** | CPU fallback 存在 |
| Argo Workflows | **推迟** | Metaflow local + Ray SSH 够用 |
| Video keyframe extraction | **推迟** | 复杂，MVP 低 ROI |

释放 6-8 周工程容量，重新分配到：实现 Lake facade、REST API 建在工作 SDK、真实 E2E 测试、CI/CD。

### 3.3 v1.0 唯一关键指标 (OMTM)

> **"数据工程师从零到可工作的 hybrid search API 能否在 1 小时内完成？"**
> - `docker compose up` 真正工作
> - `Lake.ingest()` 真正 ingest（不是 NotImplementedError）
> - `Lake.search()` 返回真实结果
> - REST API 暴露这些操作
> - 文档与实际匹配

### 3.4 DuckDB Lance Extension 降级路径

原始架构有 Daft SQL 降级路径（DuckDB 失败时 Daft 接管）。新路径是否有降级方案？是否保持 Arrow zero-copy？

## 四、Mary (Business Analyst) 评审意见

### 4.1 肯定

- Lance 统一格式是**根本原因消除**的经典案例 — 不是添加编排在多个格式边界，而是直接消除边界。
- DuckDB 原生统一查询（OLAP+向量+FTS+混合）是真正的**竞争差异化**。
- 证据链强健：DuckDB 1.5.2 兼容性通过实验验证，不是假设。

### 4.2 风险与建议

| # | 问题 | 优先级 | 建议 |
|---|------|--------|------|
| M1 | DuckDB Lance extension 性能墙无回滚 trigger | HIGH | 添加决策门："如果 Lance 查询在 Y 并发用户下超过 Xms，重新评估 Parquet 共存" |
| M2 | DuckLake→Lance 发布管道无明确团队归属 | HIGH | 文档化 ownership（Data Engineering? Platform?） |
| M3 | DuckLake 和 Lance 之间无数据质量门 | HIGH | 添加检查点："数据必须通过质量验证才能从 DuckLake 工作区提升到 Lance SSOT" |
| M4 | RBAC 对"智能数据平台"是业务关键需求 | HIGH | 应分配到 M3 或 M4 前置条件，不是 post-launch |
| M5 | M2 RAG 4 周进度风险无 buffer | MEDIUM | 添加 descope 标准 |
| M6 | M4 生产就绪 4 周可能实际需 6-8 周 | MEDIUM | 每个 M4 交付项需要信心评估 |
| M7 | Daft/Metaflow/Ray 决策矩阵缺失 | MEDIUM | 创建："用 Daft 当 X；用 Metaflow 当 Y；用 Ray 当 Z" |
| M8 | CatalogActor 无 SLA/可用性目标 | MEDIUM | 单点故障风险需明确承认和缓解 |
| M9 | Lance 单格式依赖 = 单供应商风险 | MEDIUM | 风险注册中添加格式多样化 trigger |

### 4.3 竞争定位 (Porter's Five Forces)

| 力量 | 评估 |
|------|------|
| 替代品威胁 | **低** — 统一 DuckDB-native OLAP+向量+FTS+混合在市场罕见 |
| 供应商议价力 | **中** — Lance 单供应商依赖；DuckDB 开源但背后一家公司 |
| 竞争对手 | **中** — Delta Lake + Databricks 主导企业；Arrow Lake 目标不同细分市场 |
| 新进入者威胁 | **低** — Lance+DuckDB+DuckLake 集成深度创造有意义的切换成本 |
