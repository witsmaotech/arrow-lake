# v1.7.0 — hyper-extract 集成 KG 抽取层优化方案

> **版本**：v1.7.0 核心特性 ｜ **状态**：设计完成，待实施 ｜ **日期**：2026-06-23
> **范围**：`arrow_lake/knowledge_graph/` 抽取环节升级 + HugeGraph schema 演进
> **依赖外部框架**：[hyper-extract](https://github.com/yifanfeng97/Hyper-Extract)（Apache-2.0）

---

## 1. 背景与目标

项目 KG 抽取层 `EntityExtractor`（`arrow_lake/knowledge_graph/extractor.py`）现状有四个瓶颈：

1. **单一硬编码 prompt**：5 类实体枚举（person/organization/location/concept/event）写死在 `_ENTITY_EXTRACT_PROMPT`（extractor.py:50-97），无模板化、无领域适应。
2. **无文档类型分发**：KG 模块完全没有 doc_type 路由逻辑（grep 零命中），所有文档走同一 prompt。
3. **LLM 走纯文本+json 修复链**：provider 不支持结构化输出（`BaseLLMProvider.generate` 只返回字符串，provider.py:223-248 无 `response_format`/json_schema），靠 `_try_parse_json` + 9 个修复后缀兜底，易塌成乱码。
4. **实体类型未路由**：`schema.py` 定义了 person/organization/location/concept/event 5 个细分 vertex label，但 `builder.py:256` 把所有实体都写成 `label:"entity"`，细分 label 从未启用——抽取的 `entity_type` 只存进 `entity` 顶点的 `type` 属性。

**目标**：引入 hyper-extract 作为抽取引擎，实现：
- 按文档类型选领域模板，提升抽取精准度与领域适应性
- 用 LLM 结构化输出（json_schema）替代文本修复链，提升三元组质量
- 解锁超图 / 时序 / 时空高级结构（Phase 2）
- 与 HugeGraph 无缝集成（适配层，builder/存储零侵入）

**关键决策**：分阶段渐进 + 元数据驱动文档类型识别。

## 2. 设计基石（实测事实）

- **builder 靠鸭子类型**（builder.py:242）：`self._extractor.extract(content, chunk_id=cid)` 只要求返回对象有 `.entities`(tuple of name/entity_type/properties) 和 `.relations`(tuple of source/target/relation_type/properties)。`tests/benchmark` 的 `_MockEntityExtractor` 证实可替换。**这是最小侵入的支点**。
- **ExtractionResult 契约**（extractor.py:107-132）：`ExtractionResult(entities, relations, raw_text)` / `ExtractedEntity(name, entity_type, properties)` / `ExtractedRelation(source, target, relation_type, properties)`，全 frozen dataclass。
- **AutoGraph 输出**：`{nodes:[{name,type}], edges:[{source,target,type}]}`——字段名与 ExtractionResult 不同（nodes/edges vs entities/relations），需适配层转换。
- **HugeGraphClient**（client.py）：`add_vertices(list[dict]) -> list[str]`、`add_edges(list[dict]) -> int`、`ensure_schema(payload)`、批量由调用方切片。
- **schema 已有**：8 vertex label（含细分 person/org/location/concept/event + event 带 `date`）、`date` property key。**缺**：超图中间节点 label、空间坐标 property。
- **hyper-extract Provider**：可接任意 OpenAI 兼容 base_url（`create_client("bailian"/"vllm:Model@url")` 或直接传 LangChain `ChatOpenAI(base_url=...)`）。硬性要求 LLM 支持 json_schema/function calling（不兼容 qwen-max/deepseek-v3）。

## 3. 核心架构：适配层保持 builder 无感知

```
chunk + doc_type
      │
      ▼ (config 开关: extractor_backend = legacy | he)
┌─────────────┐                 ┌──────────────────────────┐
│EntityExtractor│ (legacy, 保留)  │ HyperExtractExtractor     │ (新增)
│ 纯文本+json  │                 │  doc_type→template 路由   │
│   修复链     │                 │  Template.create → parse  │
└──────┬──────┘                 │  AutoGraph→ExtractionResult│
       │                        └─────────────┬────────────┘
       └──────────┬───────────────────────────┘
                  ▼  统一契约 ExtractionResult
            KGBuilder（零改动）→ HugeGraphClient → HugeGraph
```

关键：`HyperExtractExtractor` 实现与 `EntityExtractor` 相同的 `async extract() -> ExtractionResult` 契约，builder 无感知。config 开关控制用哪个，支持 A/B 对比与回退。

## 4. Phase 1：抽取质量 + 文档类型 + 实体类型路由

### 4.1 新增 hyper-extract 适配层 `arrow_lake/knowledge_graph/he_extractor.py`

- 类 `HyperExtractExtractor`，`async extract(text: str, *, chunk_id: str = "", doc_type: str | None = None) -> ExtractionResult`
- 内部流程：
  1. `doc_type` → template 路径（查 `DocTypeRouter`，fallback 到默认模板）
  2. 复用单例 `Template.create(template, language, llm_client, embedder)`（缓存避免每 chunk 重建）
  3. `ka = template.parse(text)`（新实例，非 feed_text，保持 chunk 间隔离）
  4. 转换：`node{name,type}` → `ExtractedEntity(name, entity_type=node.type or "concept")`；`edge{source,target,type}` → `ExtractedRelation(source, target, relation_type=edge.type)`
  5. 返回 `ExtractionResult(entities, relations, raw_text=text)`
- LLM/embedder：从项目 `LLMConfig` 构造 LangChain `ChatOpenAI(base_url=..., api_key=..., model=...)` + `OpenAIEmbeddings(...)`，喂给 `Template.create(llm_client=, embedder=)`。单一配置源，不分裂。
- 异步封装：hyper-extract 的 `parse` 是同步且内部已有 `max_workers` 并发，适配层用 `asyncio.to_thread` 包一层，避免阻塞事件循环；batch 并发复用 `HugeGraphConfig.build_concurrency`（替代 legacy 硬编码的 Semaphore(5)）。

### 4.2 新增文档类型路由 `arrow_lake/knowledge_graph/doc_type_router.py`

- `DocTypeRouter`：`resolve(doc_type: str | None) -> str`（返回 template 路径）
- 映射表来自 config（`he_doc_type_templates`），如 `{"research_paper": "academic/paper", "resume": "general/biography_graph", "default": "general/default_graph"}`
- doc_type 来源：chunk table 的元数据列 / document 顶点属性（builder 已按 `document_name` 去重建 document 顶点，可在该路径补 `doc_type` 列读取）。

### 4.3 config 扩展 `arrow_lake/config/rag.py`

在 `HugeGraphConfig` 新增字段（走现有 4 层 config：默认/.env/env/YAML）：
```python
extractor_backend: Literal["legacy", "he"] = "legacy"   # 平滑开关
he_default_template: str = "general/default_graph"
he_doc_type_templates: dict[str, str] = {}
he_language: Literal["zh", "en"] = "zh"
he_model: str | None = None        # None=复用 LLMConfig.model；指定则覆盖
```

### 4.4 builder 注入点 + doc_type 透传

- 工厂（实施时用 `search_graph` 定位 `_create_kg_extractor`/`_create_kg_builder`；Explore 报告指向 `_lake_kg.py` 但该文件已不存在，实际在 Lake facade mixin）：按 `extractor_backend` 选 `EntityExtractor` 或 `HyperExtractExtractor`。
- `builder.py:242` 调用补 `doc_type`（从 chunk table 列读取，如 `row["doc_type"]`），透传给 `extract`。legacy extractor 忽略该参数（签名兼容）。

### 4.5 实体类型精准路由（修复实体 label 矛盾，独立质量改进，legacy/he 双受益）

- `builder.py:253-262` entity→vertex 映射：按 `entity.entity_type` 路由 vertex label（`person/organization/location/concept/event`，未知类型 fallback `entity`），而非全部 `label:"entity"`。
- schema.py 的细分 label 已就绪，无需改 schema。注意 event label 带 `date` property——若 entity_type=event 且 properties 含 date，写入对应字段。

### 4.6 前置验证（go/no-go，实施首步）

- 确认项目当前 LLM 模型支持 json_schema/function calling。若不支持（如 qwen-max/deepseek-v3），需：`he_model` 指定兼容模型（qwen-plus/gpt-4o/deepseek-r1），或扩 `BaseLLMProvider` 加结构化输出方法。**实施首步须验证此项**。

## 5. Phase 2：超图 / 时序 / 空间 schema 扩展（Phase 1 验收后）

### 5.1 HugeGraph schema 扩展 `schema.py`

- **超图**：新增中间节点 vertex label（如 `relation_group`，带 `type`/`description` property）+ edge label `member_of`（`relation_group` → 任意 entity）。AutoHypergraph 的多元超边 → 中间节点 + 星形二元边，`role` 落到 edge property（保角色语义）。
- **时序**：edge label 的 properties 加 `time`（property key 已有 `date`，可复用或新增 `time` TEXT）。AutoTemporalGraph 的 `time` 字段落到 edge property。
- **空间**：新增 property key `location`(TEXT)/`coordinates`(TEXT)，挂到相关 vertex/edge label。

### 5.2 适配层扩展 `he_extractor.py`

- `HyperExtractExtractor` 按 template 的 Auto-Type 分支输出：
  - AutoGraph → ExtractionResult（Phase 1 已实现）
  - AutoHypergraph → ExtractionResult + 额外 `hyper_groups`（中间节点 + member_of 边）
  - AutoTemporalGraph → relations 的 properties 带 `time`
  - AutoSpatialGraph → entities/relations 的 properties 带 `location`
- builder 扩展：识别 `hyper_groups`/`time`/`location`，调 `add_vertices`/`add_edges` 写入对应 label/property。

### 5.3 引擎与模板策略

- 超图场景选 `method/hyper_rag` 或 `method/hypergraph_rag`；时序选 `method/atom`；通用二元 `method/light_rag` 或 `method/itext2kg_star`。模板按 doc_type 路由到对应 method + 领域模板。

## 9. 风险与回退

- **模型兼容性**：json_schema 不支持 → 用 `he_model` 覆盖或扩 provider（4.6）。
- **质量回归**：`extractor_backend` 默认 `legacy`，he 经 gold 标准对比验收后再切默认。
- **性能**：hyper-extract 内置并发 + `to_thread` 包装；若成为瓶颈，benchmark 定位后调 `build_concurrency`。
- **Phase 隔离**：Phase 2 仅 schema 扩展（新增 label/property，不破坏 Phase 1 数据），可独立验收上线。

## 11. Review 修订记录（2026-06-23）

对方案做了一轮批判性 review，识别 **4 个致命点 + 3 个次要点**。修订决定如下（实施时据此调整正文；本节为权威修订依据）。

### 11.1 🔴 致命 1：LLM 结构化输出兼容性（go/no-go 关卡）

**问题**：项目 `OpenAICompatibleProvider._build_body` **刻意不加** `response_format`（provider.py:240-242 注释「太严格，prompt 显式 JSON 更稳」），而 hyper-extract **硬要求** json_schema/function calling。若现用模型是 qwen-max/deepseek-v3（仅支持 json_object），Phase 1 质量提升前提崩塌。

**修订**：原 4.6「前置验证」升级为 **Phase 1 第 0 步（§4.0）**，含三个子任务：
1. 实测：用项目当前模型跑 `Template.create(...).parse(真实文档)`，确认能否产出合法结构化输出
2. 不兼容则：`he_model` 指定兼容模型（qwen-plus / gpt-4o / deepseek-r1）
3. 扩 `BaseLLMProvider` 加结构化输出方法 `generate_structured(messages, schema)`，**legacy EntityExtractor 继续用 `generate()` 不受影响**（向后兼容）

**关卡**：第 0 步不通过，不进入 4.1。

### 11.2 🔴 致命 2：doc_type 元数据驱动的隐藏依赖

**问题**：方案假设 chunk table 有 `doc_type` 列，但实测 `DocumentConfig` 无此字段，`builder.py:150-171` 列规范化只补 `id/document_name/chunk_index`。**doc_type 列当前根本不存在**。

**修订**：新增 **Phase 1 前置子任务（归入 §4.0）**：doc_type 字段贯通 ingest → chunk table
- `DocumentConfig` 加 `doc_type` 字段；ingest connector / 上传 API 写入 doc_type
- builder 列规范化补 doc_type 读取
- 4.2 文档类型路由依赖此前置；未贯通前 he 路径 fallback 到默认模板

### 11.3 🔴 致命 3：confidence 过滤门丢失

**问题**：legacy 三层过滤（confidence≥0.7 + `_GENERIC_ENTITY_STOPWORDS` 40 词 + relation 端点有效性）；hyper-extract AutoGraph 输出**无 confidence 字段**，适配层直转会丢质量门，中文停用词问题重现。

**修订**：4.1 适配层转换后**追加过滤层**：
- 复用 `_GENERIC_ENTITY_STOPWORDS`（中文停用词，跨 backend 共享，提取到公共模块）
- relation 端点有效性校验（source/target 须在 entities 中）
- confidence 由「LLM 显式字段」改为「模板 guideline + 引擎去重（itext2kg_star SemHash）」隐式保证；若需显式阈值，he 路径配置 `he_confidence_fallback`（默认放行，靠引擎质量）

### 11.4 🔴 致命 4：Phase 2 超图与 Phase 1 实体类型路由冲突

**问题**：Phase 1 把实体路由到 person/org/... 细分 vertex label；Phase 2 超图 `member_of(relation_group → entity)` 边的 target label 在 HugeGraph 中**强类型固定**，无法同时指向多种细分 label——与 Phase 1 路由直接打架。

**修订**：5.1 超图 schema 细化，二选一（实施前先验证 HugeGraph 多 label 能力）：
- **方案 A（推荐）**：`member_of` 的 target 用通用 `entity` label。实体双写——细分 label（person/org/...）+ 通用 entity label 投影，member_of 指向 entity。需确认 HugeGraph 是否允许一个 vertex 多 label；若不允许，回退为 entity label + type property（放弃细分 label 路由，回到 Phase 1 前状态）。
- **方案 B**：为每种细分 label 建独立 member 边（member_of_person / member_of_org / ...），schema 膨胀但类型严格。

**约束**：Phase 1 实体路由策略（4.5）必须与 Phase 2 此决定对齐。

### 11.5 🟡 次要点（记录，实施时处理）

5. **KG extractor 工厂位置**：`_lake_kg.py` 已不存在，实施首步用 `search_graph` 重新定位 Lake facade KG mixin。
6. **并发模型测算**：`to_thread`(build_concurrency) × `parse`(max_workers=10) 可能线程爆；实施时单测峰值线程数，必要时降 parse 内层并发。
7. **关系评测 gold**：`entity_gold_standard.json` 只测实体不测关系，补关系 gold 标准，否则「三元组精准度」关系侧无量化基线。

### 11.6 修订后的 Phase 1 实施顺序


**结论**：智谱 GLM-4-Plus 的正确用途是 **legacy KG 主力 provider**，而非 he_model 备选。he backend 继续用 qwen3/Ollama。
