深模块

七个候选,一个统一的根因。横跨 RAG、KG 与 Lake facade,同一个形状反复制造 bug: 配置与知识以位置参数在浅模块之间手工转发,而把它们串起来的编排逻辑 没有测试——只有被抽出来的纯函数有。v1.9.5/v1.9.6 反复出现的 "dead config"、"fire-and-forget GC"、 "host 与 container 分歧" 不是编码疏忽,而是这个形状的可预见产物。

横切关注点 · 测试的形状

纯函数有测试,连接它们的布线没有。verifier.verify()、 query_transform、reranker._parse_score 都有扎实的单测—— 但把它们接起来的调用点(getattr(config,"enable_verification",False)、异步扇出、 iscoroutine 桥接、facade→TaskManager→builder 的派发)一个测试都没有。测试断言了 top_k 到达 retriever,却从不断言 strategy。深化能从结构上修掉它: 接口即测试面,行为在调用者真正穿越的那条缝上一次断言到位。

改造后 · 一个深的 RetrievalStage

问题

"按 strategy 检索、排序、装配 context 窗口"被切成两个浅模块,靠一个把 strategy 当位置参数走私的回调连起来——于是每个旋钮都要手工转发 6 次。

方案

一个深的 RetrievalStage 拥有 retrieve(plan) → RankedWindow;一次解析 RAGQueryPlan,作为数据下发,而非 N 个参数。

  • · 局部性:dead-config 这一类在源头消亡
  • · 杠杆:一个接口,router + SDK + graph 路径共用
  • · 消灭 _score/_rrf_score 列耦合
  • · 测试打在一条缝上,而非 6 跳

2 · 把控制面做成构造器 port

强烈推荐 端口与适配器

arrow_lake/__init__.py:100,331 · arrow_lake/api/app.py:163,219,232 · arrow_lake/api/deps.py:18 · arrow_lake/config/system_db.py:29

改造前 · 持久化是运行期属性

改造后 · ControlPlane port,两个 adapter

问题

持久化成了隐藏的运行期属性——三个 mixin 里都用 getattr(self,"_…_store",None) 探测——于是 host 的 Lake() 静默退化,写出的 dataset 容器看不见。

方案

在 __init__ 注入 ControlPlane port;NullControlPlane 与 LibSQLControlPlane 正是证明这条缝合理的两个 adapter。

  • · 局部性:能力检查集中在一个构造器
  • · host-vs-container 404 变成响亮报错
  • · 对齐并正式化 v1.9.0 控制面拆分
  • · store 作为契约变得可测
ADR 提示。ARCHITECTURE.md §3 把 "Facade + Mixin" 定为既定哲学。本候选保留 facade 并深化它——mixin 的作者划分不变,但控制面从 "事后钉属性" 变成注入的 port。值得重开 §3,把这条 port 显式写下来。

3 · 拆分 _lake_kg 胖接口

强烈推荐 进程内

arrow_lake/_lake_kg.py(1571 LOC · 40 方法) · knowledge_graph/builder.py · knowledge_graph/client.py

改造前 · 一个 mixin,五个职责

改造后 · 薄 facade + 3 个深模块

问题

40 方法的 mixin,其中 42% 是纯透传,而真正的行为(build 派发、GraphRAG 引擎)却待在错误的家,旁边挤满 workaround。

方案

沿三条缝拆:派发→KGBuilder、聊天→KGRagEngine、运维→HugeGraphLifecycle;17 个 wrapper 折成 2 个。

  • · 局部性:build 派发挨着它拥有的任务态
  • · 接口:40 方法 → ~12
  • · fire-and-forget GC 有了测试的家
  • · 杠杆:一个派发,REST + SDK + CLI 共用

改造后 · 一个深的摄入方法

问题

HTTP 层手搓 embed→FTS→vector→Gravitino→cache 流水线(还在 async_tasks 里重复一遍)——于是 SDK 调用方拿到的产品比 HTTP 调用方还差。

  • · 杠杆:SDK 与 HTTP 能力对齐
  • · 删掉重复的 blob-key 解析
  • · 接口收缩;facade 吸收编排

deploy/scripts/entrypoint-hugegraph.sh · knowledge_graph/client.py:103,356,467 · _lake_kg.py:31,670 · knowledge_graph/queries.py:3

改造前 · 运维知识散在 4 处

改造后 · 一个 adapter 把 HugeGraph 当系统管

问题

运维知识(幽灵清理、drop 后 restart、gremlin 绑定、后端特定 REST)一半在 196 行 shell 脚本里,一半在 Python workaround 里——两半从不互相引用。

  • · 部落式的 shell 知识有了契约
  • · 一条缝可对 fake 测试

改造后 · 一个模板,一个钩子

sequenceDiagram

  participant B as Base.query(模板)
  B->>B: messages + retrieve + window
  B->>GR: _augment_context(window)

  GR-->>B: 增强后的 context 文本

问题

GraphRAG.query 端到端覆盖基类,复制了消息构造/响应/会话保存——已经漏了一个镜像(save_turn)。

方案

基类 query() 变模板方法,带一个空操作 _augment_context 钩子;GraphRAG 只覆盖这个钩子——~120 LOC → ~40。

  • · 局部性:parity bug 结构上不可能
  • · 杠杆:一条 message/响应路径
  • · session + verify 两个 pipeline 各跑一次
  • · 接口缩到一个钩子

7 · reranker 这条缝上统一 async 契约

强烈推荐 进程内

arrow_lake/rag/reranker.py:42,180,300,317 · arrow_lake/rag/pipeline.py:257 · arrow_lake/query/hybrid.py:290

改造前 · 缝上契约未定义

改造后 · 基类 async,一条规则

问题

基类声明 def rerank,但两个 adapter 偷偷用 async def 覆盖;调和规则活在每个调用方里——第二个调用方已经搞错了。

方案

基类声明 async def rerank;sync adapter 直接 return。删掉每个调用方的桥接;hybrid.py:290 的潜伏 bug 顺手消失。

  • · 局部性:一条契约,一处
  • · 消灭 hybrid.py 潜伏的静默 Noop
  • · 缝保留——4 个真 adapter ✓
  • · 七者中 effort 最低

首推

先做 #1 —— 深化 RAG 检索阶段

↑ 回到卡片

它是本组里最纯粹的深化:两个浅模块合并到一个小接口背后,配置一次解析成 RAGQueryPlan,而非手工转发 6 次。它自包含(单子系统、爆炸半径适中), 是 接口即测试面 最干净的范例,并且恰好消灭了最伤这个仓库的 bug 类——dead strategy、dead reranker、 _score/_rrf_score 列耦合——正是 v1.9.5/v1.9.6 反复咬人的那些。 检索后端属于本地可替换,所以深化后的模块可对 stub 干净测试,无需真实 LanceDB。

若想要更大的结构改造:候选 #2(ControlPlane port)是 host-vs-container 分歧与 "配置到不了模块"反复出现的根因——但它触及整个 facade,爆炸半径更大。 若想要最便宜的胜利:#7(reranker 一条 async 契约)改一个签名,顺手删掉 hybrid.py:290 里一个潜伏的静默 Noop。
