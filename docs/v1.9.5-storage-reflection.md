# v1.9.5 存储反思:MinIO 使用方式与 Lance 放置策略

> 状态:反思沉淀(已 review,核实关键事实)
> 关联:[v1.9.5 RAG 质量规划](v1.9.5-rag-quality-plan.md) 批 6
> 起因:疑问「Lance 格式文件是否不宜放 MinIO、影响性能,只放原始上传文件?」

---

## 0. 结论先行

**Lance 留在 MinIO,不要挪本地——这是正确架构,挪了是倒退。** 「Lance 不宜放对象存储」这个前提
**不成立**:Lance 就是为对象存储设计的列式格式,放 MinIO 是它的主场。项目现有的存储分层
(HugeGraph/libSQL 放本地、Lance 放对象存储)已经体现了正确的「按访问模式选存储」原则。
真正的性能优化点是开 Lance 本地读缓存 + 修 RAG 走向量,而不是改存储位置。

---

## 1. MinIO 在系统中的使用方式(全量盘点)

| # | 用途 | 路径/前缀 | 客户端 | 性质 |
|---|---|---|---|---|
| 1 | **Lance 数据湖**(主数据面) | `s3://arrow-lake/{dataset}/...` | Lance Rust object_store | 查询热路径 |
| 2 | **原始上传文件** | `s3://arrow-lake/uploads/{ds}/{uuid}_{file}` | BlobStoreManager(boto3) | 溯源/重解析,非热路径 |
| 3 | 备份/恢复 | 同 bucket | BackupManager→BlobStoreManager | 运维 |
| 4 | Gravitino fileset | `s3://...`(s3.* 属性) | Gravitino | 治理元数据,非热路径 |
| 5 | Metaflow 工件 | `s3://...` | metaflow S3 | 流程工件 |

关键事实:
- **Lance 表与原始文件同处一个 bucket `arrow-lake`**,仅靠前缀隔离(`{dataset}/` vs `uploads/{ds}/`)。
- `base_uri` 被直接设成 bucket 名(`compose: BASE_URI="${MINIO_BUCKET:-arrow-lake}"`),`s3_uri` 拼成
  `s3://{bucket}/{base_uri}`(`config/storage.py:101`)。
- 原始文件上传有两条路径:`POST /{name}/upload`(经 API)与 `POST /{name}/upload/presign`(直传 MinIO)。

## 2. Review 新发现:项目已有正确的存储分层(强佐证)

核实 `deploy/docker-compose.prod_minimal.yml`,系统其实**已按访问模式分层**:

| 数据 | 存储位置 | 为什么这么选 |
|---|---|---|
| **HugeGraph**(图遍历) | 本地卷 `hg-server-data:/var/lib/hugegraph`(rocksdb) | 高频随机遍历,本地 NVMe 直读最快 |
| **libSQL system-db**(控制面) | 本地卷 `system-db-data:/var/lib/sqld` | RBAC/会话/任务高频读写,延迟敏感 |
| **KA dump**(hyper-extract) | 本地 `/data/ka` | `ka.dump` 写本地 FS,不写对象存储 |
| **导出落盘** | 本地 `/data/lake/exports` | 异步写,read-only 根 FS 下需持久可写卷 |
| **Lance 数据湖** | **对象存储 MinIO** | 大规模列式 + 多节点共享 + 弹性容量 |
| **原始上传文件** | **对象存储 MinIO** | 大文件归档,非热路径 |

**这恰恰证明 Lance 放 MinIO 不是疏忽,而是与 HugeGraph 放本地同一套原则的体现**——按访问模式选存储。
图遍历/控制面走本地,列式数据湖走对象存储,这是业界湖仓标准分层。

## 3. 核心判断:为什么「Lance 不宜放 MinIO」不成立

Lance 的设计目标之一就是「云原生、对象存储友好」:

| Lance 特性 | 为什么对对象存储友好 |
|---|---|
| append-only fragments | 写时只追加新文件,不重写旧文件 → 避免对象存储最怕的「读-改-写」放大 |
| manifest 精确定位 | 随机读直接寻址 column chunk,零拷贝 → 向量检索 random access 比 Parquet 快 |
| 不可变文件 + 版本 | 天然契合对象存储语义 |
| 官方一等支持 | LanceDB 原生列 S3/GCS/Azure/MinIO,IVF_PQ 在 S3 上是卖点 |

**对比**:若是 Parquet 放 MinIO 做向量检索,那确实性能差(随机读要拉整 row group)。但 Lance 不是
Parquet——它就是为了解决「列式 + 对象存储 + 随机读」而生。

**本项目实际场景**:minio 与 api 同机,走 docker loopback(~0.1ms),数据量未到海量。对象存储延迟
主要来自 list manifest + SigV4 签名 + HTTP 建连,单机 loopback 下**不是瓶颈**(多轮 RAG 跑通即证)。

**挪本地会丢掉**:多节点共享、弹性容量、MinIO 成熟的备份/一致性、bucket 级迁移。换来的是省一点
loopback 开销——**得不偿失**。

## 4. 真正的性能优化点(核实后有效)

### ✅ 4.1 开 Lance 本地读缓存(快赢,已验证生效)

- 现状:`lance_cache_size=0` 默认关(`config/storage.py:51`)。
- **已核实生效**:`ingest/storage.py:416-417` 把它传进 `lance.dataset(lance_uri, cache_size=...)`
  ——pyarrow/lance 的 page cache,缓存最近读取的 column chunk,对向量随机读直接有效。
- 动作:`ARROW_LAKE__STORAGE__LANCE_CACHE_SIZE=1073741824`(1GiB)。
- **这是唯一的本地缓存杠杆**(grep 确认除 cache_size 外无 prefetch/readahead 机制)。

### ✅ 4.2 修 RAG 走向量/hybrid(见规划批 1)

这才是「回答简单」的真凶,与存储位置无关。

### 🟡 4.3 Lance 表与原始文件分 bucket(可选,隔离)

- 现状:同 bucket 不同前缀。`BlobStoreManager` 已支持指定 bucket(`blob_store.py:100` 的 `bucket` 参数)。
- 收益:IO/配额/生命周期独立。原始文件可设单独过期策略(如 30 天转低频),它不在查询热路径。
- 改动:新增 `arrow-lake-uploads` bucket,blob_store 构造时传入;数据面 bucket 不变。

### 🟡 4.4 minio 内存

给 minio 容器足量内存,它自身会缓存热对象。compaction 已开(`maintenance_enabled=true`)。

---

## 5. 什么时候才该把 Lance 放本地(反向条件)

需**同时满足**才考虑:
1. 确定单机部署、永不扩展多节点;且
2. 对延迟极致敏感(在线检索 <10ms 级);且
3. 数据集规模本地盘装得下。

**本项目当前不满足**——目标是湖仓 + 多数据集 + RAG + 可能多节点,Lance 留 MinIO 是对的。
即使将来要降延迟,也优先走 4.1(缓存)+ 4.2(向量检索) 路线,而非迁移存储。

---

## 6. 原始上传文件的放置结论

**原始文件该留 MinIO**,但与 Lance 表分开管理:
- 它是溯源/重解析(换 docling 重跑)的依据,放对象存储合理。
- 不在查询热路径,可设**生命周期规则**(30 天后转低频存储/或定期清理)。
- 建议分 bucket(4.3),便于独立的生命周期与配额管理。
