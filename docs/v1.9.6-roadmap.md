## 🔴 P0(生产关键,必做)

### P0-1 RAG 防幻觉(引用校验 / faithfulness verify)
- **现状**:`pipeline.py:296-360` 生成后零校验;`_extract_citations` 只包 chunk 元数据,**citations 与答案文本零映射**;prompt 口头要求「标 [n]」无强制。
- **方案**:接入点 `pipeline.py:333`(generate 后)。轻量版:正则提 `[n]` 校验编号 + 答案句 embedding vs chunk cosine(阈值 0.6 标 unsupported,复用 extract_llm embed 零额外服务)。完整版:LLM judge(extract_llm 单次调用,逐句 vs context,返 support_ratio)。`RAGResponse` 加 `verification` 字段 + `enable_verification` 开关。
- **工作量**:M(轻量 S)| **ROI**:高 | **代码**:`arrow_lake/rag/pipeline.py:333`

### P0-2 Reranker 默认切 cross-encoder
- **现状**:`CrossEncoderReranker` **已实现**(`reranker.py:67-138`,bge-reranker-v2-m3 连续分),但默认 `"ollama"`(binary yes/no,粒度粗)。
- **方案**:默认切 `cross-encoder` + 加 `reranker_device`(auto/cuda/cpu)+ `reranker_warmup_on_init`(构造后 predict warmup)+ 部署预下载 HF 模型(`hugging-cli download BAAI/bge-reranker-v2-m3`)。
- **工作量**:S | **ROI**:高(连续分排序显著提升)| **代码**:`_lake_rag.py:112` / `reranker.py:67` / `config/rag.py:82`

### P0-3 KG 抽取质量(模板收紧)
- **现状**:模板已有 type/relation 枚举 + definition 必填,但 `_get_type_enum`(`he_extractor.py:438`)正则解析 YAML description 脆弱;snap 非枚举值粗暴塌缩「实体」丢分类;空 definition 仍入图。
- **方案**:YAML 加显式 `enum: [...]` 字段(替正则,向后兼容)+ snap 用编辑距离归一化(「架构组件」→「组件」)+ strict 模式过滤空 definition + 抽 `_parse_enum_from_yaml` util 去重。
- **工作量**:M(2-3d)| **ROI**:高(直接决定 KG 质量)| **代码**:`he_extractor.py:438-522` / `templates/*.yaml`

### P0-4 GraphRAG 并行化 + KA 缓存
- **现状**:`_graphrag_retrieve`(`_lake_kg.py:940`)三步串行(vector 原文 + search_ka + neighbor);`load_ka_for_query` 每次磁盘 reload KA(60s+);QuestionEntityCache process-local。
- **方案**:`asyncio.gather` 三路并行(延迟 -40~50%)+ `HyperExtractExtractor` 加 `LRU[dataset→KA]`(按 dump mtime 失效)+ `time.monotonic()` 替 `time.time()`。
- **工作量**:S-M(1-2d)| **ROI**:高(首字节延迟砍半)| **代码**:`_lake_kg.py:940` / `he_extractor.py:280` / `graph_rag.py:31`

### P0-5 血缘可视化(console/lineage.html)
- **现状**:后端全就绪 — `LineageStore`(Lance 持久)+ `trace_upstream/downstream/full_graph` + `/api/v1/lineage/graph/{ds}?format=mermaid|dot|json`(`lineage.py:97`)+ libSQL 加速 + Gravitino 双向同步。**console 零消费**(仅 docs 原型)。
- **方案**:新增 `console/lineage.html`,mermaid.js 渲染(最快 2d)或 vis-network/cytoscape 交互式(4-5d,节点折叠/列级展开)。`trace_full_graph` 加 `max_nodes` 截断防 OOM。
- **工作量**:S-M(2-5d)| **ROI**:**极高**(后端全就绪,纯前端,旗舰治理功能)| **代码**:`api/routers/lineage.py:97` / 新 `console/lineage.html`

### P0-6 脱敏 4 函数暴露 + HMAC 强制 + audit
- **现状**:`MaskingEngine`(`masking_engine.py`)支持 redact/hash/partial/nullify 4 函数,但 `gravitino_policies.create_masking_policy` **写死 redact**(`:88`),governance.html 无函数选择;HMAC key 缺失静默回退 nullify(合规隐患);无脱敏审计日志。
- **方案**:`create_masking_policy` 加 `function` 参数 + governance.html 4 选 1 下拉 + 预览;HMAC key 启动校验(可 opt-in insecure);masking 应用写 audit 表。
- **工作量**:S-M(2-3d)| **ROI**:高(合规必需,低投入)| **代码**:`quality/gravitino_policies.py:88` / `quality/masking_engine.py:160`

## 🟧 P1(质量/体验/可用性)

### P1-1 DuckLake 物化视图持久化
- **现状**:`ducklake_workspace.py:225` `_metadata` 表 TEMP/session-scoped → 跨会话 `list_views` 返空,**MV 无生命周期管理**(基本是 demo)。
- **方案**:`_metadata` 落持久 catalog 表 + maintenance 周期触发 cleanup/stale 重建。
- **工作量**:M(1-2d)| **ROI**:高(BI 场景必需)| **代码**:`query/ducklake_workspace.py:225`

### P1-2 system_db HA(备份/embedded replica)
- **现状**:`system-db` 单容器单卷(`prod_minimal.yml:161`),挂 → 全控制面失败;默认 `SYSTEM_DB_ENABLED=false`。
- **方案**:短期 volume 定时快照(litestream/mc);中期 libsql embedded replica(每 worker 本地 file: + 异步 sync);长期 sqld 多副本。
- **工作量**:S-M(0.5-3d)| **ROI**:高(单点风险)| **代码**:`system_db/connection.py` / `prod_minimal.yml:161`

### P1-3 docling GPU 验证 + 接线
- **现状**:`Dockerfile.gpu` 装 cu124 torch,但 docling 调用点未显式 `AcceleratorOptions(device="cuda")`;CPU 跑大 PDF 慢(AIGC 7.9M 等 10min+)。
- **方案**:GPU 镜像跑 109 页 PDF 测速(CUDA_VISIBLE_DEVICES 对比)+ docling 调用点接 `AcceleratorOptions` + 构建期 `torch.cuda.is_available()` 校验。
- **工作量**:M(2d)| **ROI**:高(5-10× 加速,docling 可日常用)| **代码**:`Dockerfile.gpu:48` / `ingest/document.py`

### P1-4 KG 增量 API 暴露 + orphan 清理
- **现状**:`build_dataset_ka(incremental=True)` 完整实现(fed_chunks sidecar hash),但 API `/kg/build` 默认 `incremental=False`;删 chunk 的 orphan 顶点不清理。
- **方案**:路由加 `?incremental=true` + 增量后 diff → 批量删 orphan 顶点。
- **工作量**:S-M(1-3d)| **ROI**:中(大 dataset 增量省时)| **代码**:`routers/knowledge_graph.py:114` / `he_extractor.py:707`

### P1-5 KG 联邦查询(跨数据集)
- **现状**:per-dataset `kg_{ds}` 完全隔离,无跨图查询;Vermeer OLAP(pagerank/louvain)无 dataset_name 参数。
- **方案**:`kg_federated_query(query, datasets=[...])` 客户端 fan-out 并行 + 合并去重 + Vermeer 补 dataset_name。
- **工作量**:M(2-3d)| **ROI**:中-高(跨数据集洞察)| **代码**:`_lake_kg.py` / `knowledge_graph/client.py`

### P1-6 Gravitino SDK 1.3.0 Phase B 验证
- **现状**:server 1.3.0 + SDK 1.2.1(REST 兼容);Table ops 手搓 urllib(`gravitino_bridge.py:255`);masking policy `associate_policies` 可能与 1.3.0 不符。
- **方案**:验 SDK 1.3.0 `create_multiple_location_fileset`/`associate_policies` 签名 → 迁 Table ops 到 SDK + lineage 同步重试/对账。
- **工作量**:L(4-6d)| **ROI**:中-高(解锁治理深化)| **代码**:`catalog/gravitino_bridge.py:255`

### P1-7 image search 产品化
- **现状**:`image_search_demo.py` E2E 验过(CLIP 文搜图/以图搜图),但 host/容器 catalog 分歧 + 容器缺 CLIP + 无 console 入口。
- **方案**:统一 host/容器 catalog(共享 system-db)+ 容器镜像内置 CLIP + search.html 以图搜图链路。
- **工作量**:M(2-3d)| **ROI**:中-高(打通产品最后一公里)| **代码**:`examples_image/` / `console/search.html`

### P1-8 console/showcase.html 旗舰页
- **现状**:19 页功能分散,缺串通 ingest→KG→RAG→检索→治理→血缘的演示页。
- **方案**:新增 `console/showcase.html`,一页串核心能力 + 数据回流动画。
- **工作量**:M(3-5d)| **ROI**:中-高(演示/获客)| **代码**:新 `console/showcase.html`

### P1-9 RAG 流式补 citations/latency 帧
- **现状**:`query_stream`(`pipeline.py:362`)只流 text,丢弃 window(citations/latency/context_tokens)→ 前端流式无溯源。
- **方案**:yield tagged union 或 SSE 多事件(首帧 citations + content + 末帧 latency/verification),与 P0-1 verify 协同。
- **工作量**:S | **ROI**:中 | **代码**:`pipeline.py:362` / `routers/rag.py:110`

### P1-10 RAG parent-chunk 邻居扩展(docling 500 chunk 配套,升级)
- **docling 经验沉淀**:docling HybridChunker 默认 ~500 token(`_get_docling_hybrid_chunker` 不传 chunk_size),是 docling 反复实践沉淀的合理值(结构感知切分 + token budget 平衡),**不调**。DocumentChunker.chunk_size(批4 改 1200 字符)只对 kreuzberg/jsonl 路径;docling 走 HybridChunker(token),单位不同不该共用。
- **为何 parent-chunk 必要**:docling 500 token chunk 信息密度适中但**跨 chunk 上下文断裂**(如「143 亿」数据可能在相邻 chunk);parent-chunk 扩展补全前后邻居,提升单片段完整性。这是 docling 500 配套的必要补全(非调大 chunk_size)。
- **现状**:Chunk 有 chunk_index(BTREE 索引)但 ContextChunk 不透传;KG 有 next_chunk 边但检索未复用。
- **方案**:`table_to_chunks` 透传 document_id+chunk_index,rerank 后对 top-N 扩前后 chunk(`WHERE document_id=? AND chunk_index IN(i-1,i,i+1)`)。纯检索侧,不改摄入。
- **工作量**:M | **ROI**:**中-高**(docling 500 chunk 跨段断裂常见,扩展直接提升答案完整性)| **代码**:`context.py:56,274` / `pipeline.py:212`

### P1-11 RAG 查询分解(DecomposeTransformer)
- **现状**:`query_transform.py` 有 HyDE/multi_query(同义改写,不拆维度);并行检索基建就绪。
- **方案**:加 `DecomposeTransformer`(LLM 输出子问题数组)+ 复用并行检索 + map-reduce 合成。
- **工作量**:M(合成策略)| **ROI**:中(复杂多面问题)| **代码**:`query_transform.py:115`

## 建议 v1.9.6 落地(一个迭代)

按 ROI + 协同,建议聚焦 **P0 全 6 项**(都已验证后端就绪或高 ROI):

| 批 | 项 | 工作量 | 理由 |
|---|---|---|---|
| **批1** | P0-1 防幻觉 + P0-2 reranker cross-encoder + P1-9 流式补帧 | S-M | RAG 质量闭环(检索→连续分重排→生成→流式带引用→faithfulness 校验) |
| **批2** | P0-3 KG 抽取质量 + P0-4 GraphRAG 并行化 | M | KG 质量 + 性能双提升 |
| **批3** | P0-5 血缘可视化 + P0-6 masking 4 函数 | S-M | 兑现已沉没后端成本(后端全就绪),旗舰治理 + 合规 |

**P1 选做**(按需):docling GPU(P1-3,兑现 GPU 投资)/ system_db HA(P1-2,若转 enabled=true)/ DuckLake MV(P1-1,BI 场景)。

**P2/P3 留后续版本**(v1.9.7+ 或上线前批次)。

## 关键洞察(4 Agent 评估共识)

1. **后端就绪、前端未消费**:血缘(mermaid/dot/json 全有)+ masking(4 函数引擎全有)→ console 零消费。**P0-5/P0-6 是最高 ROI**(4-6 人天兑现沉没成本)。
2. **RAG 质量闭环缺口**:reranker 已实现但默认未用 + 无 faithfulness 校验 + 流式丢引用 → **批1 三项协同**形成完整质量链。
3. **KG 双重瓶颈**:抽取质量(模板 snap 粗糙)+ GraphRAG 性能(三步串行)→ **批2 两项**质量+性能双升。
4. **运维单点**:system_db + docling CPU + 监控缺失 → 上线前必修(P1-2/P1-3/P2-2)。
