## 三、方案 A:provenance + value + aliases 三字段

### A.0 核心洞察(决定实现成本)

- **source_chunk 数据已在 builder 手里**:`_insert_kg`(builder.py:764)的 `owning_chunk_id`(per-chunk path)+ `entity_chunks: name→[chunk_id]`(per-dataset/map_reduce path)就是 provenance,只是当前没写进 entity vertex property。**零额外抽取成本**。
- **value/aliases 走与 `definition` 完全相同的模式**:`_insert_kg` L804 已有 `dict(e.properties).get("definition","")` —— `e.properties` 来自 LLM 返回(extractor.py:56 entity schema 已含 `properties` dict)。加 value/aliases = 模板 `entities.fields` 让 LLM 抽 + `_insert_kg` 从 `e.properties` 取 + schema 注册 property key,三处一致改动。

## 四、方案 B:Leiden 社区检测 + 社区摘要 + 社区路由

### B.0 能力定位(为什么需要、边界在哪)

map-reduce(AutoGraph 二元 + entity_resolver)解决"高效率+高质量",但**不内建层次化检索**:plain graph 无社区结构,大图(>10k 顶点)问答时 retriever 拿到的是平铺的 kneighbor 子图,无法先路由到主题社区再细化。社区检测给图加一层"主题分区",让 RAG 查询能"先选社区、再展开子图",逼近 graph_rag 的层次化质量,**而不换引擎、保留 map-reduce 的高效率**。

**边界**:社区检测是 **build 期 offline 计算**(一次性,不在查询热路径);社区路由是查询期只读社区归属。不引入串行 feed_text(graph_rag 的慢根源)。

### B.1 依赖选型(三档)

| 选项 | 包 | 体积 | 算法 | 建议 |
|------|----|----|------|------|
| **MVP** | `networkx`(纯 Python) | 轻 | `community.louvain_communities()` / `greedy_modularity_communities()` | **批2 首选**:零额外重依赖,networkx 本就常作为图工具基础;Louvain 是 Leiden 的前身,质量接近 |
| 精专 | `leidenalg` + `igraph` | 中(C 扩展) | 真正 Leiden | 质量最优时升级;igraph 需 C 编译,镜像构建注意 |
| 重 | `graspologic` | 重(拉 sklearn/scipy/stats) | HierarchicalClusterer(Leiden) | 不建议,依赖膨胀 |

**决策**:批2 用 **networkx 内置 Louvain**(零额外依赖,networkx 已是社区检测事实标准库,加它一个包);若 wuhu 实证社区质量不足,再升 `leidenalg`。文档名仍称"社区检测",代码注释说明算法可替换。

pyproject.toml:

```toml
[project.optional-dependencies]

```

### B.2 社区检测模块(新)

`arrow_lake/knowledge_graph/community_detector.py`(纯逻辑,embedder/LLM 注入,可单测):

```python
def detect_communities(
    vertices: list[dict],          # HugeGraph entity 顶点快照 [{id, properties:{name,type,...}}]
    edges: list[dict],             # HugeGraph 边快照 [{outV, inV, label, properties}]
    *,
    resolver=None,                 # 可选:用 entity_resolver 合并后再分区(已消歧)

```

- networkx 建无向图(关系双向都算邻接),`community.louvain_communities(G)` 返回社区划分。
- `Community(comm_id, member_names: list[str], member_count)`。

### B.3 社区存储(存 HugeGraph,贴合现有架构)

schema.py 追加:

```python
PropertyKeyDef("summary", "TEXT", "SINGLE"),       # 社区主题摘要(LLM 生成)
PropertyKeyDef("member_count", "INT", "SINGLE"),
PropertyKeyDef("comm_id", "TEXT", "SINGLE"),       # 社区编号(路由用)
# 新 vertex label:
VertexLabelDef("community", ("name", "summary", "member_count"), ("name",),
               nullable_keys=("summary", "member_count")),
# 新 edge label:entity → community
EdgeLabelDef("member_of", "entity", "community", ("comm_id",)),
```

build 流程(map_reduce INSERT 之后)追加一步 `detect_and_store_communities`:

1. `client.get_vertices(graph, label="entity")` + `get_edges` 拉快照(复用 `_cached_graph_snapshot` 机制)。
2. `detect_communities(...)` → Community 列表。
3. 每个 Community:LLM 生成 `summary`(复用 he LLM client,输入成员 name+type+definition),`add_vertices(label="community")` + 每个成员 `add_edges(member_of)`。

**配置**(`HugeGraphConfig`):

```python
he_community_detection: str = "off"    # off | auto(默认 off,大图 opt-in)
he_community_min_size: int = 3
he_community_max_summary_chars: int = 200
```

`auto` = 顶点数 ≥ 阈值(如 1000)时自动开;小图 skip。避免小图无谓 LLM 成本。

### B.4 社区路由(查询期,两条 QA 路径分别接)

**路径1:RAG `/rag/query?use_kg=true`** — `retriever.py:retrieve`(L53):

```python
async def retrieve(self, question, *, extracted_entities, ...):
    # 现状:entity → kneighbor → triplets
    # 增强:先尝试社区路由
    if self._config.he_community_detection != "off":
        community = await self._route_to_community(extracted_entities, graph_name=g)
        if community:
            # 取社区全成员 + 成员间内部边,作为子图(比 kneighbor 更完整)
            triplets = await self._community_subgraph(community, graph_name=g)
            # 不够再补 kneighbor
    # fallback:现有 kneighbor 路径
```

`_route_to_community`:取 extracted_entities 命中的 entity → 沿 `member_of` 找所属社区 → 返回社区。若多实体跨社区,取成员最多的共同社区或合并。

**路径2:kg.html 问答** — `_lake_kg.py:_build_neighbor_context`(L111):

在 anchor 命中后,追加该 anchor 所属社区的 `summary` 作为主题上下文:

```python
# _build_neighbor_context 返回的 anchor dict 追加:
community_summary = comm_id2summary.get(comm_of_anchor)
out.append({... , "community": community_summary})
```

`_augment_question_with_graph` 渲染时加一行"【所属主题】{community_summary}"。

### B.5 顺带修:retriever predicate 压扁(C,批1 落地)

`retriever.py:retrieve` L128 `predicate = f"related_to_{n_label}"` 丢了 relation_type。memory `issue_graphrag_quality_isolated_vertex` 标注的遗留。修法:

- `traverser_kneighbor` 只返顶点不返边 → 需加 `client.get_vertex_edges(vid, graph_name=g)`(REST `GET /graphs/{name}/graph/edges?vertex_id="..."`)。
- 拿到边后取 `properties.relation_type or label`,与 `_lake_kg.py:147` 同源逻辑。

**为什么放批1**:社区路由接 retriever 时三元组必须有语义,否则社区子图也是一堆 `related_to_entity`。C 是 B 的前置。
