# v1.9.5 RAG 问答质量提升规划

> 状态：设计稿（待 review 确认后实施）
> 起点：v1.9.4（commit `e770e09`）
> 触发：文档解析 + chunk + RAG 问答已跑通，但实测回答「比较简单」，反思提升空间

---

## 0. 背景与问题

文档摄入 → 分 chunk → 建索引 → RAG 问答全链路已通。但连续几轮问答，回答内容偏「简单」：
单薄、缺细节、不带结构、不引用来源。本规划做一次端到端反思，定位真实根因，给出分批
可落地的提升方案。

**审视范围**：`arrow_lake/rag/`（pipeline / context / prompt / reranker / query_transform /
graph_rag）+ `_lake_rag.py` + `_lake_search.py` + `config/rag.py` + `ingest/chunker.py`。

---

## 1. 根因诊断（按严重度排序）

### 🔴 P0-0 ｜ RAG 默认走纯 FTS，向量索引根本没接进 pipeline（最严重，第一轮反思漏掉）

**证据链**：

| 环节 | 代码 | 实际行为 |
|---|---|---|
| RAG retriever | `_lake_rag.py:142` `_rag_retriever` → `self.text_search(...)` | 调的是 `text_search` |
| text_search 本体 | `_lake_search.py:195` → `FullTextSearchBridge` | **纯 BM25 全文检索 + jieba 分词**，docstring 明写 "Full-text search" |
| 死配置 | `config/rag.py:73` `default_retrieval_strategy="hybrid"` | pipeline 的 `strategy` 参数只用于选 score 列名（`_rrf_score` vs `_score`，见 `pipeline.py:221`），**从不传给 retriever** |
| 接口缺位 | `pipeline.py:70` `RetrieverFunc = Callable[[str,str,int], pa.Table]` | 签名里**没有 strategy 参数**，retriever 无从感知策略 |
| 能力闲置 | `_lake_search.py:370` `hybrid_search(query_vector, query_text)` | Lake 明明有 vector / hybrid 检索，**RAG 路径完全没用** |

**结论**：你以为在跑「向量 RAG」，实际默认跑的是**纯关键词检索**。花大力气建的 IVF_PQ 向量
索引在 RAG 问答里 0 参与。语义相关但字面不同的 chunk 大量漏召回 → context 缺料 → 回答简单。

**这是比 prompt 更根本的根因。不解决它，prompt 再好也是「无米之炊」。**

---

### 🔴 P0-1 ｜ QA 生成 prompt 极简

`arrow_lake/rag/prompt.py:50` 的 `default_qa` 模板全文：

```text
Answer the following question based on the provided context.
If the context does not contain enough information, say so.
Context: {{ context }}   Question: {{ question }}   Answer:
```

不要求详尽、不要求分点、不要求引用编号、不要求覆盖背景与结论。任何模型在此指令下都倾向
给 1-2 句话。

### 🔴 P0-2 ｜ 无 system_prompt

`config/rag.py:77` `system_prompt: str = ""`。`pipeline.py:128` 为空就不注入 system 消息。
**完全没有角色 / 语气 / 详尽度 / 输出格式约束。**

### 🔴 P0-3 ｜ QA 生成模型未配旗舰

两阶段 LLM 框架**已就绪**（`_lake_rag.py:37` 的 `qa_llm` 分流、`config/rag.py:96` 的 `qa_llm`
字段），但默认 `None` → 回退全局 `llm`。若全局是本地 `ministral-3:3b` 或 `qwen-turbo`，生成
能力天然有限。**已铺好路却没走，最可惜的一项。**

---

### 🟧 P1-1 ｜ 查询变换默认关闭

`query_transform: str = "none"`（`config/rag.py:86`）。`HyDETransformer` / `MultiQueryTransformer`
**代码全写好了**（`query_transform.py`），multi-query 还会并行多路检索 + 去重合并（`pipeline.py:215`），
但默认关。复杂 / 多 facet 中文问题单次原始检索召回不全。

### 🟧 P1-2 ｜ reranker 是 binary 评分

默认 `OllamaReranker`（`reranker.py:221`）用 Qwen3-Reranker yes/no judge，**只能给 1.0 / 0.0 /
0.5**（`reranker.py:344`）。大量相关 chunk 同分，精排区分度低。

### 🟧 P1-3 ｜ context 有引用标记但 prompt 没让模型用

`context.py:212` assemble 输出 `[1] text [2] text`，但 `default_qa` 没告诉模型用这些编号做引用。
标记白打。与 P0-1 配套修复。

---

### 🟨 P2 ｜ chunk 太碎

`chunker.py:141` `chunk_size=512`（**字符**），中文 ≈ 340 token/块。单 chunk 信息密度低，检索
片段零碎，LLM 拼不出有深度的回答。`chunk_overlap=64` 同步偏小。中文 RAG 业界常用 800–1500 字符。

---

### 🟦 P3 ｜ GraphRAG 未联动

KG 已按数据集建好（per-dataset HugeGraph），`GraphRAGPipeline` 注入逻辑完整（`graph_rag.py`：
实体抽取 → 三元组检索 → RRF 融合 → `graph_qa` 模板），但只有 `hugegraph.enabled=True` 才走
（`_lake_rag.py:44`）。没开 = 纯向量 RAG，**已建好的实体关系三元组 0 参与问答**。

## 2. Review 补充（第一轮之外的边角）

| # | 点 | 说明 | 归档 |
|---|---|---|---|
| 补-1 | FTS 索引需存在且新鲜 | hybrid 依赖 `_fts_segmented` 列 + tantivy 索引；documents 摄入集曾 FTS 不可见（v1.8.9 已修，见 memory `issue_ingest_documents_retrieval_schema`），混合检索前需确认目标数据集 FTS 索引已建 | 批 1 前置校验 |

## 3. 方案设计（分批，按依赖与 ROI 排序）

> 原则：**先修检索（有米），再修生成（巧妇），最后增强召回与 KG 联动。**
> 每批独立可验收，互不阻塞（批 4 依赖批 1 的 retriever 改动，但可同批落地）。

### 批 1 ｜ 🔴 检索纠偏：把 vector / hybrid 真正接进 RAG（P0-0）

**目标**：让 `default_retrieval_strategy` 真正生效，RAG 默认走 hybrid（向量 + FTS RRF）。

**改动清单**：

1. **`arrow_lake/rag/pipeline.py`**
   - 扩展 `RetrieverFunc` 签名，增加 strategy 透传：
     ```python
     RetrieverFunc = Callable[[str, str, int, str], pa.Table]  # (question, dataset, top_k, strategy)
     ```
   - `_retrieve()`（`:174`）把 `strategy` 传给 retriever。
   - `_retrieve_and_build_context()`（`:201`）用 `strategy or self._config.default_retrieval_strategy`
     作为生效策略（解决死配置）。

2. **`arrow_lake/_lake_rag.py`**
   - `_rag_retriever(self, question, dataset_name, top_k, strategy)` 按 strategy 分流：
     - `fts` → `self.text_search(...)`（现状）
     - `vector` → `self.embed_texts([question])` → vector_search
     - `hybrid` → `self.embed_texts([question])` → `self.hybrid_search(query_vector, question, ...)`
   - 复用已有的 `_get_component("hybrid"/"fts")` 缓存与 `embed_texts`。

3. **`arrow_lake/config/rag.py`**
   - `default_retrieval_strategy` 默认值保持 `"hybrid"`（现在才真正生效）。
   - 增加 `qa_temperature`（或复用 `qa_llm.temperature`），见批 3。

**前置校验（补-1 / 补-2）**：
- 目标数据集需已建 FTS 索引（`lake.create_fts_index(ds)`）+ 向量索引（IVF_PQ）。
- 摄入侧 vector 列名与 `hybrid_search` 的 `vector_column` 默认值对齐。

**验收**：
- 同一问题，strategy=hybrid 的 `retrieval_count` 与命中率显著高于 fts（语义相关 chunk 召回）。
- `_rrf_score` 列真实出现在 context chunks 上。
- 单元测试：mock retriever，验证 strategy 正确透传到 retriever 调用。

---

### 批 2 ｜ 🔴 生成引导：升级 prompt + system_prompt（P0-1 / P0-2 / P1-3）

**目标**：让模型在拿到好 context 后，产出详尽、结构化、带引用的回答。

**改动清单**：

1. **`arrow_lake/rag/prompt.py`** — 重写 `default_qa` 模板：

   ```text
   你是一名严谨的资料分析助手。请基于下方「参考资料」回答问题，遵循这些要求：
   1. 回答要详尽、有条理：先给结论，再展开背景、关键细节、数据/依据，必要时分点陈述。
   2. 每条事实性陈述都应在句末用 [n] 标注来源，n 对应参考资料编号（如 [1]、[3]）。
   3. 若参考资料不足以完整回答，明确指出「哪部分有依据、哪部分缺失」，不要编造。
   4. 若问题涉及多个方面，逐项覆盖，不要遗漏。
   5. 用专业、客观的中文表述。

   参考资料：
   {{ context }}

   问题：{{ question }}

   回答：
   ```

   - 同步升级 `graph_qa` 模板（KG 三元组场景，要求标注实体关系来源）。

2. **`arrow_lake/config/rag.py`** — 给 `system_prompt` 一个高质量默认值（非空），定义角色：
   - 角色：资料分析助手
   - 行为：基于 context、引用来源、不幻觉、中文专业
   - 可被 env 覆盖。

**验收**：
- 同一 context，新模板输出明显更长、带 `[n]` 引用、分点结构。
- 现有 prompt 单测（`tests/unit/rag/`）需同步更新模板快照。

---

### 批 3 ｜ 🔴 旗舰 QA 模型（P0-3 / 补-3）

**目标**：生成阶段独立用旗舰模型，框架已就绪，纯配置。

**配置（env，不改代码）**：

```bash
# QA 生成走百炼 qwen-max（框架已支持 qa_llm 分流）
export ARROW_LAKE__RAG__QA_LLM__PROVIDER=openai
export ARROW_LAKE__RAG__QA_LLM__API_BASE=https://dashscope.aliyuncs.com/compatible-mode/v1
export ARROW_LAKE__RAG__QA_LLM__API_KEY=<百炼 key>
export ARROW_LAKE__RAG__QA_LLM__MODEL=qwen-max
export ARROW_LAKE__RAG__QA_LLM__MAX_TOKENS=8192       # qwen-max 输出上限,给足空间不截断
export ARROW_LAKE__RAG__QA_LLM__TEMPERATURE=0.3      # 补-3：QA 偏低温更稳
# 抽取/重排仍走轻量全局 llm（或单独配 extract_llm=qwen-turbo）
```

**注意（踩坑预警，来自 CLAUDE.md 运维速查）**：
- 百炼（dashscope）**必须走代理**，不要放进 `NO_PROXY`，否则每 chunk 超时。
- `qwen-max` 只支持 `json_object`，不支持 `json_schema`（但 RAG 生成不用约束解码，无影响）。
- `qa_llm` 分流只作用于「生成」，reranker / KG 抽取仍用 `extract_llm or 全局 llm`。

**验收**：对比 qa_llm=None vs qwen-max，同问题回答深度 / 准确性 / 表达明显提升。

### 批 4 ｜ 🟧 召回增强（P1-1 / P2 / 补-4）

**目标**：召回更全、chunk 信息密度更高。

**改动清单**：

1. **开 multi_query 查询变换**（env，框架已就绪）：
   ```bash
   export ARROW_LAKE__RAG__QUERY_TRANSFORM=multi_query
   export ARROW_LAKE__RAG__MULTI_QUERY_VARIANTS=3
   ```
   - 注意：multi_query 会对每个变体并行检索（`pipeline.py:216`），单 query 延迟略增但召回提升。
   - extract_llm 需可用（用于生成 query 变体）。

2. **调大 chunk_size**（`ingest/chunker.py:141` 默认值 + 摄入参数）：
   - `chunk_size: int = 512` → `1200`（字符，中文约 800 token）
   - `chunk_overlap: int = 64` → `150`
   - **需要重新摄入才生效**（已有数据集 chunk 已固化）。

3. **调大检索池**（env）：
   ```bash
   export ARROW_LAKE__RAG__DEFAULT_TOP_K=20
   export ARROW_LAKE__RAG__RERANKER_TOP_N=10
   ```

4. **（可选）reranker 升级 cross-encoder**（P1-2）：
   - `ARROW_LAKE__RAG__RERANKER=cross-encoder` + `RERANKER_MODEL=BAAI/bge-reranker-v2-m3`
   - 连续分，精排更准；但需 HF 模型本地缓存（容器内可能需联网下载）。
   - ollama binary 已够用时先不动，列为可选。

**验收**：复杂多 facet 问题召回更全；chunk_size 调大后单 chunk 信息量提升（需重摄入数据集对比）。

---

### 批 5 ｜ 🟦 GraphRAG 联动（P3）

**目标**：已建 KG 的数据集，问答自动注入实体关系三元组。

**配置（env，前提：数据集已跑过 `kg_build`）**：

```bash
export ARROW_LAKE__HUGEGRAPH__ENABLED=true
# 其余 hugegraph 配置见 CLAUDE.md 运维速查（host/port/auth/graph_name）
```

**机制**（已实现，`graph_rag.py`）：
- 开启后 `_get_rag_pipeline` 自动构造 `GraphRAGPipeline`（`_lake_rag.py:56`）。
- 每次问答：从问题抽实体（缓存 300s）→ 并行检索向量 + 图三元组 → RRF 融合（`graph_weight=0.3`）→
  `graph_qa` 模板生成。
- KG 不可用时优雅降级回纯向量 RAG（`graph_rag.py:217`）。

**验收**：涉及实体关系的问题（「X 和 Y 是什么关系」「X 包含哪些」）回答带结构化关系，且 citations
含 `knowledge_graph` 来源。

### 批 6 ｜ 🟩 存储优化（独立维度，env 为主）

> 详细论证见 [v1.9.5 存储反思](v1.9.5-storage-reflection.md)。本批源自「Lance 是否不宜放 MinIO」的反思。

**核心判断（纠正前提）**：「Lance 不宜放对象存储」**不成立**。Lance 就是为对象存储设计的列式
格式，放 MinIO 是主场。项目现有分层（HugeGraph/libSQL 放本地、Lance 放对象存储）已正确体现
「按访问模式选存储」原则。**Lance 不迁移，真正优化点是开本地读缓存。**

**改动清单**：

1. **开 Lance 本地读缓存**（P0，env，已验证生效）：
   - `ingest/storage.py:416` 把 `lance_cache_size` 传进 `lance.dataset(cache_size=...)`，是 pyarrow
     page cache，对向量随机读直接有效。**唯一的本地缓存杠杆**（无其他 prefetch 机制）。
   ```bash
   export ARROW_LAKE__STORAGE__LANCE_CACHE_SIZE=1073741824   # 1GiB
   ```

2. ✅ **Lance 表与原始文件分 bucket**（P1，已实现 v1.9.5）：
   - `StorageConfig.s3_uploads_bucket`（空=用主 bucket，向后兼容）+ `uploads_bucket` property。
   - `BlobStoreManager.ensure_bucket()`：bucket ≠ 主 bucket 时自动建（首次上传不 404）。
   - 原始文件路径（`datasets._get_blob_store` 上传/下载 + `_lake_ingest` store_raw_pdf）用 uploads
     bucket；backup/admin 保持主 bucket（数据面/管理操作）。
   - compose `S3_UPLOADS_BUCKET=arrow-lake-uploads`。199 blob/storage 测试零回归。

3. **minio 内存**（P2）：给 minio 容器足量内存（自身缓存热对象）。compaction 已开。

**验收**：
- 开 cache_size 后，重复 RAG 查询延迟下降（缓存命中）。
- 分 bucket 后 uploads 进独立 bucket，数据面查询不受 uploads IO 影响。

**不做**：把 Lance 从 MinIO 迁回本地卷（论证为倒退，丢多节点共享/弹性/备份）。

**P2 原始文件生命周期（已实现 v1.9.5）**：`StorageConfig.uploads_expiration_days`（默认 0=禁用，保留重解析能力）+ `BlobStoreManager.set_lifecycle_expiration(days)`（构造 uploads bucket 时按配置应用，boto3 `put_bucket_lifecycle_configuration`，minio 原生支持 expiration）。compose 注释化 `UPLOADS_EXPIRATION_DAYS=30` 按需启用。

## 7. 验收标准（整体）

落地后对同一组测试问题（建议 5–10 个，覆盖事实型 / 关系型 / 多 facet 型）对比 v1.9.4 基线：

- [ ] **召回**：hybrid 命中相关 chunk 数 ≥ 纯 fts（语义相关项不再漏）
- [ ] **详尽度**：回答平均长度 / 分点数显著提升
- [ ] **引用**：回答带 `[n]` 来源标注，且标注可对应到真实 context chunk
- [ ] **准确性**：旗舰 QA + 好 context 下，幻觉率下降（人工抽检）
- [ ] **KG**：关系型问题答案含结构化实体关系（批 5 数据集）
- [ ] **回归**：`tests/unit/rag/` + `tests/integration/test_rag_integration.py` 全绿
- [ ] **存储**：开 `lance_cache_size` 后重复 RAG 查询延迟下降（缓存命中）；分 bucket 后 uploads 独立、数据面 IO 不受影响
