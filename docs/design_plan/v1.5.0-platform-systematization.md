# Arrow Lake v1.5.0 — Platform Systematization Plan

**Version:** v1.5.0-draft
**Date:** 2026-05-26
**Preceded by:** v1.4.4 (RAG Quality Leap + SDK/CLI High Performance)
**Source:** BMAD Party Mode Product Review (6 agents, 5 rounds)
**Theme:** 不加功能，系统化现有能力 — 可靠、可发现、可信赖

---

## 一、版本定位

### 核心原则

> Arrow Lake v1.4.4 的技术广度已足够支撑平台定位。v1.5.0 的全部任务不是"做得更多"，而是让已有的能力变得**可靠（质量）、可发现（体验）、可信赖（文档）**。

### 产品愿景确认

Arrow Lake 是一个**端到端统一多模态数据湖平台 + 知识工程**系统，支撑 AI 及传统业务数据全生命周期管理，提供 RAG、知识图谱等前沿 AI 服务能力。

### 版本关键词

**Reliable · Discoverable · Trustworthy**

## 二、架构分层重构

### 目标架构：三层 + 双平面

```
┌──────────────────────────────────────────────────────────────┐
│  Application Layer (应用层)                                   │
│  CLI · SDK · REST API · 场景化入口                           │
│  用户直接触达的界面层                                          │
├──────────────────────────────────────────────────────────────┤
│  Service Layer (服务层)                                       │
│  ┌─────────────────────┐  ┌──────────────────────┐          │
│  │   Data Plane        │  │  Knowledge Plane      │          │
│  │   Ingest Pipeline   │  │  RAG Engine           │          │
│  │   SQL Analytics     │  │  Knowledge Graph      │          │
│  │   Export            │  │  Embedding Service    │          │
│  │   Quality Gates     │  │  LLM Gateway          │          │
│  └────────┬────────────┘  └──────────┬───────────┘          │
│           │                          │                       │
│           └──────────┬───────────────┘                       │
│                      │ Gravitino 元数据桥接                   │
├──────────────────────┴───────────────────────────────────────┤
│  Kernel Layer (内核层)                                        │
│  Storage Abstraction (LanceDB) · Connectors · Vector Engine  │
│  Compute Runtime (Daft/Ray) · Schema Management              │
└──────────────────────────────────────────────────────────────┘
         │
    ┌────┴─────────────────────────────────────────┐
    │  Infrastructure                              │
    │  MinIO/S3 · Redis · DuckDB · HugeGraph       │
    │  OTel Collector · Prometheus · Grafana        │
    └──────────────────────────────────────────────┘
```

### 关键约束

1. **层间单向依赖**：Application → Service → Kernel，不允许反向调用或跨层穿透
2. **双平面正交**：Data Plane 和 Knowledge Plane 通过 Gravitino 元数据层关联，不互相依赖内部实现
3. **接口契约化**：每层只暴露接口（Protocol / ABC），上层依赖接口而非实现

### 重构范围评估

| 模块 | 当前状态 | v1.5.0 目标 | 变更范围 |
|------|----------|-------------|----------|
| `arrow_lake/core/` | Lake Facade + 8 Mixins | 抽取 Protocol 接口，按层分组 | 中 |
| `arrow_lake/rag/` | 与存储层有直连路径 | 通过 Service Layer 抽象访问 | 中 |
| `arrow_lake/cli/` | 15 个命令组按技术模块分组 | 按场景重组导航 | 低 |
| `arrow_lake/api/` | 15 个 Router | 保持不变，加 OpenAPI spec | 低 |

### Phase 1: 质量体系强化（2 周）

**目标**：分层覆盖率替代总覆盖率，关键路径测试补齐。

#### 1.1 测试分层策略

| 层级 | 覆盖率目标 | 测试重点 |
|------|-----------|----------|
| Kernel | ≥ 95% | Schema 迁移、连接池生命周期、并发写入隔离性、存储抽象接口合约 |
| Service | ≥ 90% | Pydantic model 验证、RAG pipeline contract、质量门控逻辑 |
| Application (集成) | ≥ 80% | CLI exit code + stdout、SDK 调用链、API 端到端 |
| E2E | ≥ 60% | 关键用户旅程（Ingest → Search → RAG） |

#### 3.2 Starter 体验（🟢 "第一次约会"）

零配置完成第一个有意义场景：

```
$ arrow-lake quickstart

? 你想做什么？
  ❯ 用我的文档做问答 (RAG)
    分析现有数据 (SQL)
    构建知识图谱

→ 选择了 RAG 场景

? 上传你的文档（拖拽或输入路径）: ./faq-docs/

⠋ 正在处理 23 个文件...
  ✓ 解析完成 (PDF: 15, TXT: 8)
  ✓ 分块完成 (chunks: 142, avg: 512 tokens)
  ✓ 嵌入完成 (model: all-MiniLM-L6-v2)
  ✓ 索引构建完成 (vector + FTS)

✅ 知识库就绪！试试问一个问题：

  $ arrow-lake search "退货流程是什么？"

💡 接下来你可以：
  • 连接更多数据源：arrow-lake connect ./more-data/
  • 提升检索质量：arrow-lake knowledge rag-config --enable-reranking
  • 查看完整指南：docs/quickstart.md
```

#### 3.3 错误翻译层

| 原始错误 | 翻译后 |
|---------|--------|
| `daft.exceptions.ColumnNotFoundError: Column 'embedding_vector' not found in schema` | `Column 'embedding_vector' doesn't exist. Available: [id, text, metadata, created_at]. Did you mean 'embedding'?` |
| `lancedb.errors.IndexNotBuilt` | `No vector index found. Run: arrow-lake knowledge build-index --column embedding` |
| `redis.exceptions.ConnectionError` | `Cannot connect to Redis. Check: docker compose ps redis. Guide: docs/compute-plane/deploy/docker-compose.md` |

实现方式：在 CLI 和 SDK 入口添加错误拦截层，根据异常类型映射到用户友好的消息 + 可操作建议。

#### 3.4 "推荐下一步"引擎

每个操作完成后输出 2-3 个建议（预定义决策树）：

| 触发操作 | 推荐下一步 |
|---------|-----------|
| 首次 ingest 完成 | `search` 提问 / `connect` 接入更多数据 / `knowledge build-index` 构建索引 |
| 首次 RAG 查询成功 | `knowledge rag-config --enable-reranking` / `knowledge graphrag` 开启图谱增强 |
| 创建数据集 | `analyze` SQL 分析 / `knowledge build-index` 构建搜索索引 |
| 开启 Helm 部署 | `admin observe` 配置监控 / `govern rbac` 配置权限 |

#### 3.5 SDK 改进

- `lake.status()` — 返回当前 lake 状态摘要 + 建议操作
- 所有 Mixin 接口抽取为 `Protocol`（PEP 544），便于用户自定义实现
- 错误翻译层同时应用于 SDK 调用链

### Phase 4: 架构加固（1 周）

**目标**：解决依赖风险和单点故障。

#### 4.1 Redis 高可用方案

| 方案 | 复杂度 | 推荐 |
|------|--------|------|
| Redis Sentinel | 中 | ✅ v1.5.0 推荐 |
| Redis Cluster | 高 | v2.0 考虑 |
| 本地降级（JWT 无状态化 + 内存 semaphore） | 低 | 作为 fallback |

**交付物：** Redis Sentinel 配置 + Docker Compose profile + 降级策略文档

#### 4.2 外部依赖 Criticality 分级

| 依赖 | Criticality | 宕机影响 | 降级策略 |
|------|-------------|----------|----------|
| LanceDB | Critical | 数据不可读写 | 无降级，必须高可用 |
| Redis | Critical | 认证/分布式锁失效 | JWT 无状态降级 + 内存锁 |
| DuckDB | High | OLAP 分析不可用 | 读缓存 + 只读模式 |
| MinIO/S3 | High | 新数据不可写入 | 本地缓存队列 |
| HugeGraph | Medium | 图谱增强不可用 | 纯向量/FTS 检索降级 |
| Gravitino | Low | 元数据同步暂停 | 本地元数据继续服务 |

#### 4.3 SLO 定义

| 指标 | SLO | 测量方式 |
|------|-----|----------|
| RAG 查询 P95 延迟 | < 2s | OTel trace |
| 向量检索 P99 延迟 | < 500ms | OTel trace |
| 数据摄入吞吐量 | > 100 docs/s | Prometheus counter |
| 可用性 | > 99.5% | Uptime probe |
| 索引构建成功率 | > 99% | Job metric |

## 五、STOP / START / CONTINUE

### STOP

| 行为 | 原因 |
|------|------|
| 在 v1.5 加新功能 | 已有功能未被系统化交付，加功能加剧混乱 |
| 用总覆盖率 80% 当质量指标 | 掩盖关键路径覆盖不足 |
| README 同时讲 SDK 和 K8s 平台 | 信息过载，读者流失 |
| 文档按文件系统组织 | 用户按场景思考，不按目录思考 |
| CLI 按技术模块分组 | 用户按目标操作，不按内部架构操作 |

### START

| 行为 | 理由 |
|------|------|
| 维护依赖兼容性矩阵 | 三框架共存，生存级需求 |
| 按三层架构重组所有用户触点 | 平台定位需要清晰结构映射 |
| 测试分层覆盖率追踪 | 比总覆盖率更能反映真实质量 |
| 编写 OpenAPI Spec | 没有 API 合同就没有可信集成层 |
| 找设计伙伴用 Starter 路径实测 | 所有 DX 假设都需要验证 |

### CONTINUE

| 行为 | 理由 |
|------|------|
| 全栈平台定位 | 核心价值，不是缺陷 |
| Gravitino 元数据治理集成 | 投资已完成，继续深化 |
| 安全加固节奏 | v1.4.2 成果显著，保持 |
| LanceDB 作为向量引擎 | 选型合理，优化而非替换 |
| 2872 测试基数 | 分层优化的好基础 |

## 八、风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 文档重组工作量大 | 可能延期 Phase 3 | 优先 P0 交付物，P2 可延到 v1.5.1 |
| CLI 重组可能破坏现有用户习惯 | 用户迁移成本 | 保留旧命令作为 alias，至少保留一个版本 |
| Redis 高可用增加部署复杂度 | 与"简单部署"目标冲突 | Docker Compose 默认单节点，HA 作为可选 profile |
| 测试分层可能发现深层问题 | 修复耗时 | 预留 buffer 时间，P2 问题可延到 v1.5.1 |
