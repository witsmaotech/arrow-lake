**日期**: 2026-04-15
**参与者**: Winston (架构师)、Amelia (开发者)、John (产品经理)、Paige (技术写作者)
**评审范围**: 80 Story 全量交付后架构、代码质量、产品就绪度、文档质量

## Winston（架构师）

### 1. DARMU 技术栈 —— 实际跑起来的是 LanceDB + DuckDB + Arrow

Daft 和 Metaflow 基本是摆设——Daft 只出现在占位符中（`daft_sql()` 抛出 `NotImplementedError`），Ray 有配置但 Bridge 层未使用，Metaflow 在配置中引用但无实际集成。LanceDB 承担了所有核心工作：向量搜索、全文搜索、数据存储。DuckDB 处理所有 SQL 查询路径。

**风险：** LanceDB 的 API 跨版本不稳定。一次大版本升级可能导致大量重构。

### 2. Bridge 模式是正确的分解方式，但有三个结构性问题

- **没有共享基类或 Protocol。** 每个 Bridge 都用 `storage: Any` 和 `config: Any`，没有结构化类型约束。
- **DuckDB 初始化代码在 4 个 Bridge 中重复。** 应提取为 `DuckDBSession` 上下文管理器。
- **危险关键字正则在 6 个文件中各有一份副本**，且关键字列表不一致。应提取到 `arrow_lake/validation.py`。

### 3. 关键瓶颈：每次 SQL 查询都会将整个数据集加载到内存

`OlapSearchBridge.query()` 先把整个 Lance 数据集物化为 Arrow Table，再注册到 DuckDB。对于 100GB 的数据集，意味着每次查询占用 100GB 内存。`max_result_rows` 只截断输出，不限制输入。

**这是当前最大的架构风险。** 修复方案：Lance Scanner + DuckDB Arrow Scanner 集成 + RecordBatchReader 流式迭代。

### 4. Facade 是"漏水的抽象"

- `ingest()` 和 `catalog()` 9 个 Sprint 后仍是空壳
- `LineageStore` 和 `AuditTrail` 完全绕过 `LanceStorageManager`
- 每次调用都重新实例化 Bridge，没有连接池或资源复用

### 5. 配置膨胀超过实际功能

`ArrowLakeConfig` 有 19 个子配置，其中 argo、autoscale、lifecycle 等配置的功能尚未实现。配置复杂度超越实际功能 = 技术债。

| # | 位置 | 问题 |

| 1 | `export.py:148-149` | **路径遍历检查是死代码。** `Path(output_path) != path` 永远为 `False`（上一行就是 `path = Path(output_path)`），`..` 检查永远不执行。`../../etc/passwd` 可直接通过。 |

- `Lake` Facade 返回类型全是 `Any`，缺少具体类型
- `lineage.py:164` 静默吞掉存储异常（直接返回 `[]`）

## John（产品经理）

### 1. SDK 存在公信力问题

README 展示了 `Lake.from_yaml()`、`lake.ingest()`、`lake.quality_check()`，但：
- `from_yaml` 根本不存在
- `ingest()` 直接抛出 `NotImplementedError`

"基础用法"部分四个调用中有两个是运行即崩溃的死代码。使用指南也使用 `lake._get_storage()` 私有方法。

### 2. 功能完整度出人意料地强，但有一个明显缺口

80 Story 覆盖完整数据生命周期：摄取、搜索（向量/FTS/混合/分面/集成）、质量、去重、导出、血缘、审计、版本管理、CLI、HTTP。

**关键缺口：**
- `Lake` Facade 上没有 `ingest()` —— 用户最期望的第一个操作
- 缺少 `lake.list_datasets()`、`lake.delete_dataset()`、`lake.upsert()`
- 缺少 `lake.search(query_text=...)` 自动嵌入入口
- 宣称支持"流式写入"但文档只展示了批量写入

### 3. 文档语言问题

全部中文。面向全球数据工程师社区，英文必须是主语言。此外缺少 LICENSE 文件、PyPI 包、CONTRIBUTING.md。

### 4. v0.2.0 第一优先级

**完善 `Lake` Facade：**
1. 实现 `Lake.ingest()` 
2. 实现 `Lake.catalog()`
3. 添加 `Lake.list_datasets()`、`Lake.delete_dataset()`
4. 添加 `Lake.search(query_text=...)` 自动嵌入
5. 更新所有文档，只使用 `Lake` 公共方法

## Paige（技术写作者）

### 1. README 新用户信任危机

快速入门代码展示不存在或会崩溃的方法。在用户接触的第一秒就建立了错误预期。

### 2. usage-guide.md 广度令人印象深刻

16 章、900 行，但第 2 章使用 `lake._get_storage()` 私有方法。此外缺少错误处理示例和故障排查章节。

### 3. 关键缺失文档（按优先级）

| 优先级 | 文档 | 说明 |
|--------|------|------|
| **CRITICAL** | API 参考文档 | 没有生成的参考。Docstring 质量很高，用 `pdoc` 或 `mkdocstrings` 跑一遍即可 |
| **HIGH** | 架构文档 | 没有说明数据流、组件关系、存储布局 |
| **HIGH** | CONTRIBUTING.md | 没有开发环境搭建、测试命令、PR 流程指南 |
| **MEDIUM** | 英文 README | 中文-only 阻断全球社区 |

### 4. 示例 Notebook 与代码库脱节

- `quickstart.ipynb` 用原生 numpy 代替 `lake.search()`
- `hybrid_search.ipynb` 引用了不存在的 `alpha` 参数
- `05_quality_pipeline.ipynb` 有语法错误（多余引号）
- `06_metaflow_pipeline.ipynb` 导入了不存在的 flow 模块

### 5. 语言建议：中英双语，英文为主

README 和 CONTRIBUTING 用英文。使用指南可保留中文作为次级文档。
