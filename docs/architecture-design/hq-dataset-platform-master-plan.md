# 高质量数据集平台建设总体规划(Master Plan)

> 版本:v1.0 · 日期:2026-08-21 · 状态:**已评审定稿(待批准启动 MS1)**
> 文档定位:本方向**唯一管理文档**——背景/目标/决策/里程碑/风险/评估/实施全部在此维护;内部支撑分析材料与试点域业务文档不在公开仓库
> 决策级别:产品方向级(影响后续 2-3 个大版本) · 推进方式:**里程碑制,阶段门管控,步步为营**

## 一、整体背景

### 1.1 业务背景(为什么做)

需求源自**首个试点域**:行业安全监测领域的大规模物联感知场景(万级前端设备、亿级日增监测数据、30+ 业务场景)。客户的战略是把数据存量升级为数据要素:建设**面向行业垂类大模型的高质量数据集体系**,通过第三方质量认证(如信通院 ADAQ),以数字合约进入可信数据空间流通——12 个月建设周期、6 个业务里程碑。

试点域业务方法论(调研报告/本体手册/实践手册,内部材料)给出完整框架:八大本体模型(M1-M7+ME)、ODL-SDL-ADL-PDL 四层存储、DQM 2.0 三层质量防护、L1-L4 分层标注、五维质量评估、数据飞轮与数字合约。**其中工具链明确:标注用 Label Studio(开源+定制插件)+ 自研 AI 预标注 + 标注管理后台**——平台选型与业务预期天然吻合。

> **产品定位声明**:本规划描述的是**领域无关的平台能力**(本体形式化/语义层/决策行动层/标注供应链/质量评估/语料供料);文中出现的具体域示例(燃气泄漏研判、规则编号、验收数据集等)均为**试点域实例化**,更换业务域时方法论与里程碑不变,仅替换域本体内容与验收样例。

### 1.2 平台现状(Arrow Lake 有什么)

**强项(代码级核实,2026-08-21)**:

| 能力 | 现状 | 对业务需求的意义 |
|---|---|---|
| 摄入与存储 | 13 类数据源异步摄入 + Lance@MinIO 版本化 + DuckDB OLAP | ODL/SDL 承载 |
| 入口质量门 | `quality/gate.py` IngestionQualityGate:schema 校验+评分阈值+**死信路由** | DQM 第一层结构已存在 |
| 质量规则/画像 | rules/scoring/profiler/dedup/schema_validation/nemo_curator + `/quality/*` 端点 8 个 | 五维评估地基 |
| LLM 标注雏形 | `POST /{name}/quality/llm_label` + llm_enrich | L2 预标注种子 |
| 脱敏 | masking_engine(泛化/部分/置空/HMAC),查询时执行 | 标注下发前脱敏 |
| 抽取模板体系 | 8 个 YAML 模板;project_concept_graph=22 类型严格枚举+15 关系枚举+definition 必填 | **隐式本体**(待形式化) |
| 模板管理 | v1.10.0 CRUD+AI 生成+试跑+质量验证页 | 本体工程管理面雏形 |
| KG | HugeGraph+hyper-extract+实体消歧+增量构建+`/kg/quality` | 图实例存储 |
| 权限与审计 | v1.10.5 RBAC/scopes/审计 | M5 主体模型子集 |
| 血缘/版本 | sys_lineage_events+Lance 版本+restore | 血缘链起点 |
| 治理元数据 | Gravitino tags→ACL/masking/retention(保持现状,前置评估已决策) | 治理执行层 |

**红区(缺失)**:本体形式化与校验(模板约束是自然语言散文)、人工标注工作流(完全空白)、数据集级五维评估、语义对齐引擎、PDL 发布层、漂移监控、数据飞轮闭环。

### 1.3 演进缘起(决策历程)

业务文档加载学习(2026-08-21)→ 方向评估(Arrow Lake×Semantica×Label Studio,结论:方向对+三修正)→ 自我 review(修正两处言过其实+补三处遗漏)→ 深度分析(5 个并行 agent 全量精读)→ 战略定稿(路线 B)→ 两问深化(三层落地+标注供应链)→ **本总规划(收拢为唯一管理文档)**。

## 二、目标

### 2.1 北极星(一句话)

把 Arrow Lake 从"数据湖仓"进化为**本体驱动的高质量数据集平台**:语义层统一对象口径 → 决策层可审计研判 → 行动层受控行动 → 标注供应链决策驱动 → 五维质量门 → 训练语料四形态供给,形成"数据→本体→标注→模型→回流"的完整飞轮。

### 2.2 分项目标(可量化)

| 维度 | 目标 | 度量 |
|---|---|---|
| 本体 | 试点域(燃气) M1+M3 落地,自有域(22 类)全量形式化 | SHACL 门禁拦截率可度量;规则带国标版本引用 |
| 语义层 | 对象标识锚定 + Object Set 查询 | 跨源同口径验证通过 |
| 决策/行动 | 试点域(燃气)vertical slice 端到端 | 研判依据可溯率 100%;越权拦截生效 |
| 标注 | 试点样例数据集 走通 L2→L4 | kappa≥0.81;预标注采纳率有基线 |
| 质量 | 五维评估+星级准入门 | 训练级 95 分门禁生效 |
| 供料 | 语料四形态导出 | SFT 指令对/三元组/偏好对/黄金集各有样例产出 |

### 2.3 范围边界(五件不做)

本体运行时(M4 通用编排/Saga/Action 执行引擎)、Neo4j 第二图库、联邦学习平台、区块链确权结算、大模型训练设施。**边界变更需重新评审本规划。**

## 四、里程碑路线(总览)

### 4.1 依赖与时序

```
MS1 本体与规则地基 ──┬──▶ MS2 语义层 ──▶ MS3 决策与行动层(vertical slice)
   (~3周,承重墙)     │
                     └──▶ MS4 标注闭环 ──▶ MS5 评估发布与语料
                        (~3-4周,可并行)    (~3周)
```

串行主线(默认小团队):MS1→MS2→MS3→MS4→MS5,合计 **14-16 周**;若有余力,MS4 可与 MS2/MS3 并行(压缩至 ~11 周)。

### 4.2 里程碑总览

| 里程碑 | 主题 | 周期 | 依赖 | 退出标准(DoD) | 业务价值 |
|---|---|---|---|---|---|
| MS1 | 本体与规则地基 | ~3 周 | 业务专家并行介入 | 拦截率可度量+本体版本 diff 可查+专家评审一轮签字 | 抽取质量门+可审计规则知识 |
| MS2 | 语义层 | ~2-3 周 | MS1 | 跨源同口径验证通过+对象查询 API 可用 | 统一对象口径(治"A 系统正常 B 系统泄漏") |
| MS3 | 决策与行动层 | ~3 周 | MS2 | 试点域(燃气)vertical slice E2E+三项度量基线 | 可审计研判+受控行动 |
| MS4 | 标注闭环 | ~3-4 周 | MS1 | 试点样例数据集 L2→L4 全流程跑通 | 高质量标注生产线 |
| MS5 | 评估发布与语料 | ~3 周 | MS4 | 发布 E2E+语料四形态样例+黄金集挂入回归 | 认证级质量门+训练供料 |

### 4.3 阶段门机制(步步为营的执行纪律)

1. 每个 MS 启动前出**版本级实施计划**(对齐版本迭代 playbook 六阶段:规划→TDD→实现→review→发版→复盘);
2. 每个 MS 结束跑 **DoD 验收**,不达标不进入下一 MS(可降级:记录缺口、缩范围、延期,但不带病前进);
3. MS 间允许**部分重叠**(如 MS4 的 LS 部署准备可与 MS3 后期并行),但 DoD 独立验收;
4. 任何范围/边界变更回写本规划 DR 清单并评审。

## 五、各里程碑功能点明细

### MS1:本体与规则地基(~3 周)

**目标**:模板的隐式本体形式化为机器可校验的 SHACL;建立规则注册表(可审计研判知识);本体版本管理。

| # | 功能点 | 形态 |
|---|---|---|
| F1.1 | 本体核心模块 | `arrow_lake/ontology/`:TemplateOntologyAdapter(模板 YAML→OWL dict)/ ShapeBuilder(**枚举+必填+类型对 PropertyShape**,Semantica 生成器不做的恰是核心)/ OntologyValidator(pyshacl 封装+violation 分级)/ 导出 Turtle |
| F1.2 | 本体与规则存储 | system_db 迁移 V010:ontology_versions(快照+diff)+ontology_rules(rule_id/条件表达式/结论/**来源引用含国标版本**/状态) |
| F1.3 | SHACL 质量门接入 | KG build `_finalize` 前校验;**shadow 模式两周**(只计数)→强制;违规分级 reject/warn |
| F1.4 | 管理 API 与页面 | 本体 CRUD API + console 本体管理页(浏览/版本 diff/规则列表) |
| F1.5 | prompt 增强 | shapes 渲染回模板 rules 段(本体驱动抽取的轻实现) |
| F1.6 | 自有域验证 | project_concept_graph 22 类型全量 shape 化,门禁度量基线报告 |
| F1.7 | 试点域(燃气)共建(**业务专家**) | M1 对象清单+标识规范(`GAS.SEGMENT.RG01-001-S047`)+试点域判定级规则 10+ 条;九步法②⑤⑧专家环节 |

**DoD**:①门禁前后缺陷逃逸对比可度量;②本体版本 diff 可查;③试点域(燃气) M1+M3 经专家评审签字一轮。**风险钩子**:R1(专家缺位→F1.7 挂起,MS1 以 F1.6 收口)。

### MS2:语义层(~2-3 周)

**目标**:对象标识锚定+语义对齐,提供 Object Set 式查询(返回业务对象而非数据行)。

| # | 功能点 | 形态 |
|---|---|---|
| F2.1 | 对象标识规范 | `领域.类型.序列` 标识+entity_id_map(源系统 ID→对象 ID) |
| F2.2 | 语义对齐引擎 | semantic_alignment 配置(ontology_ref/unit/transform 如 kPa→MPa)→SDL 物化或查询视图;对齐血缘记录 |
| F2.3 | Object Set 查询 API | `POST /api/v1/objects/query`:按对象类型+过滤 → Lance 列+KG 子图+规则引用的聚合对象 |
| F2.4 | console 对象浏览页 | 按业务对象浏览(管网/告警事件),非按表 |
| F2.5 | 试点域(燃气)对象化样例 | 管段/阀门/调压站/传感器/告警事件 对象化接入 |

**DoD**:跨源同口径验证(同一浓度值经两源系统→同一对象同一属性同一单位)。

### MS3:决策与行动层(~3 周)

**目标**:研判(规则求值+GraphRAG grounding)与受控行动(行动目录),试点域(燃气)vertical slice 端到端。

| # | 功能点 | 形态 |
|---|---|---|
| F3.1 | 研判 API | `POST /api/v1/decisions/assess`:对象→M3 规则求值→结论+规则编号引用+置信度 |
| F3.2 | Grounding 集成 | GraphRAG 上下文注入研判;回答只引本体对象+附引用链 |
| F3.3 | 行动目录 | `arrow_lake/actions/` YAML(permission/preconditions/execute/audit/postEvent)+执行中间件(复用 require_permission+audit,加前置状态) |
| F3.4 | 事件注册表(ME) | 行动后置事件发布+订阅(进程内;Redis streams 可选) |
| F3.5 | **vertical slice** | 告警对象→试点域规则研判→预警发布行动(权限/前置状态/审计/后置事件)端到端 |
| F3.6 | 度量 | 研判准确率(vs 规则黄金集)/依据可溯率/越权拦截计数 |

**DoD**:vertical slice E2E 演示+三项度量基线报告。

### MS4:标注闭环(~3-4 周)

**目标**:决策驱动的标注供应链——采样→预标注→人工校对→质检→ADL。

| # | 功能点 | 形态 |
|---|---|---|
| F4.1 | LS CE 部署 | `deploy/docker-compose.annotation.yml`(独立 profile);S3 source storage(access key)接 MinIO;内网段 |
| F4.2 | **本体→标注模板生成器** | M1/ME/M3 → LS labeling config(NER Labels+Relations)+L4 字段结构(五段:objects/events/rules_applied/scenario/relations) |
| F4.3 | 采样引擎 | 四策略(uncertainty/diversity/committee/**failure_case**)+预算分配(高价值数据集优先,深度标注成本约束) |
| F4.4 | 预标注管线 | hyper-extract→NER spans+relations 映射;import **内嵌 predictions**(静态,无需 ML backend);复用 `/quality/llm_label` 做 L2 事件分类预标 |
| F4.5 | 回收与 ADL | webhook 接收(1s 超时无重试→**轮询对账为主**);ADL=Lance 版本化(join 源记录+标注+本体引用+标注者元数据) |
| F4.6 | 质检自建 | Fleiss' kappa 计算/多人任务复制/分歧仲裁流(L4 三审:专家→交叉→终审) |
| F4.7 | console 标注管理页 | 项目/指派/进度/质检看板/分发回收全审计(sys_audit_trail) |
| F4.8 | 脱敏前置 | 下发前按敏感级别 masking(L2 泛化/L3 假名);LS 为 transient 工作区 |

**DoD**:试点样例数据集(燃气泄漏)样例走通 L2→L4 全流程,机械环节无人工干预;kappa 达标样本产出。

### MS5:评估发布与语料(~3 周)

**目标**:五维质量门+发布层+训练语料四形态,闭合数据飞轮。

| # | 功能点 | 形态 |
|---|---|---|
| F5.1 | 五维评估引擎 | 权重 0.20/0.35/0.20/0.15/0.10;星级(<60→≥95);准入门 85/95/98;一票否决项;报告页 |
| F5.2 | 相关性抽样任务 | 抽样评估反哺标注队列 |
| F5.3 | 漂移监控 | 分布基线+KL 散度(7 天基线/1h 窗) |
| F5.4 | 发布层 | 数据集目录+发布流程(版本锁定/元数据登记/CHANGELOG/MAJOR.MINOR.PATCH 语义) |
| F5.5 | 记录级血缘链 | 采集→门控→对齐→脱敏→标注→评估→发布 全链记录 |
| F5.6 | **语料四形态导出** | ①SFT 指令对(system prompt=本体定义+M3 规则,target=L4 全要素)②预训练三元组 ③RLHF 偏好对(专家 vs 模型研判)④回归黄金集(1000+ 必过) |
| F5.7 | 数据集规格书 | 业务模板字段(id/version/category/lifecycle_status/schema/scale/quality/labeling/usage)的 YAML 发布物 |
| F5.8 | 飞轮回流钩子 | 研判失败案例→采样队列(决策驱动闭环) |

**DoD**:发布流程 E2E+四形态语料样例导出+黄金集挂入回归测试。

### 6.2 工程纪律(全程有效)

- 热路径零改动:ontology/annotation/actions 均为独立模块;LS 独立 compose profile,不进默认栈
- 新路由/改 lifespan 一律 `docker restart arrow-lake-api-1`(历史教训:--reload 不可信赖)
- 密钥/配置双 .env 同步;LS token 走同样管理
- 测试用 .venv;新增模块单测覆盖(TDD);门禁类功能必须有 shadow 期
- system_db 新迁移同步 bump 幂等测试(V010 起)
- 对外集成(LS)一律轮询对账为主、事件为辅(webhook 无重试)

### 6.3 业务专家协作(R1 专项)

每域建模启动前确认:专家名单/评审会节奏(建议双周)/签字流程;平台侧交付评审材料包(对象清单+规则草案+校验报告)降低专家负担;专家产出物(对象/规则/签字)进 system_db 留痕。

### 7.2 三件套选型关键事实(核查过)

**Semantica**:ontology 模块可独立(纯 dict+rdflib 内存);SHACLGenerator 只反映观察到的约束(枚举/必填需手动 PropertyShape——恰是我们的核心工作);pyshacl 可选 extra;`not conforms→exit 1` 天然质量门;⚠️ pip 全量依赖 ~2GB、`_run_pyshacl` 私有 API、**不做本体驱动抽取**(方向是"抽取→图→反推")。
**Label Studio CE**:Apache-2.0;import ≤25 万条/50MB 且** predictions 内嵌=静态预标注**;webhook 1s 超时无重试无签名;导出同步易 90s 超时(用 Snapshot API);S3(access key)source storage ✅;NER+Relations config 成熟;❌ overlap/agreement/指派/自动主动学习/SSO/RBAC 全 Enterprise——但业务手册本来就是自建设计(kappa_calculator.py/active_learning.py/标注管理后台)。
**Arrow Lake(核查修正)**:quality 模块 16 文件含 gate 死信路由与 llm_label 端点——比早期评估认定的强;真正的红区只有本体形式化与标注工作流。
